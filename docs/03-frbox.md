# frbox 0.21.0 —— D300 的全系统模拟器

> 本文只讲**模拟器怎么造的**。为什么要造、造到哪一步、哪些结论已经被证伪，见
> [`02-findings.md`](02-findings.md) 和 `reports/14`–`32`。想直接跑，跳到第二节。

---

## 1. 它是什么，不是什么

**是**：一个纯 Python 3 的整机模拟器。把一个固件镜像和一份内存映射加载进去，从复位向量开始
逐条执行富士通 FR 指令，总线、外设、中断控制器、定时器、串口都是被建模的对象；带 monitor、
断点、快照、日志类别，命令行肌肉记忆对齐 QEMU。

**不是**：能让 D300 "开机出画面" 的模拟器。B 段 7 MB 固件执行到第 191,518 步、
停在 `0x000407D8` 的 `reti` 上，此后 PC 从系统栈弹出 0 —— 这不是模拟器的缺陷，是
**固件自身的启动链就到这里为止**（见第 7 节和 `KNOWN_ISSUES.md` 第 21 条）。

不依赖 QEMU，也不依赖 Java。整个东西是两个数字：

```
代码      ~3,600 行 Python（含 1,867 行取证脚本）
依赖      无（标准库）
速度      30,000–43,000 步/秒（单线程 CPython 3.13）
```

## 2. 跑起来

```bash
git clone https://github.com/Pinksert/D300-emulator-analysis
cd D300-emulator-analysis/emu

python -m frbox -M help                       # 列出机器
python -m frbox -M d300-a -c "bp 0xFE50C;c;info"   # A 段跑到启动链尽头
python -m frbox -M d300-b -c "bp 0x407D8;c;info"   # B 段同上
python frbox_selftest.py                      # 345 条断言
python fr_selftest.py                         # 63 条 CPU 断言
```

固件默认从仓库 `data/` 读（`A3000111.bin` / `B3000111.bin`）。要用别的目录：

```bash
FRBOX_FW_DIR=/path/to/D300Update python -m frbox -M d300-a
```

`data/` 里没有固件时第一条命令就会明确报 `固件不存在：<路径>`，不会静默跑 0 步。

## 4. CPU 核心

### 4.1 指令表从哪来

没有手写 800 条指令的 switch。解码表在 import 时从 binutils 的 CGEN 描述生成：

| 输入 | 用途 |
|---|---|
| `fr30.cpu` | 指令模式、操作数类型、`(dni ...)` 语义注释 |
| `fr30-opc.c` | 每个助记符的编码与宏展开 |

跑 `python fr_cover.py` 把 65,536 个 16 位字逐个喂进解码器，得到客观分数：

```
16 位编码 64,346 ／ 32 位首字 320 ／ 48 位首字 16 ／ 未定义 854
可执行编码 64,682   未实现指令 0   覆盖助记符 122 种
```

「未实现 0」是硬指标：凡解码成功就一定执行得下去，不会有 `Unimpl` 漏在运行路径上。

### 4.2 三个必须记住的语义坑

1. **目标是最后一个操作数**。`add Rj, Ri` 是 `Ri ← Ri + Rj`，反了就是全盘错。
2. **位测试立即数是掩码，不是位号**。`btstl #8` 测 bit3；`btsth #4` 测 bit6。
   而 `btsth #u4,@rN` 的立即数整体左移 4 位（半字节掩码），N 标志按**掩码结果的 bit7** 置位。
3. **延迟分支与 `call`**。带 `:d` 的分支后面那条指令一定先执行；`call` 把返回地址放进
   RP（`dr1`）而不压栈，所以模拟 `call` 的递归必须先存 RP。

### 4.3 EIT 的压栈顺序

```
进入：PS 先压系统栈，然后 PC；向量槽 = TBR + (255 - vec) * 4（倒序表）
返回：reti 从 SSP 依次弹 PC、PS
```

核对的抓手很硬：A 段 `TBR = 0x000FFC00`，槽 `TBR + 0x3FC = 0x000FFFFC` 读出
`0x000FC000`，正是复位入口 —— 如果表序反了，这个读值一定对不上。

## 5. 总线

`AddressSpace` 是三个概念的合体（对应 QEMU 的 AddressSpace + MemoryRegion）：

- **区域列表**按基址排序，二分查找；`rd/wr` 只认地址和宽度，不关心背后是什么。
- **跨区访问按字节拆**：一次 4 字节读落在两个区域交界上，会拆成两次访问分别记账。
- **未映射访问必须记账**：读返回 0、写丢弃，但地址与次数入表。`0x9F580000` 这块 1 MB
  外部 RAM 就是这么发现的 —— 固件往上写了 6,000 多次，一开始全进"未映射"。

低 4 KB（`0x0000–0x0FFF`）是 FR 的**直接寻址 I/O 区**，由一个 `DirectPage` 多路器占住，
内部再按偏移分派给具体设备。好处是"没建模的偏移"不会污染未映射统计，而是单独记一份
`unknown_reads`，能看出固件还摸过哪些寄存器（本次最热的是 `0x0DF`、`0x042/0x043`）。

## 6. 设备

原则：**有实证的才绑中断线**，推断出来的设备默认不占向量，并在 `info devices` 里标注来源。

| 设备 | 地址 | 实证程度 |
|---|---|---|
| 时钟/复位组 | 直接页 `0x480–0x48F` | ★★★ 位语义由 20 万步 watch 反推（见 6.1） |
| 串口 | 直接页 `0x60–0x67` | ★★☆ ISR `0x12FDB4` 的读写顺序反推寄存器布局 |
| 重载定时器 | 直接页 `0x10–0x17` | ★☆☆ 结构按 FR 系列通用布局摆，只作时间源 |

### 6.1 时钟寄存器组 0x482：一个"必须建模，否则永远自旋"的例子

A 段复位第二跳的初始化里，向 `0x482` 写 `0x08`（启动位），然后死等 `0x482` 的 bit7。

早期我们靠 `--latch 0x482=0x88:2` 这种"第 N 次读之后返回某值"的补丁骗过它。做完
静态扫描（59 处引用，只有 6 条 `stb` 真写）和动态 watch（200,142 步里读 66,660 次、
写 6 次，**没有一次写 bit7**）之后结论变了：

> bit7 只能来自硬件 —— 软件从不写它。

于是有了 `dev_clk.py`：写 `0x08` 武装倒计时，`tick()` 递减，到 0 时硬件把 bit7 和
`0x484` 的"切换完成"位一起置起；`0x483` 要求连续写 `0xA5`、`0x5A` 两键才解锁。
建模后不再需要 `--latch`，A 段照常跑完 43,446 步。

这一段也是项目里唯一一次**推翻自己结论**的地方：早先报告把它当成"双机握手寄存器"，
是错的（`KNOWN_ISSUES.md` 第 20 条留着这段记录）。

## 7. 机器

不是"一个 CPU + 一份固件"，是两套独立的处理器子系统：

| | `d300-a` | `d300-b` |
|---|---|---|
| 角色 | IO 协处理 | 主控 / UI |
| ROM | `0x00080000` + 524,290 B | `0x00040000` + 7,340,032 B |
| RAM | `0x00001000–0x0007FFFF` | `0x00001000–0x0003EFFF` + `0x9F580000` 1 MB |
| TBR | `0x000FFC00` | `0x000EFC00` |
| SSP | `0x0007F000` | `0x0003F000` |
| 复位入口 | `0x000FC000` | `0x00040000` |
| 实测行程 | 43,446 步 / 824 个 PC / 0 次中断 | 191,518 步 / 1,239 个 PC / 1 次中断 |
| 停在哪 | `0x000FE50C` 的 `reti` | `0x000407D8` 的 `reti` |

这些数字没有一个是猜的：ROM 基址与长度 = 镜像文件大小；TBR = 向量槽里读出复位入口的
那个基址；RAM 上界 = 固件真正写过的高地址。

### 7.1 A 段的启动链是四条跳，第三跳是空 `ret`

```
0x000FC000 → 0x000F8010 → 0x00080044 → 0x000804FA → jmp 0x000FE426
                                          ↑ 一条孤立的 ret
```

`0x000804FA` 正是 REALOS `vsta_knl()` 该在的位置。内核对象其实都建好了（4 个 TCB 在
`0x00045C38` 起，自引用空环、状态 0），只是**从来没有 `sta_tsk` 把它们挂上就绪队列**。
`0x00080520`（main 的第二条 `call`）同样是纯 `ret`。

这四处空桩在 **1.02 / 1.03 / 1.10 / 1.11 四个版本里逐字节一致**（`probe/exp_xver.py`
从各自复位入口解析 call 链比对），所以不是"1.11 改了它"，是这套固件本来就这样。

### 7.2 于是有了 `boot_task`：跳过调度器，手工构造任务上下文

```bash
python -m frbox -M d300-a -c "boottask 0x8133A::0:0x80506 table rp=0x81338;info"
```

语义是：先跑到 `0x80506`（BSS 清零完成），然后把 PC 设成任务 1 的入口 `0x8133A`、
`r15` 设成栈、`r4` 放参数。跳进去之后：

- 1,981 步到达第一个硬件等待 `0x0DCD2C`；
- 期间踩过 **500 个应用区 PC**、发过 10 次 `int #0x40`、自己写了 6 个中断回调槽；
- 对照实验（不铺垫 BSS）同一段只有 207 个 PC、4 次服务调用，且在 `0x0FECA0` 散架。

回调槽的地址公式是 `0x3F01C + (vec - 0x10) * 4`，任务 1 真注册了 5 个：
`vec 0x13 / 0x19 / 0x1B / 0x24 / 0x3C`。

### 7.3 自旋消除器：把「等硬件就绪」放行

应用区代码里有三处同构忙等（置启动位 → 轮询就绪位）：

```
ldi:20 #0x0AF, r12      borl  #2, @r12      btsth #7, @r12      beq -4
```

前两处地址是 `ldi:20` 直接写死的，静态扫一遍就能认；**第三处不行**：

```
0x0CE132  borl  #2, r8      ; r8 = 基址 | 2，运行时才知道是多少
0x0CE134  btsth #4, @r8     ; 等 bit6
0x0CE136  beq   -2
```

所以 `frbox/autospin.py` 改成**运行期解密**：发现某个 0x100 窗口里连续 3,000 步没离开，
就单步 96 步把循环体收下来，在循环体里找 `btsth/btstl`，读它的 `u4` 掩码和**它用的那个
寄存器当前的值** —— 后者就是要等的寄存器地址；校验该位确实是 0（不是卡点就换下一个候选），
再置 1（`< 0x1000` 走直接页影子，否则直接写内存）。每处最多放行 8 次。

```bash
python -m frbox -M d300-a --task 0x8133A:0x462EC:0:0x80506 --rp 0x81338 --autospin \
       -c "c 40000;info;autospin"
```

实测三处全中（`results/frbox/autospin-session.txt`）：

| # | 轮询指令 | 等待 | 旧→新 | 发生在 |
|---|---|---|---|---|
| 1 | `0x0DCD30` | 直接页 `0x0AF` bit7 | `0x02→0x82` | 14,776 步 |
| 2 | `0x09C97A` | 直接页 `0x174` bit6 | `0x02→0x42` | 17,931 步 |
| 3 | `0x0CE134` | 直接页 `0x524` bit6（地址是算出来的） | `0x02→0x42` | 33,771 步 |

放行之后任务 1 执行到 **4,473 个不同 PC**（V7 手工抠掉三处卡点时是 500 个；V8 当时用的是
错栈顶，量到 4,512）、56 次
`int #0x40`、6 个回调槽。

### 7.4 故障判定：PC 掉出可执行区就停

放行之后程序一路跑到 `0x080504` 的 `ret`，然后 PC=0。V8 当时把原因归成「缺少调度器铺的
栈帧」——**这个判断是错的**。0.9.0 用变量隔离验了一遍，成因只有一条：

**`boot_task` 从来没设过 RP。** 任务的收尾是 `ld @r15+,rp; ret`，返回地址就是进函数时
压进栈的那个 RP。`boot_task` 只设了 PC / SP / r4，`dr[1]` 沿用了引导阶段最后一次 `call`
留下的 `0x00080500`，于是任务「返回」到 main 的尾巴上，一路弹栈弹到别处。

**顺带否掉一个很像的嫌疑**：栈顶取错（用表头字段 `0x4616C` 而不是真值 `0x462EC`）
**对结局没有影响**。RP 给对之后，栈顶从 `0x45000`、`0x46000`、`0x4616C`、`0x462EC`
一路换到系统栈 `0x7F000`，五种取值跑出来都是入口后 **32,726 步**、停在 **`0x081338`**，
一个字节不差 —— 因为任务的压栈/弹栈是平衡的，栈顶只决定那 4 个字节落在哪里。

RP 补成固件自带的停机占位（`boot_task(..., from_table=True, rp=0x81338)`），任务 1 跑
**42,442 步**（含 9,716 步铺垫）回到 `bra -1`，路径干净。**不需要先造一个假的调度器。**

### 7.5 REALOS 任务表

入口 `0x000FE000`：16 字节表头 + 8 条 `0x1C` 字节记录。

表头：`+0x00` 任务数（8）、`+0x04` 基准 SP `0x0004616C`（**不是任务栈顶**）、
`+0x08` `0xFFFFFFFF`、`+0x0C` `0x000C001C`。

| 偏移 | 含义 |
|---|---|
| `+0x00` | TCB 指针（相邻两条差 `0x2C`，即 TCB 大小） |
| `+0x04` | 任务号 `<< 16` \| 属性（`0x0004`，任务 5 是 `0x0002`） |
| `+0x08` | 保留 |
| `+0x0C` | 状态：`0x80000000` = 已激活，`0` = 未启动 |
| `+0x10` | 入口地址 |
| `+0x14` | 栈顶 |
| `+0x18` | 保留 |

八条记录（复位态）：

| # | 号 | 状态 | 入口 | 栈顶 |
|---|---|---|---|---|
| 1 | 1 | 已激活 | `0x08133A` | `0x0462EC` |
| 2 | 2 | — | `0x089632` | `0x046404` |
| 3 | 3 | — | `0x08B264` | `0x0464D8` |
| 4 | 4 | — | `0x08C486` | `0x046600` |
| 5 | 5 | 已激活 | `0x0A62FE` | `0x0466B4` |
| 6 | 6 | — | `0x0A6A30` | `0x0467D0` |
| 7 | 7 | — | `0x0A9A4E` | `0x0468FC` |
| 8 | 8 | — | `0x0ACC32` | `0x04699C` |

用 `machine.task_table()` 拿，`monitor` 里是 `tasks`。

以前模拟器会闷头执行一串 0，现在 `machine.run()` 每步先看 PC 落在哪个区：

```python
def exec_region(self, pc):
    r = self.bus.find(pc)
    return None if (r is None or r.kind not in ("rom", "ram")) else r
```

落在 IO 或未映射区就记 `machine.fault = (pc, 原因)` 并停下，`info` 里会打出来。
这条判据的价值是让"跑飞"变成一个明确的、可复现的停点，而不是一堆看不懂的 `ld 0x0000`。

### 7.6 原生 REALOS：不用我们的内核，用固件自己的（V10）

**这一节推翻了 §7.2 的前提。** 前面八个版本都说「A 段的 REALOS 进不去，只能手工造任务上下文 +
μITRON 半主机假装内核」。真实情况相反：内核一直在固件里，完整无缺，只是 CPU 少做了一步 ——
`andccr` / `orccr` 改 CCR 的 S 位时不换 `r15`。

FR80 的 CCR 里 S 位（bit 5）决定 `r15` 此刻指向 SSP 还是 USP。S 位一翻，`r15` 必须立刻
换支并把旧值存回原来那根。`ps` 的 setter 做对了这件事，`reti` 也因此从来没出过问题；
但 `andccr` / `orccr` 是直接给 `self.s` 赋值，绕过了 setter —— 于是
REALOS 恢复任务上下文时读的还是旧栈，`reti` 弹出错的 PC：

```python
# 修复前
self.s = (ccr >> 5) & 1

# 修复后：走 setter，setter 里那一段会把 r15 在 SSP/USP 之间换支
self.ps = (self.ps & ~0xFF) | ccr
```

修复之后，复位链一路跑到固件自己的调度器，**中间不需要我们做任何事**：

```
0x0FC000 复位（TBR=0xFFC00，r15 = SSP 0x7F000）
  → 0xF8010 → 0x80044
  → call 0x0FC020（立即 ret）/ call 0x0FC028（jmp 0x0FE426，REALOS 初始化 7,220 步）
  → call 0x0804FC（BSS 清零 + 配直接页）→ 回来写 *(0x3FBB0) = 2
  → bra 0x0FE4DE（首次派发）
43,428 步到 0x0FE4E6；0x0FE4DE–0x0FE514 这二十几条就是上下文恢复。
```

要干预的话在 **`0x0FE4E6`**（`r14` 刚装好 TCB、当前 TCB 变量还没被写回）把 `r14`
换成想要的那个任务的 TCB：`Machine.boot_realos(task_id)` / CLI 的 `--realos N`
/ monitor 的 `realos N`。

内核内部的结构 V11 已经挖到能逐字段引用（`probe/exp_realos_flgcb.py`）：

| 东西 | 地址 | 步长 / 索引 |
|---|---|---|
| 服务分发表 | `0x0FE3B8` | 索引 = 服务号 ×2（带符号），条目是相对基址的 int16 |
| 对象登记表 | `0x0FE180` | 0x10；第 N 个 = `0x0FE180 + (N-1)*0x10`；`+0x04` = 控制块指针 |
| 标志控制块 | `0x045C38` | 0x10；`+0x00` 自指（空队列）、`+0x04` 等待队列头、`+0x08` 位模式、`+0x0C` 回指登记表 |
| 任务表 | `0x0FE000` | 头部 0x10 + 记录 0x1C；**13 条**（id 1–12 + 空闲 0） |
| 任务控制块 | `0x0459FC` 起 | 0x2C；`+0x18` 保存的 SP、`+0x24` 回指自己的表记录 |

μITRON 的参数顺序是**从任务 1 的调用点指令**读出来的：`wai_flg` 的调用点 `0x08147E`
把 `p_flgptn / flgid / waiptn / wfmode` 依次放进 `r4 / r5 / r6 / r7`；`clr_flg` 的调用点
`0x08C82A` 把 `flgid / 位模式` 放进 `r4 / r5`。返回值一律在 `r12`。

**边界（V10 时的说法，V11 已作废）**：`*(0x45980)` 全程只被写过 1 次 ——
「至今没有发生过一次真正的任务切换」。原因见 `KNOWN_ISSUES.md` 第 39 条（现已标 `[FIXED]`）。

### 7.7 原生调度：任务真的换起来了（V11）

第 39 条在 V11 被推翻。真因不在内核，是仿真台缺了三样东西：

**① ILM 的优先级约定一直搞反了。** 正确是「级别号越小优先级越高，受理条件 `lvl < ILM`」：

```python
# 修复前：号越大越优先，受理条件 lvl > ILM
if lvl <= self.ilm: return False
# 修复后
if lvl >= self.ilm: return False
```

反证：任务上下文 PS 的 ILM 是 `0x1F`，而固件写进 48 个 ICR 的级别全在 `0x12–0x1F`。
按旧约定任务运行时一条中断都进不来。反过来则处处自洽 —— `vec 0x3F`（调度器）的 ICR=0x1E
是所有启用向量里最低的（调度器本就该最低），内核 `stilm #0x1E` 恰好只挡它一级，
派发因此被自然地推迟到 `reti` 回到任务上下文之后。

**② 直接页 `0x44` 是「请求调度」寄存器。** 内核每次要换任务就写 1 进去
（`0x0FECEC ldi:8 #1,r13` / `0x0FECF0 dmovb @0x44`，普通内存写不是 `int`），
30 万步写了 1,016 次，**固件里没有任何一处读它** —— 只写不读，只可能是硬件。
建模：写非零字节 → 挂一条 `vec 0x3F`，级别取固件自己写进 ICR 的值。

**③ `0x3F4` / `0x3FC` 是硬件优先级编码器。** 调度器 `0x0FE830` 写就绪位图进 `0x3F4`、
从 `0x3FC` 读回、乘 8 当就绪队列数组的下标。所以读回值必须等于「最高优先级号」：

```
结果 = 前导零个数 = 32 - bit_length(位图)
实测：0x50800000 → 1 ／ 0x80000000 → 0 ／ 0x00000001 → 31 ／ 0 → 32
```

三样齐了之后，100 万步里 `*(0x45980)` 换了 6 次（首次由 `0x0FE4EC`，其余由 `0x0FE8BE`）：

```
43,429 任务 1 → 43,516 任务 5 → 43,806 任务 1 → 44,614 任务 5
→ 45,125 任务 1 → 45,341 空闲任务，最后停在 0x000FE510（空闲任务的 bra -1）
调度请求 7 次 / 编码查询 7 次 / 位图为 0 的次数 0 / 中途没有停机
```

内核的调度数据结构（`probe/exp_realos_sched.py`）：

| 地址 | 内容 |
|---|---|
| `0x00045980` | 当前 TCB（调度器 `0x0FE798` 处读它） |
| `0x00045984` | 就绪位图，置位规律 `bit(31 − 优先级)` |
| `0x00045988` | 就绪队列数组，13 条 × 8 字节（next, prev），空队列自指 |
| `0x000459F0` | 派发请求字节，调度器用 `xchb` 原子读走并清零 |
| `0x0003F4 / 0x0003FC` | 优先级编码器（写位图 / 读优先级号） |
| 直接页 `0x44` | 请求调度（只写） |

⚠️ **A / B 两个模式必须分开报**：A = `enable_xfer()` + `realos.prepare()`，
任务 1 一路跑到底，30 万步 1,888 次服务、`*(0x45980)` 只写 1 次；
B = `boot_realos()`（= A + `enable_dispatch()`），只有 14 次服务、写 6 次。
CLI 的 `--realos` 走 B，裸跑默认 A（保住 V2–V10 的基线）。

⚠️ **别读成「相机跑起来了」**：13 个任务只有 3 个上场（1 / 5 / 空闲），
7 次调度全部来自内核自身的服务调用，没有一次是外设中断引发的。
见 `KNOWN_ISSUES.md` 第 41–44 条。

## 8. 中断

### 8.1 向量表

A 段 48 个槽（`0x10–0x3F`）实测分布：

```
39 个真 ISR（各自的入口都在应用区）
 8 个未用 → 兜底 0x000FE250 → 0x00081338 的 bra -1（原地停机）
 1 个特殊 → 0x3F → 0x000FE776（全固件唯一一条 andccr #0xEF，清 I 位并带队列）
```

`probe/exp_allisr.py` 把 48 个向量全量注入一遍，判定"是否精确 `reti` 回注入点、
`r15`/SSP 是否逐位复原"。结果 **39 个 OK**，8 个未用向量按预期进死循环，`0x3F` 走飞
（它本来就不是普通 ISR）。这一步是"中断通路真的可用"的硬证据，不是"看起来像能用"。

### 8.2 中断控制器

ICR 组在 `0x440–0x46F`，48 个寄存器对应 48 个向量，级别 `0x12–0x1F`。
但**哪条线接哪个外设，只有两条有实证**：

```
IRQ 0x1B → ISR 0x0012FDB4   串口（读直接页 0x60，非零则 set_flg(3, 0x20)）
IRQ 0x20 → ISR 0x0012FE54   EXT9（索引 0x1BC480 的 25 项函数指针表，末尾写 0x38 = 0xFB）
```

`icu.py` 因此做成可配置绑定表：没实证的设备 `bind=None`，需要时在机器配置里显式接上，
并在这份文档和报告里标明来源。

## 9. μITRON 半主机

`INT #0x40` 是陷阱入口（A 段 `0x000FE3C0`，B 段 `0x00040668`）。分发器是 6 条指令：

```
lsl    #1, r12            ; 服务号 ×2 → 字节偏移
ldi:32 #<表尾>, r13
lduh   @(r12, r13), r12   ; 取 16 位相对偏移
extsh  r12                ; 符号扩展（服务号是负数）
add    r13, r12           ; 目标 = 表尾 + 偏移
call   @r12
```

所以服务表是"相对表尾的有符号 16 位偏移"，服务号从 −1 递减。`fr_itron.py` 把每个服务
分成两档记：**真实现**（真的执行了那段内核代码）和**桩**（只回一个错误码），绝不混在
一个通过率里。

实测（D300 1.11）：

```
A 段 176 槽：真实现 18 条，桩 158 条
B 段 176 槽：真实现 56 条，桩 120 条
```

### 9.1 两档实现：一律立即返回 vs 真的会停

`attach_itron()` 走的是上面那条「查表 + 记日志 + 返回错误码」的路，**所有服务都立刻返回**。
这对 `sys_get_ver` 这类查询没问题，对 `sys_wai_flg` 就致命：等待立刻「成功」，
任务于是不停地在 `wai_flg → clr_flg → sta_tsk` 上打转。

`attach_kernel()`（CLI `--itron-block`）是另一档：只实现「会让任务停下来」的那部分，
其余仍然立刻返回。

| 服务 | 号 | `attach_kernel` 的行为 |
|---|---|---|
| `sys_wai_flg` | −46 | 按 `wfmode` 判（`0x02` 或等待 / 否则与等待），不满足就阻塞 |
| `sys_set_flg` | −48 | 真改位模式，并把新值写进 `r13` |
| `sys_clr_flg` | −47 | 真改位模式（`bits == 0` 当清全部） |
| `sys_sta_tsk` / `sys_ter_tsk` | −23 / −25 | 记进 `task_ops`，返回 `E_OK` |
| `sys_slp_tsk` / `tslp_tsk` / `dly_tsk` / `ext_tsk` | −38 / −37 / −85 / −21 | 一律按「停下来」处理 |

**参数顺序有两套**，混用不报错但会读错：

| 服务 | 标志号 | 位模式 | 模式 | 输出 |
|---|---|---|---|---|
| `sys_wai_flg` | `R5` | `R6` waiptn | `R7` wfmode | `R13` flagptn / `R12` err |
| `sys_set_flg` / `sys_clr_flg` | `R4` | `R5` | — | `R12` err |

阻塞时机器进入 `blocked` 状态，`run()` 立刻停手，`info` 会打出：

```
阻塞      任务阻塞于 wai_flg(flag 3, 0x2000, mode=2)，当前值 0x0（或等待：任一位）   @ PC=0x00081490
          用 flag set <id>=<bits> 注入外部事件，再 resume 继续
```

`resume()` 不是「直接往下走」，而是把 CPU 的 PC 和全部寄存器恢复到那条 `int` 指令之前
**重跑一遍** —— 这样 `r12` / `r13` 由同一条代码路径产生，不会出现「状态对了但寄存器没填」。

### 9.2 `--autoevent`：把事件补上并记下来

`attach_kernel(auto_event=True)`（CLI `--autoevent`）在等不到时直接把等待位补上，
并把这次补的事件记进 `kernel.events`。跑一遍就能得到**整条启动握手序列**：

```
 #  步数      PC       标志  等待位     模式  送来之前的值
 1  9,841     0x081490  3     0x2000     2     0x00000000
 2  17,320    0x08C808  1     0x8000     2     0x00000000
 ...
13  35,345    0x08195E  1     0x4000     2     0x00008200
```

这不是「假装跑通」：每个事件都是一次真实的 `wai_flg` 调用，步数和 PC 都能逐条回查。
它回答的是「如果外部世界按这个顺序送事件，任务会怎么走」，而不是「任务自己能跑完」。

## 10. 快照

`savevm` / `loadvm` 对应 QEMU 的同名命令。格式：

```
"FRBOXSNP" + 4 字节长度 + JSON 元数据 + 各块原始字节
```

## 14. 已知缺口

不是"再跑跑就好"的清单，是**当前能力的边界**：

1. ~~**没有调度器，任务上下文是硬造的。**~~ **V10 已推翻**：内核一直在固件里，
   之前进不去只是因为 `andccr`/`orccr` 改 S 位时不换 `r15`。修掉之后固件自己的 REALOS
   原生跑起来（43,428 步到派发点 `0x0FE4E6`），**V11 更进一步：任务真的换起来了**
   （100 万步 6 次切换）。现在的边界不是「有没有调度器」，而是：
   **13 个任务里只有 3 个上场**，其余 10 个的上下文要靠 `sta_tsk` 去建，
   而触发 `sta_tsk` 的硬件事件（按键 / 拨盘 / 存储卡 / 时钟）一个都没有。
   旧现象里「任务 1 在 `0x080504` 的 `ret` 上掉出界、RP 弹出 0」那段仍然成立，
   但那是 `boot_task`（手工跳）这条老路的记录，不是原生路径。
2. **自旋消除器有误伤可能。** 判据是「0x100 窗口内 3,000 步没离开」，一个真的长延时循环
   也会被当成忙等而放行一个不相关的位。所以它默认关着，只在明确知道前面有硬件等待时开。
3. **三处外设窗口语义未解**：`0x50000000` / `0x68000000` / `0x4000D000`，都有上万次
   访问记录，但不知道是哪个控制器。直接页 `0x524` 是第三个卡点等的那个，也不知名。
4. **854 个未定义编码**归属未定：可能是 FR80/FR81 专有指令（已知 `srch0/srch1/srchc`
   三条就是 binutils 表里没有、靠 NikonEmulator 标注补的）。
5. **没有 gdbstub**。想看汇编级单步只能靠 monitor 或 `-d in_asm`。
6. **B 段没有帧缓冲，也没有字库**。就算把中断链路全接通，也不会"出画面" —— 真正的
   显示对象由外部芯片处理，固件只发事件标志。

## V12：把「任务在等什么」变成可读、可推

V11 能换任务了，但 13 个任务只上场 3 个，其余 10 个卡在「缺硬件事件」上。V12 把这件事拆成三步。

### 1. 读对 TCB

```
TCB（0x2C 字节）
  +0x00 等待对象控制块（不等待时是就绪队列节点）
  +0x08 状态字：低字节 0 = 运行/就绪，4 = 等待，0x10 = 休眠/退出
                 高位 0x00100000 = 等标志，0x00010000 = 等消息
  +0x14 waiptn（等标志时的位模式）
  +0x18 保存的 SP  ← **任务的现场在这里，不在任务表里**
```

`realos.states()` / `blockers()` / `flags()` 把这几个字段摊平成表；monitor 的 `tasks` 直接打印
「在等 flag3 的 0x2000，现 0x0，1 个在等」。两个坑写在 KNOWN_ISSUES 45/46。

### 2. 被动流水（不改变执行）

`fr_emu` 加了 `int_hook`（看一眼就放行），`frbox/flow.py` 用它记 calls / switches / waits / sets。
自检里有一条断言守着「挂了流水之后步数与 PC 完全不变」。

### 3. 用固件自己的内核注入事件

```python
from frbox import realos
realos.set_flag(m, 3, 0x2000)   # = kernel_call(m, -48, r4=3, r5=0x2000)
realos.wake_task(m, 5)          # = kernel_call(m, -39, r4=5)
```

实现是让 CPU 执行一次 `eit(0x40)`：参数进 R4–R7/R12（**32 位补码**），走固件自己的陷阱入口
`0xFE3C0` → 分发表 `0xFE3B8` → 真实现，`reti` 回标记地址 `0x81338` 算返回，然后恢复寄存器。
实测 `set_flg` 139 步、`err=0`。

⚠️ 这是「注入外部事件」，不是「硬件真的产生了事件」。19 次注入之后（`probe/exp_native_drive.py`）：
曾有现场的任务 0/1/4/5/7/9/10，真跑过 1/4/9/10，停机时 4/5 等消息、9 等 flag10、10 在跑。

## V13：补上「完成位 + 中断」，让固件自己往前走

V12 以为任务 4/5 卡在消息上，V13 发现任务 5 只是 `slp_tsk` 休眠；真正缺的是
**中断和状态位必须一起到**（回调 `0x0A687A` 会先 `btstl #8,@0x80`）。

- `frbox/dev_evt.py`：`CompletionEvent`，`period=N` 周期触发 / `period=0` 按启动位触发；
  状态位默认 `0x80/bit3`，向量 `0x23`，可配。默认关闭，`--events` / `enable_events()` 才挂。
- `realos.wait_kind()` / `in_flag_queue()`：等待原因位表
  （`0x00100000` 标志 / `0x00400000` 消息 / `0x00010000` 休眠），等待对象靠扫 flag 队列反查。
- monitor：`tasks` 会写「休眠（等 wup_tsk）」「等消息」；新增 `events [PERIOD]`。

实测（100 万步、不注入）：36 次服务调用，任务 1 推完三个等待点后停在 `flag9/0x400`；
固件自己 `sta_tsk(9)` 与 `sta_tsk(4)`，任务 4 跑完 `ext_tsk` 退出。
事件周期 1,024–16,384 结论一致。

## V14：不是等一个位，是在等一张事件位图

V13 只补了「一个状态位 + 一个中断」，能推任务 5，推不动任务 1/9。V14 把五个回调槽逐个
反汇编（跟寄存器抽位判定）之后看到：它们判的不是各自外设的寄存器，而是同一个 RAM 字
`0x00041A56` —— 一张固件自己维护的事件位图。固件里本来就有转发样本（`0x0AD662`：
`0x90` 的 bit8 → 位图 bit8），我们缺的是中间这一步。

| 槽 | 向量 | 回调 | 判定 |
|---|---|---|---|
| `0x3F028` | 0x13 | `0x0ACBDA` | 位图 bit4 |
| `0x3F040` | 0x19 | `0x0ACAFE` | 位图 bit8 |
| `0x3F048` | 0x1B | `0x088A96` | 直接页 `0x60` 的 bit8/bit1/bit2 |
| `0x3F074` | 0x23 | `0x0A6938` | 无（直接叫醒） |
| `0x3F078` | 0x24 | `0x0AD28E` | 位图 bit9 |

- `frbox/dev_bits.py`：`BitEvent(mask, vecs, period, addr=0x41A56)`，周期把位置 1 再挂一串中断。
  `Machine.enable_bits()` / `--bits MASK[:VECS[:PERIOD]]` / monitor `bits`。默认关闭。
- monitor 新增 `fast [N]`：不吃自旋保护直接跑 N 步（`cont` 会在自旋处停下，喂事件时不好用）。
- `--version` 改成跟 `frbox.__version__` 走（之前硬编码在 cli 里）。

判据：**位图 bit4 与 bit8 必须同时置**，vec 0x19 的回调才走到 `ref_tsk`（`0x0ACB16`）→
`sta_tsk(8)`（`0x0ACB2C`）；单喂任一位都无效（100 万步 × 13 种组合，`results/frbox/evt-matrix.txt`）。
位图全置时任务 8 改走入口 `0x0ACC16` —— 位图还编码「哪一类事件」。

任务 8 起来后卡在直接页 `0x90` 的轮询环 `0x0AD64E`；逐位实测**只有 `0x90.bit1` 能放行**
（反汇编写的是 `btstl #2`，立即数与位号不是一一对应），放行后走到 `0x0ACE86` 转 sleep。

另一个结论：flag 的位模式只有内核 `0x0FED42` / `0x0FEDD6` 两个写入点（`sys_set_flg` /
`sys_clr_flg` 内部），应用层没有直接改内存的路径。所以「静态扫不到 `set_flg(9, 0x400)`」
是有效否定 —— 任务 1 等的 `flag9/0x400` 在软件流程里永远不会被置，只能来自外部。

## V15：一把尺子，和一次自我更正

### 1. 位操作立即数是掩码（V14 的未解之谜结案）

`BANDL / BORL / BEORL / BTSTL #u4, @Ri` 操作的是 **`@Ri` 指向的那一个字节**，
`u4` 是**低半字节掩码**，`...H` 是**高半字节掩码**（真掩码 = u4 << 4）：
`btstl #2` = 掩码 0x02 = bit1；`btsth #4` = 0x40 = bit6；`btsth #8` = 0x80 = bit7。
CPU 侧一直是对的（`mask = g("u4")`），错的是读反汇编的方式。新增 `frbox/bits.py`
（`mask() / bits() / describe()`）统一这层翻译。

### 2. 更正 V14 的两条结论

- **「位图 bit4+bit8 必须同时置」不成立。** 不碰位图、只打 vec 0x13 与 0x19，
  固件自己就 `sta_tsk(8)`；16 位逐位单喂，每一位都行。V14 的基线只打了 0x23，
  两个回调没跑，于是把「回调跑了」误判成「位图位对了」。
  位图真正的作用是**选路**：bit14 → `sta_tsk(8)` 改从 `0x0ACC16` 发出；bit15 → 服务 32→69。
- **`0x0ACB2C` / `0x0ACC16` 是 `sta_tsk` 的调用点，不是任务入口。**
  `Flow.calls` 的 `c[1]` 是 `int #0x40` 的指令地址。任务 8 的真入口是 **`0x0ACC32`**。

### 3. 覆盖率

`frbox/cover.py`：每条指令 `buf[(pc - rom_base) >> 1] = 1`，A 段 262,145 槽 ≈ 1.8 MB。
`--cov` / monitor `cov [MINLEN]` / `Coverage.holes() / diff()`。
`machine.reset()` 重绑缓冲区，换 CPU 不丢。

四场景 30 万步：A 1,443 地址 / B(+0x23) 6,119 / C(+vec13,19) 2,764 / D(+bits) 2,764。
⚠️ 事件越多 ≠ 覆盖越广：B 只有一路 0x23 反而最多，因为任务 9 走的是「一路往下」的初始化路径。

### 4. 任务 4 是被任务 8 的忙等饿死的

`readyq` 显示 `0x45984 = 0x10800000`（优先级 8、3），槽 3 `head=任务8 / tail=任务4`。
任务 8 当队头且卡在 `0x0AD652` 死等 `0x90`（纯忙等不让出），同优先级轮转到不了任务 4。
放行 `0x90.bit1` → 任务 8 sleep(`0x0ACE86`) → 任务 4 被派发、跑完 `ext_tsk` 退出，
执行地址 2,764 → 6,382，服务 32 → 40。

⚠️ 口径：状态字 ready 只说明「在队列里」，不说明「被派发过」。

### 5. 新增命令

- `--cov`（CLI）、`cov [MINLEN]`、`readyq`（monitor）：
  `cov` 报「执行了多少地址 + 最长的未执行区间」，`readyq` 倒就绪位图与 13 个优先级槽
- `probe/`：`exp_bitmask.py`、`exp_bit_matrix.py`、`exp_coverage.py`、
  `exp_ready_queue.py`、`exp_task4_unblock.py`

## V16：那 7 个不开机启动的任务，是被谁按住的

V15 留下的话是「7 个任务入口从没执行过，谁 `sta_tsk` 它们没定位」。V16 不去追那条路径，
改成先问一个更基本的问题：**任务本身（代码、栈、TCB）是好的吗？**

### 1. 任务表有位「复位就激活」

任务表 `0x0FE010` 起每 `0x1C` 一条、共 13 条，`+0x0C` 是状态字，最高位
`0x80000000` = **复位时就激活**。真实固件里只有任务 1 / 5 / 0 是 1。
把它置 1 再复位，REALOS 初始化就会自己把任务建起来 —— 不用知道是谁叫的它。

⚠️ 任务表在 ROM 区：`bus.wr(0xFE038, 4, 0x80000000)` 读回来还是 0，只能改 `bus.rom`；
`m.load()` 会重装 ROM 冲掉改动，`m.reset()` 不会。顺序必须是 load → 改 → reset。

**单任务对照：7 个全部跑过**（判据 = 覆盖率里入口地址被执行，不是状态字）：

    2  → 跑过，卡 flag10/0x8000      3  → 跑过 → ext_tsk（4 次服务）
    6  → 跑过 → ext_tsk（1 次服务）  7  → 跑过，卡 flag6/0x200
    10 → 跑过（就绪）                11 → 跑过，卡 flag5/0x1
    12 → 跑过，卡 flag10/0x1000

### 2. 全开 ≠ 全跑

三场景各 20 万步（`results/frbox/all13.txt`）：

| 场景 | 执行地址 | 服务 | 入口被执行过的任务 |
|---|---|---|---|
| A 原始 | 6,382 | 40 | 5/12 |
| B 全开（7 个激活位全置 1） | 10,685 | 157 | 9/12（7、10、12 没轮到） |
| C 全开 + 逐任务解锁 | 24,170 | 342 | **11/12** |

任务 11 优先级 1，一起跑起来之后低优先级的 7/10/12 拿不到 CPU。
任务 12 单开能跑，所以这是抢占不是缺陷 —— 与 V15「任务 4 被任务 8 忙等饿死」同类。

### 3. `unlock.trace`：一站一站往下推

每轮：跑 `batch` 步 → 读该任务状态 → 等 flag 就用 `realos.set_flag()` 置位。
判据「有进展」= PC / 服务数 / 覆盖地址任一变化；三者都不动判死；
同一 `(flag, pat)` 第 3 次出现也停（有人在清位，继续置只会绕圈）。

任务 1 的完整轨迹 **14 站**，第 5 站就是 V13 起一直没解的 `flag9/0x400`，
之后又走 9 站才自己 `ext_tsk` 退出 —— 它是中途一站，不是终点。
任务 11 是 7 站：`flag1/0x8000` → `flag5` 的 0x1 / 0x800 / 0x200 / 0x100 / 0x2000 → 退出。

### 4. flag 是握手闸门，不是事件通知

任务 2、9 会绕回同一等待点。`Flow.sets()` 显示**清位的是等待方自己**：

    任务 2  clr flag8  0xFFFFDFFF   ← 清掉自己要等的 0x2000
    任务 9  clr flag10 0xFFFF0330

`clr_flg(flgid, clrptn)` = `flag &= clrptn`，所以这些 flag 是任务之间的**握手闸门**：
等待方自己清、对端来置。

→ V14「静态扫不到 `set_flg(9,0x400)` 是有效否定」仍成立，但它只说明**固件代码里没人置**，
不说明**永远没人置**。置它的人在另一条任务里，而那条任务当时没被调度。

- CLI `--boot TASKS`；monitor `boot` / `unlock TASK [ROUNDS]`

## V17：第二条同步通道打通了，然后一格新代码都没多

V16 收尾时任务 5 在 A / B / C 三个场景里都停在 `rcv_msg`（PC `0x000A6326`，状态字
`0x00400004`）。flag 那套注入推不动它 —— 消息和事件标志是两种原语。V17 把这条路走通了，
代价是得到一个明确的否定结论。

### 1. 它不是死锁，是没人再发

运行流水的三行就能说清：

    步 43622   0x000A6324  rcv_msg  r4=0x000466E4  r5=1  tcb=0x45AAC（任务 5）
    步 44433   0x00008179C  snd_msg  r4=1          r5=0x000417DC  tcb=0x459FC（任务 1）
    步 51963   0x000A6324  rcv_msg  r4=0x000466E4  r5=1  tcb=0x45AAC（任务 5）

先等、后收、再等。任务 5 是**常驻消息循环**，只是第二条消息永远不来。

### 2. A 段是单信箱架构

线性扫 ROM 找 `int #0x40`（1,008 处，R12 常量可定 1,003 处），再回溯 `ldi r12,#imm`：

| 服务 | 处数 | 备注 |
|---|---|---|
| `set_flg` -48 | 213 | |
| `wai_flg` -46 | 206 | |
| `clr_flg` -47 | 161 | |
| `sta_tsk` -23 | 108 | V11 数过 |
| **`snd_msg` -63** | **15** | **R4 全是 1** |
| **`rcv_msg` -61** | **1** | **`0x000A6324`** |

id 1 ↔ 控制块 `0x000466E4`（任务 5 的 R4 给的是地址，发送侧给的是编号，同一个对象）。

### 3. 投递要借固件自己的内核

`realos.kernel_call(m, -63, r4=1, r5=msg)` —— 让 CPU 执行一次 `eit(0x40)`，
走 `0xFE3C0` 陷阱入口 → 分发表 → 真实现。挂链、唤醒全是固件代码干的，
返回 `err=0 / 219 步`。**不伪造队列指针、不挂半主机**。

### 4. 任务 5 是「消息→标志」的转发器

投一条消息，服务流水多出 11 次调用（全在 TCB `0x45AAC`）：

    wai_flg(flag2,0x4000) → clr_flg(flag2,~0x4000) → can_wup → slp_tsk
    → wup_tsk → can_wup → slp_tsk(任务11) → wup_tsk
    → set_flg(flag2,0x4000) → set_flg(flag3,0x2000) → rcv_msg（回到原地）

首尾是同一处 `rcv_msg`，中间没有 `ext_tsk`、没有跳走 —— 常驻循环。

### 5. 消息不是数据，是「回调注册」〔V18 已更正，见下段〕

发送侧（`0x00081760`）是一条固定流水线：`clr_flg(3,0xFFFFDFFF)` → 填 `+0x08/+0x0A/+0x0C/+0x0E`
四个半字 → `snd_msg(1, 0x000417DC)`。实测抓到的那条：

    +0x08 = 0x8000   +0x0A = 0x0000   +0x0C = 0x00C0   +0x0E = 0x2000
    +0x10 = 0x0008225E   ← 落在 A 段代码区的指针

任务 5 收到后把整条抄到固定缓冲 `0x0003FE48`（反汇编里 `r8 = 0x3FE48`），**包括那个代码指针**，
然后才去 `wai_flg` / `set_flg`。所以消息是「把 0x0008225E 挂到某个事件上」的登记单。

### 6. 主实验：服务在涨，覆盖不动

| 场景 | 步数 | 投递 | 执行地址 | 服务 | 跑过任务 |
|---|---|---|---|---|---|
| A 基线 | 243,428 | 0 | 6,382 | 40 | 5/12 |
| B 投 1 条 | 283,647 | 1 | 6,382 | 51 | 5/12 |
| C 投 8 条 | 565,180 | 8 | 6,382 | 128 | 5/12 |
| D C 后空转 20 万步 | 765,180 | 8 | 6,382 | 128 | 5/12 |
| E 全开 dormant + 投 8 条 | 565,848 | 8 | 10,685 | 222 | 9/12 |
| P 复现 V16-C | 619,408 | 0 | 24,170 | 342 | 11/12 |
| Q P + 投 11 条 | 662,576 | 11 | **24,170** | **471** | 11/12 |
| R Q + 二次扫描 | 750,864 | 12 | **24,170** | 498 | 11/12 |

每投一条 **+11 次服务**，执行地址 **+0**。E 的 10,685 也不是投递带来的（V16 的 B 场景就是 10,685）。

原因：这条路基线头 5 万步里已经走完了（步 44433 那条消息是任务 1 自己发的），后面每一条都在重放。

内容矩阵（首字当命令码，12 个值 + 固定首字改第二字，共 15 例）否证了「消息首字是命令码」：
15 例数字**完全一致**（6,419 / +37 / 服务 88 / 落脚 PC 全是 `0x0A6326`），新增调用点 0 个。

⚠️ 这里的 +37 与上表的 +0 不矛盾，差别在**投的是什么**：矩阵投的是「除首字外全 0」的消息，
固件样本（`+0x08=0x8000`、`+0x10` 带代码指针）基线里早走过。全 0 消息让任务 5 走了
另一条登记分支，只在第一次投递时出现（6 次投递仍 +37，不是 6×37）。
**换「别的内容」能多走 37 个地址，但换 12 种内容走的是同 37 个。**

## V18：登记是活的，派发是死的

V17 留下两个问号：回调指针 `0x0008225E` 谁调用、任务 5 被叫醒后为什么卡在闸门上。
V18 把前者查到了底。

### 0. 先更正 V17 的一处读法

V17 §5 说「消息 `+0x10` 是代码指针，任务 5 整条抄到 `0x3FE48`，所以消息 = 回调注册单」。
挂访存监视重跑，两件事都不对：

- 回调段 `0x8225E–0x8229C` 共 32 个地址，基线里**命中 0 个**；
- 任务 5 只把 `+0x08` 起**四个半字**写到 `0x3FE50/52/54/56`，落地缓冲 `+0x10` 实测 **0**；
- `0x417DC +0x10` 那个 `0x0008225E`，其实是**全局回调槽 `0x417EC`** —— 发送侧构造区，不是交给信箱的载荷；
- `0x0008225E` 在全段 `ldi` 立即数里**只出现 1 次**（`0x8145E`），装进 r6 送给登记函数 `0x81744`。

→ **「投递消息」和「登记回调」是并列两件事**，不是载荷关系。
「消息首字不是命令码」这个否定结论仍成立（15 例矩阵），但机制描述按上面收敛。

### 1. 两套对称单槽

| | 槽 0 | 槽 1 |
|---|---|---|
| 代码指针槽 | `0x417EC` | `0x417F4` |
| 倒计时槽 | `0x417F0` | `0x417F8` |
| 挂起标志 | `0x3F404`（bit1） | `0x3F40D`（bit2） |
| 派发器 | `0x8223A` | `0x822CE` |
| 唯一引用点 | `0x80606` | `0x808A4` |
| 基线登记值 | `0x8225E` / 计数 `0x0C` | `0x822F2` / 计数 `0x08` |

派发器本体很短：

    0x00082252  ld   r0, @(0x417EC)    ; 从全局单槽取代码指针
    0x00082258  call r0                ; 「谁调用回调」的答案

`0x8223A` 自己只有一处引用 `0x80606`，在启动代码区那张「事件位 → 处理函数」分派表里
（`btstl` 逐位测，bit2 对应它），整段被 `0x805E4 bne +0x50` 挡着 —— 只在「没事可干」时才跑。

### 2. ⭐决定性事实：主循环从没执行过

基线 24 万步跑完：

    槽0 = 0x0008225E  计数 0x000C  标志[0x3F404] = 0x02 *挂起*
    槽1 = 0x000822F2  计数 0x0008  标志[0x3F40D] = 0x04
    主循环 0x80588 覆盖 False；派发器 0x8223A / 0x822CE 覆盖 False

`0x80588` 静上也**没有任何调用者**：相对 `call` 0 个、`jmp` 0 个、`ldi` 0 个、
4 字节常量 0 处、A 段向量表里也没有。
→ ⚠️ 只能报「当前模型里没人调」，**不能**报「固件设计有缺陷」——真机可能由未建模的时钟/中断拉起它。

### 3. ⭐倒计时门控

前 11 圈每圈 10 步、只把计数从 `0x0C` 减到 1、覆盖 +0；第 12 圈归零才真 `call`：

    tick 11  槽0 0x8225E → 0x82278   632 步  +133   ← 真执行
    tick  8  槽1 0x822F2 → 0x00000000 165 步  +42    ← 一次性，跑完注销

## V18：登记是活的，派发是死的

V17 留下两个问号：回调指针 `0x0008225E` 谁调用、任务 5 被叫醒后为什么卡在闸门上。
V18 把前者查到了底。

### 0. 先更正 V17 的一处读法

V17 §5 说「消息 `+0x10` 是代码指针，任务 5 整条抄到 `0x3FE48`，所以消息 = 回调注册单」。
挂访存监视重跑，两件事都不对：

- 回调段 `0x8225E–0x8229C` 共 32 个地址，基线里**命中 0 个**；
- 任务 5 只把 `+0x08` 起**四个半字**写到 `0x3FE50/52/54/56`，落地缓冲 `+0x10` 实测 **0**；
- `0x417DC +0x10` 那个 `0x0008225E`，其实是**全局回调槽 `0x417EC`** —— 发送侧构造区，不是交给信箱的载荷；
- `0x0008225E` 在全段 `ldi` 立即数里**只出现 1 次**（`0x8145E`），装进 r6 送给登记函数 `0x81744`。

→ **「投递消息」和「登记回调」是并列两件事**，不是载荷关系。
「消息首字不是命令码」这个否定结论仍成立（15 例矩阵），但机制描述按上面收敛。

### 1. 两套对称单槽

| | 槽 0 | 槽 1 |
|---|---|---|
| 代码指针槽 | `0x417EC` | `0x417F4` |
| 倒计时槽 | `0x417F0` | `0x417F8` |
| 挂起标志 | `0x3F404`（bit1） | `0x3F40D`（bit2） |
| 派发器 | `0x8223A` | `0x822CE` |
| 唯一引用点 | `0x80606` | `0x808A4` |
| 基线登记值 | `0x8225E` / 计数 `0x0C` | `0x822F2` / 计数 `0x08` |

派发器本体很短：

    0x00082252  ld   r0, @(0x417EC)    ; 从全局单槽取代码指针
    0x00082258  call r0                ; 「谁调用回调」的答案

`0x8223A` 自己只有一处引用 `0x80606`，在启动代码区那张「事件位 → 处理函数」分派表里
（`btstl` 逐位测，bit2 对应它），整段被 `0x805E4 bne +0x50` 挡着 —— 只在「没事可干」时才跑。

### 2. ⭐决定性事实：主循环从没执行过

基线 24 万步跑完：

    槽1 = 0x000822F2  计数 0x0008  标志[0x3F40D] = 0x04

### 3. ⭐倒计时门控

## V19：那条没人拉的中断线

V18 结尾留了一个 OPEN：「真机上谁拉起 0x80588 这个主循环」。V19 的答案是：
**没人 call 它，它是被中断打进来的** —— 它就是 INT 0x2B 的处理函数。

### 1. 接线在向量表里

| 项 | 值 |
|---|---|
| TBR | `0x000FFC00`（= A 段 ROM 文件偏移 `0x7FC00`；按**地址**查，不是按偏移） |
| 索引 | `0xD4` → INT `n = 255-0xD4 = 0x2B` |
| 表项 | `0xFFF50: 00080588` |
| ICR | `0x45B`（= `0x440 + (0x2B-0x10)`）= `0x1A`，固件自己配的级别 |
| 本体 | `0x80588`–`0x80968`（994 B / 378 条指令）：`stm0 #0xFF` / `stm1 #0xFC` 开场，`reti` 收尾 |
| 邻居 | 另有 38 个向量落在 `0x809BE`–`0x8129C` 的 ISR stub 区 |

⚠️「静态上找不到调用者」这个观测成立，但它不是「没接线」的证据：中断处理函数不需要 `call`。

### 2. 结构：14 字节待办标志 + 61 个位开关

`0x80588` 是纯位分派器：逐位测 `0x3F402`–`0x3F40F`，命中就
`ldi:20 r12,#处理函数; call @r12`。

| | 条数 | 说明 |
|---|---|---|
| 主路径 `0x80588`–`0x8095C` | 54 | 覆盖 `0x3F402`、`0x3F404`–`0x3F40F` |
| 尾声子程序 `0x8096A`–`0x809BA` | 7 | 专管 `0x3F403` 的 bit0–bit6（`0x8095C` 的 `call` 进来，`ret:d` 出去） |
| 合计 | **61** | 指向 **57** 个不同处理函数，14 个标志字节全部用上 |

- 槽 0 派发器：`0x3F404` bit1 → `0x8223A`（测 `0x80602`、装 `0x80606`、调 `0x8060A`）
- 槽 1 派发器：`0x3F40D` bit2 → `0x822CE`（测 `0x808A0`、装 `0x808A4`、调 `0x808A8`）
- 有 5 个位指向 `0x8095C`：那不是处理函数，是**尾声起点**，等价于「有事但不用处理」

⚠️ 掩码口径（V15 铁律）：`btstl #u4` 的立即数**是掩码**（`#2` 测 bit1、`#8` 测 bit3），
`btsth #u4` 是 `u4 << 4`（`#4` 测 bit6）。按位号读会整体错位。

### 3. 接上之后：回调链自己走

`Machine.enable_isr2b()` → `frbox.isr2b.Irq2B`，请求一次就进 `0x80588`，
300 步跑完、干净 `reti`，**+299** 个执行地址。连请求下去：

| 第几次中断 | 这一趟步数 | 新覆盖 | 槽 0 |
|---|---|---|---|
| 1 | 300 | +299 | `0x8225E` / 计数 12（这一趟还没走到 `0x80602` 那格） |
| 2 | 601 | +543 | 计数 11（第一次轮到派发器） |
| 24 | 1196 | +133 | → **`0x82278`** / 计数 10 |
| 44 | 678 | +13 | → **`0x82298`** / 计数 8 |
| 60 | 711 | +36 | → **`0x822B6`** / 计数 30 |
| 120 | — | — | 计数 0、`0x3F404` 清 0，链注销 |

节拍是「每两次中断减一格」：派发器在 `0x8224C` 把 bit1 `bandl` 清掉，
`0x81A1E` 再 `borl` 置回，而置回本身也受别的位门控。

| 同口径对照 | 真执行回调 | 新覆盖 |
|---|---|---|
| V18 手动 `cb.tick()` | 5 次（12/22/30/60/61 圈） | +624 |
| V19 中断 240 次 | 3 次换站 + 1 次注销 | **+2053** |

### 4. 全开 dormant 任务 + 中断

服务调用 57 → **301**（+244）；任务 4/8/9 变 `ready`，任务 6 由 `sta_tsk(6,1)` 起来；
任务 7/10/12 仍 `dormant`。V15 那条「任务 4 被任务 8 忙等饿死」在这个节拍下不再成立 ——
只能说明就绪队列的构成变了，不能反推真机调度顺序。

### 5. 新的一道墙

不替外设答话时，第 9 次中断一去不回。卡点在函数 `0x9C94A`–`0x9C9CE`（ISR 的 `0x80782` 调它）：

```
0x9C974  9020      borl  r0,#2        ; 置 0x174 的 bit1（请求）
0x9C976  9B000174  ldi:20 r0,#0x174
0x9C97A  8940      btsth @r0,#4       ; 等 bit6（应答）
0x9C97C  E2FC      beq   -4
```

`answer=True` 在 `0x9C97A` 往 `0x174` 写 `0x40`，是**替外设答话**，必须在报告里注明。

### 6. 新增

- `frbox/isr2b.py`：`vectors()` / `table()` / `Irq2B`（`raise_once/burst/state/info`）
- `Machine.enable_isr2b()` / `self.isr2b`；CLI `--irq2b N` / `--no-answer`；monitor `irq2b [N|off N]`
- 探针 `exp_isr2b.py`（A–H 八段）；results `isr2b.txt`
- 自检 **475/475** + 63/63；版本 **0.19.0**

### 7. 边界与口径

可报：向量项、ICR、本体边界、61 个开关、接上后链自己走完四站、全开任务时服务 57→301。
不可报：真机上这条线多久来一次（固件里没有节拍器模型）、`0x174` 握手背后的器件、
以及**永远不能把注入说成「相机跑起来了」**。

⚠️ 数字口径：V19 预热 **12×5000 步、不注入 vec 0x13/0x19**，基线覆盖 1,443；

## V20：那道墙是假的

V19 结尾留了一道「新墙」：不替外设答话，第 9 次中断死等 `0x174` 的 bit6。
V20 查下去发现墙不存在 —— `0x174` 一直有模型，问题出在探针自己没走设备时基。

### 1. 归属

| | |
|---|---|
| 表项 | `dev_xfer.D300_A_TABLE` 里 `0x174: (0x02, 0x40)`（启动位 bit1 / 完成位 bit6） |
| 挂载 | `Machine.boot_realos()` 头两行就是 `enable_xfer()` + `enable_dispatch()` |
| 运行期 | `dp.owner(0x174)` = `XferHandshake`，且在 `m.devices` 里 |
| 同表其它项 | `0x0AF:(0x02,0x80)`、`0x524:(0x02,0x40)`、`0x534:(0x02,0x40)` |

⚠️「静态找不到 `call`」和「缺器件」是两件事。V19 在后者上滑了一步。

### 2. 分水岭：`cpu.step()` vs `m.step()`

`Machine.step()` 每 `cycles_per_tick`（256）步分发一次 `d.tick()`，`cpu.step()` 不会。
`XferHandshake.tick()` 就是靠这一分发把完成位置起来的（`delay=64`，一次 tick 就够）。

| 口径 | 第 9 次中断 | `0x9C97A` 上自旋 | 终点 PC | `[0x174]` |
|---|---|---|---|---|
| `cpu.step()` | 两万步超时 | 6,519 次 | `0x9C97A` | `0x02` |
| `m.step(1)` | 605 步，正常 `reti` | 14 次 | `0xFE510` | `0x00` |

访存监视看得很清楚：`0x9C97A` 一共读 14 次，前 13 次返回 `0x02`，第 14 次返回 `0x42`
（`0x02 | 0x40`）—— **没有一行代码写过 `0x40`**。

### 3. 改成默认走设备时基

- `raise_once` / `burst` 加 `run_tick=True`（默认），内部用 `Machine.step(1)`
- `answer` 默认改 `False`：靠模型答话，不硬写
- CLI：`--no-answer` 退役（`argparse.SUPPRESS`），新增 `--answer` 作对照
- monitor：`irq2b off N` → `irq2b answer N`
- `run_tick=False` 可稳定复现 V19 的自旋，自检里有这条反向断言

| 口径 | 请求 | 硬写 | 覆盖 | 结果 |
|---|---|---|---|---|
| V19（`answer=True`） | 240 | 15 次 | +2053 | 全部 `reti` |
| V20（设备模型） | 240 | **0 次** | +2053 | 全部 `reti` |

覆盖一样，因为固件拿到 bit6 之后的走法一样；区别只在「谁给的位」。

### 4. 顺带摸清的两组结果寄存器

`0x8A500` 附近是一个按通道号选寄存器的大 switch，静态解出两组：

| 组 | 结果寄存器 | 位宽 | 个数 | 配套握手 |
|---|---|---|---|---|
| 10 位组 | `0x178` `0x17A` … `0x18E`（步长 0x2） | `& 0x3FF` | 12 | `0x174` |
| 12 位组 | `0x528` `0x52A` `0x52C` `0x52E` `0x538` `0x53A` `0x53C` `0x53E` | `& 0xFFF` | 8 | `0x524` / `0x534` |

12 位组在 `0x52E` 之后跳到 `0x538`，中间 `0x530`–`0x536` 不在表里。

240 次中断的访存统计：`0x174` 读 616 / 写 60，`0x176` 与 `0x177` 各写 15，
`0x186` 读 15，其余 11 路 0 次。也就是**只走 15 趟、只取第 8 路**。

给 12 路灌全 0 / 0x200 / 0x3FF / 渐变，覆盖全是 **+2053** —— 这些值只被搬运，不参与分支。
与 V15「事件越多 ≠ 覆盖越广」同理：**换输入 ≠ 换路径**。

### 5. 新增

- `isr2b.py`：`run_tick` 参数、`answer` 默认翻转、头部 §5 重写
- 探针 `exp_tick.py`（A–H 八段）；results `tick.txt`；报告 `docs/reports/32`
- 自检 **484/484** + 63/63；版本 **0.20.0**
- `reports/31` 第 6 节加更正框；`KNOWN_ISSUES` #86 改 `[FIXED → V20]`、补 #87/#88

### 6. 边界与口径

可报：`0x174` 归 `XferHandshake`、`boot_realos()` 无条件 `enable_xfer()`、
V19 的卡死是时基 bug、240 次不硬写也能过、两组通道的地址与位宽。
不可报：它就是 A/D 转换器（软件签名像，器件身份未证）、各通道接什么物理量、
真机上这条中断多久来一次、转换耗时多少（`delay=64` 是近似值）。

⚠️ 口径：V20 沿用 V19 预热（12×5000 步、不注入 vec 0x13/0x19，基线 1,443）；
V18 是 40×5000 + 喂事件（基线 6,382）。**两套数字不能相减。**

## V21：自动节拍 —— 给 INT 0x2B 配周期时钟

V19/V20 的中断都是手动拉线（`--irq2b N` 一次一次请求，每次跑到 reti，
中断被串行化）。V21 挂一个**周期时钟**（`frbox/dev_irq2b.py`）到设备时基上：
每 `period` 个 CPU 周期 raise 一次 vec 0x2B，`fast N` / `c` 里中断自己来 ——
包括在任务代码里、内核里被拉起来。

### 1. 设备与四口径

`Irq2BClock` 关键设计是**合并**：CPU 的受理规则是 `lvl < ILM`，被挡住的
请求留在 `cpu.irq_pending` 里重试；时钟挂请求前先看这条向量是否已有待决，
有就跳过（计进 `coalesced`），等价于「电平触发的线已经拉高」—— 不然
风暴档会把队列灌满，ILM 一放开就洪水连发。

另一个门是 **ICR 未配置就不拉**（计进 `skipped`）：ICR 的 level 还是 0 时
`raise_irq` 会强制 0x1F，而 `0x1F < ILM(0x1F)` 永不成立 —— 请求会永久
卡在待决队列把后面的到点全合并掉（boot 前挂钟实测：修复前 fired 1 /
coalesced 139 / accepted 0）。修复后 skipped=2、accepted=99、终态覆盖
与挂钟在后一致。

计数四口径（全文通用）：`fired`（挂到 ICU）/ `coalesced`（合并掉）/
`skipped`（ICR 未配置跳过）/ `accepted`（真受理进 ISR，`cpu.irq_log` 里
vec=0x2B 的条数）。自洽式：`fired − 待决 = accepted`。

### 2. 频率不是中性参数（固定 10 万步，基线 1,443）

| period | accepted | coalesced | 覆盖+ | 服务+ | 任务6 |
|---|---|---|---|---|---|
| 256 | 196 | 193 | 2053 | 3 | ready |
| 512 | 191 | 3 | 2117 | 3 | ready |
| **1024** | **97** | 0 | **2418** | 10 | **flag** |
| 2048 | 48 | 0 | 1868 | 1 | dormant |
| 4096 | 24 | 0 | 1761 | 0 | dormant |

**1024 是峰值档**：中断次数只有风暴档一半，覆盖反多 365。次数拉平
（accepted 都是 97）：风暴 +1,992 vs 从容 +2,418；给风暴 3 倍步数
（597 次）也只有 +2,056。太密 → 固件拿不到中断间的执行时间；
太疏 → 10 万步内回调链推不完、任务 6 没被拉起。

### 3. 多出来的覆盖从任务 6 的入口开始

`cov.diff`：1024 档比 256 档多执行 545 个地址（15 段），第一段
`0xA6A30–0xA6A56` = **任务 6 入口**；反向只有 109。时间线上 +541
一跳全部落在第 6–7 万步（accepted 58→68）—— 回调链第三站
`sta_tsk(6)` 拉起任务 6 的那一下。

受理现场（`cpu.irq_log` 记着每次被打断的 PC）：

- 风暴档 196 次**全部**落在空闲任务 `0xFE510` 上；
- 从容档 97 次里 93 次在空闲任务、**4 次直接打断任务 6 函数体**
  （`0xA6E6C` / `0xA6E76` / `0xA6F18` / `0xA7FC4`）。

### 4. 等价性与饱和

- 手动 240 次（+2053/+3）与自动风暴 accepted=246（+2053/+3）**完全一样**：
  手动模式「每次跑到 reti」的串行化效果 = 每 tick 一次的风暴。
  两种模式下固件都没拿到中断间的执行时间，V19/V20 口径由此无缝对照。
- period=1024 跑 100 万步：accepted 976 次，覆盖 20 万步后趋平
  （终值 +2,482）—— 再往下要**新事件源**，不是更多中断。

### 5. 新增

- `dev_irq2b.py`：`Irq2BClock`（period / 合并 / ICR 门 / 四口径视图）
- `Machine.enable_auto_irq2b()`；CLI `--auto-irq2b CYCLES`；monitor `autoirq [P|off]`
- 探针 `exp_autoirq.py`（A–H 八段）；results `autoirq.txt`
- 自检 **510/510** + 63/63；版本 **0.21.0**

### 6. 边界与口径

可报：中断可挂周期时钟并合并待决；频率不是中性参数（97 次 +2,418 >
196 次 +2,053）；多出的地址从任务 6 入口开始；97 次里 4 次打断任务 6
函数体；手动模式 ≡ 风暴模式；覆盖 20 万步饱和。
不可报：真机这条中断的实际频率（period 是模型参数）；任务 6 对应什么
功能（只知道入口和它等一个 flag）；「相机跑起来了」。

⚠️ 口径与 V19/V20 同（预热 12×5000 不注入事件，基线 1,443），
`+2053` 可直接对照；fired / coalesced / skipped / accepted 不可混用。

### 复现

```bash
cd emu
python -m frbox -M d300-a --realos 1 --cov --cb --auto-irq2b 1024 \
       -monitor none -c "fast 100000; autoirq; tasks"
python probe/exp_autoirq.py > ../results/frbox/autoirq.txt
```

## V22：双线推进 —— B 段内核活了，A 段 61 位点亮

### 0. 起点

两条线各剩一个口子：B 段 d300-b 跑到 191,518 步复位链尽头后取指失败
（终点 PC `0x6800060C` 不是代码地址）；A 段 V21 周期时钟覆盖 20 万步饱和
（+2,482），要新事件源 —— 位分派器 61 个位里只走过 2 个。

### 1. B 段诊断：0x68000000 是内核对象区

反汇编 `0x407AA–0x407D8`，认出与 A 段 `0x0FE4E6` **逐字相同**的派发序列：
`r14=[0x54F10]`（下一任务 TCB）→ `[0x68000000]=r14` → `r0=[r14+0x18]`
（保存的用户栈指针）→ `mov r0,USP`（编码 `0xB330`）→ `orccr #0x20` 切用户栈
→ `r0=[USP]`（任务入口）→ 压系统栈恢复 → `reti` 进任务。

`0x68000000` 未映射 → 读回 0 → USP=0 → 从地址 0 取出垃圾 → `reti` 后
PC=0x6800060C，整条链塌。boot 期间该窗口观测写入 **3,746 次**
（`0x68000000–0x6800B984`），里面是 REALOS 的 TCB 链表（`0x6800013C` 起
步长 `0x2C`）、当前任务槽 `[0x68000000]`、当前任务的用户栈
（空闲任务栈顶 `0x68000B98`）。按 64 KB 建 `ram-kernel` 之后 boot 跑通：
**191,520 步、PC=`0x407DC`（空闲 `bra -1`）、SP=0x68000BE8、S=1，确定性。**

### 2. 第二层坑：任务栈区 0x9F800000

`sys_sta_tsk(2)` 返回 err=0「成功」，派发还是读回 0 —— B 段任务表 28 条的
栈顶全在 `0x9F8002A4–0x9F8222A4`，而 extra_ram 只有 `0x9F58xxxx` 那 1 MB。
任务的初始帧写不进去、读回来是 0。按 256 KB 建 `ram-taskstack` 后修通。

```
d300-b extra_ram（全部实测定性）：
  0x9F580000  1 MB   ram-sdram       主控数据 RAM
  0x68000000  64 KB  ram-kernel      REALOS 内核对象区（本轮）
  0x9F800000  256 KB ram-taskstack   28 条任务的用户栈区（本轮）
```

### 3. 任务 2 上 CPU

`sys_sta_tsk(2)` err=−63（帧 boot 时已被固件建好，重复启动）；boot 后不做
任何注入、单发 INT 0x3F 也能把入口 `0x1200AC` 派发上 CPU（×16 覆盖 +221）；
一次派发 **+217**，`0x1200AC` 执行过。随后卡在 `0x14E86x` 的 SDRAM 半字表
扫描循环（`ldi:32 r10,#0x9F58F348`，比对 0xFFFF/0xAA55）—— B 段新墙：
清零 RAM 里既没有 0xFFFF 也没有 0xAA55。全开 27 任务 + 8 轮派发
只有任务 2 上过场（+264），其余都在等 CPU。

⚠️ 任务表 `0x54C10` 的 +0x0C 域与内核 TCB **错位一格**（表任务 2 的域
`0x68000194`，实际跑 `0x1200AC` 的 TCB 是 `0x68000168`），对应关系未定。

### 4. B 段向量

42 条真 ISR（INT 0x10–0x3F 全有真处理函数），26 条有效果；INT 0x3F =
调度请求向量（`0x40D32` 内联派发，单发 +121）；ICR=0x1F 的 9 条全部
受理 0 次 —— 「0x1F = 本机型不用」在 B 段再次验证。串口喂字节：ISR 里
`set_flg(3,0x20)` 真的置上了 flag 3，但没有任务在等它。boot 后空转 30 万步
覆盖 +1 —— 内核只在有中断/系统调用时才动，0 才是预期。

### 5. A 段：61 位逐位点亮

顺序扫描（每位置 1 → 一次 INT 0x2B → 记增量，基线 1,443）：
**25/61 位 call 点执行**、7 位自动应答、6 位带服务调用、5 位指向尾声。
全 0xFF 一次中断只点到 10/57 个处理函数（位之间有先后依赖）。
单开最强位 ×64：`[0x3F40C]&0x20` → `0x84900` **+2,822**、
`[0x3F402]&0x40` → `0xAD3C8` +2,406、`[0x3F404]&0x02`（槽 0 派发器）+2,336。

⚠️ **位间有状态耦合**：`[0x3F40C]&0x20` 顺序扫描 +0、干净机单点 +501。
顺序扫描表只做普查；确定性数字一律干净机单点
（自检固化：基线 1,443、`[0x3F402]&0x40` +369、`[0x3F404]&0x80` +299）。
