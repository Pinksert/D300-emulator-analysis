# frbox 0.7.0 —— D300 的全系统模拟器

> 本文只讲**模拟器怎么造的**。为什么要造、造到哪一步、哪些结论已经被证伪，见
> [`02-findings.md`](02-findings.md) 和 `reports/14`–`19`。想直接跑，跳到第二节。

---

## 1. 它是什么，不是什么

**是**：一个纯 Python 3 的整机模拟器。把一个固件镜像和一份内存映射加载进去，从复位向量开始
逐条执行富士通 FR 指令，总线、外设、中断控制器、定时器、串口都是被建模的对象；带 monitor、
断点、快照、日志类别，命令行肌肉记忆对齐 QEMU。

**不是**：能让 D300 "开机出画面" 的模拟器。B 段 7 MB 固件执行到第 191,518 步、
停在 `0x000407D8` 的 `reti` 上，此后 PC 从系统栈弹出 0 —— 这不是模拟器的缺陷，是
**固件自身的启动链就到这里为止**（见第 7 节和 `KNOWN_ISSUES.md` 第 21 条）。

不依赖 QEMU，也不依赖 Java。整个东西是两个数字：

```
代码      ~3,600 行 Python（含 1,867 行取证脚本）
依赖      无（标准库）
速度      30,000–43,000 步/秒（单线程 CPython 3.13）
```

## 2. 跑起来

```bash
git clone https://github.com/Pinksert/D300-emulator-analysis
cd D300-emulator-analysis/emu

python -m frbox -M help                       # 列出机器
python -m frbox -M d300-a -c "bp 0xFE50C;c;info"   # A 段跑到启动链尽头
python -m frbox -M d300-b -c "bp 0x407D8;c;info"   # B 段同上
python frbox_selftest.py                      # 120 条断言
python fr_selftest.py                         # 54 条 CPU 断言
```

固件默认从仓库 `data/` 读（`A3000111.bin` / `B3000111.bin`）。要用别的目录：

```bash
FRBOX_FW_DIR=/path/to/D300Update python -m frbox -M d300-a
```

`data/` 里没有固件时第一条命令就会明确报 `固件不存在：<路径>`，不会静默跑 0 步。

## 4. CPU 核心

### 4.1 指令表从哪来

没有手写 800 条指令的 switch。解码表在 import 时从 binutils 的 CGEN 描述生成：

| 输入 | 用途 |
|---|---|
| `fr30.cpu` | 指令模式、操作数类型、`(dni ...)` 语义注释 |
| `fr30-opc.c` | 每个助记符的编码与宏展开 |

跑 `python fr_cover.py` 把 65,536 个 16 位字逐个喂进解码器，得到客观分数：

```
16 位编码 64,346 ／ 32 位首字 320 ／ 48 位首字 16 ／ 未定义 854
可执行编码 64,682   未实现指令 0   覆盖助记符 122 种
```

「未实现 0」是硬指标：凡解码成功就一定执行得下去，不会有 `Unimpl` 漏在运行路径上。

### 4.2 三个必须记住的语义坑

1. **目标是最后一个操作数**。`add Rj, Ri` 是 `Ri ← Ri + Rj`，反了就是全盘错。
2. **位测试立即数是掩码，不是位号**。`btstl #8` 测 bit3；`btsth #4` 测 bit6。
   而 `btsth #u4,@rN` 的立即数整体左移 4 位（半字节掩码），N 标志按**掩码结果的 bit7** 置位。
3. **延迟分支与 `call`**。带 `:d` 的分支后面那条指令一定先执行；`call` 把返回地址放进
   RP（`dr1`）而不压栈，所以模拟 `call` 的递归必须先存 RP。

### 4.3 EIT 的压栈顺序

```
进入：PS 先压系统栈，然后 PC；向量槽 = TBR + (255 - vec) * 4（倒序表）
返回：reti 从 SSP 依次弹 PC、PS
```

核对的抓手很硬：A 段 `TBR = 0x000FFC00`，槽 `TBR + 0x3FC = 0x000FFFFC` 读出
`0x000FC000`，正是复位入口 —— 如果表序反了，这个读值一定对不上。

## 5. 总线

`AddressSpace` 是三个概念的合体（对应 QEMU 的 AddressSpace + MemoryRegion）：

- **区域列表**按基址排序，二分查找；`rd/wr` 只认地址和宽度，不关心背后是什么。
- **跨区访问按字节拆**：一次 4 字节读落在两个区域交界上，会拆成两次访问分别记账。
- **未映射访问必须记账**：读返回 0、写丢弃，但地址与次数入表。`0x9F580000` 这块 1 MB
  外部 RAM 就是这么发现的 —— 固件往上写了 6,000 多次，一开始全进"未映射"。

低 4 KB（`0x0000–0x0FFF`）是 FR 的**直接寻址 I/O 区**，由一个 `DirectPage` 多路器占住，
内部再按偏移分派给具体设备。好处是"没建模的偏移"不会污染未映射统计，而是单独记一份
`unknown_reads`，能看出固件还摸过哪些寄存器（本次最热的是 `0x0DF`、`0x042/0x043`）。

## 6. 设备

原则：**有实证的才绑中断线**，推断出来的设备默认不占向量，并在 `info devices` 里标注来源。

| 设备 | 地址 | 实证程度 |
|---|---|---|
| 时钟/复位组 | 直接页 `0x480–0x48F` | ★★★ 位语义由 20 万步 watch 反推（见 6.1） |
| 串口 | 直接页 `0x60–0x67` | ★★☆ ISR `0x12FDB4` 的读写顺序反推寄存器布局 |
| 重载定时器 | 直接页 `0x10–0x17` | ★☆☆ 结构按 FR 系列通用布局摆，只作时间源 |

### 6.1 时钟寄存器组 0x482：一个"必须建模，否则永远自旋"的例子

A 段复位第二跳的初始化里，向 `0x482` 写 `0x08`（启动位），然后死等 `0x482` 的 bit7。

早期我们靠 `--latch 0x482=0x88:2` 这种"第 N 次读之后返回某值"的补丁骗过它。做完
静态扫描（59 处引用，只有 6 条 `stb` 真写）和动态 watch（200,142 步里读 66,660 次、
写 6 次，**没有一次写 bit7**）之后结论变了：

> bit7 只能来自硬件 —— 软件从不写它。

于是有了 `dev_clk.py`：写 `0x08` 武装倒计时，`tick()` 递减，到 0 时硬件把 bit7 和
`0x484` 的"切换完成"位一起置起；`0x483` 要求连续写 `0xA5`、`0x5A` 两键才解锁。
建模后不再需要 `--latch`，A 段照常跑完 43,446 步。

这一段也是项目里唯一一次**推翻自己结论**的地方：早先报告把它当成"双机握手寄存器"，
是错的（`KNOWN_ISSUES.md` 第 20 条留着这段记录）。

## 7. 机器

不是"一个 CPU + 一份固件"，是两套独立的处理器子系统：

| | `d300-a` | `d300-b` |
|---|---|---|
| 角色 | IO 协处理 | 主控 / UI |
| ROM | `0x00080000` + 524,290 B | `0x00040000` + 7,340,032 B |
| RAM | `0x00001000–0x0007FFFF` | `0x00001000–0x0003EFFF` + `0x9F580000` 1 MB |
| TBR | `0x000FFC00` | `0x000EFC00` |
| SSP | `0x0007F000` | `0x0003F000` |
| 复位入口 | `0x000FC000` | `0x00040000` |
| 实测行程 | 43,446 步 / 824 个 PC / 0 次中断 | 191,518 步 / 1,239 个 PC / 1 次中断 |
| 停在哪 | `0x000FE50C` 的 `reti` | `0x000407D8` 的 `reti` |

这些数字没有一个是猜的：ROM 基址与长度 = 镜像文件大小；TBR = 向量槽里读出复位入口的
那个基址；RAM 上界 = 固件真正写过的高地址。

### 7.1 A 段的启动链是四条跳，第三跳是空 `ret`

```
0x000FC000 → 0x000F8010 → 0x00080044 → 0x000804FA → jmp 0x000FE426
                                          ↑ 一条孤立的 ret
```

`0x000804FA` 正是 REALOS `vsta_knl()` 该在的位置。内核对象其实都建好了（4 个 TCB 在
`0x00045C38` 起，自引用空环、状态 0），只是**从来没有 `sta_tsk` 把它们挂上就绪队列**。
`0x00080520`（main 的第二条 `call`）同样是纯 `ret`。

这四处空桩在 **1.02 / 1.03 / 1.10 / 1.11 四个版本里逐字节一致**（`probe/exp_xver.py`
从各自复位入口解析 call 链比对），所以不是"1.11 改了它"，是这套固件本来就这样。

### 7.2 于是有了 `boot_task`：跳过调度器，手工构造任务上下文

```bash
python -m frbox -M d300-a -c "boottask 0x8133A:0x4616C:0:0x80506;info"
```

语义是：先跑到 `0x80506`（BSS 清零完成），然后把 PC 设成任务 1 的入口 `0x8133A`、
`r15` 设成栈、`r4` 放参数。跳进去之后：

- 1,981 步到达第一个硬件等待 `0x0DCD2C`；
- 期间踩过 **500 个应用区 PC**、发过 10 次 `int #0x40`、自己写了 6 个中断回调槽；
- 对照实验（不铺垫 BSS）同一段只有 207 个 PC、4 次服务调用，且在 `0x0FECA0` 散架。

回调槽的地址公式是 `0x3F01C + (vec - 0x10) * 4`，任务 1 真注册了 5 个：
`vec 0x13 / 0x19 / 0x1B / 0x24 / 0x3C`。

## 8. 中断

### 8.1 向量表

A 段 48 个槽（`0x10–0x3F`）实测分布：

```
39 个真 ISR（各自的入口都在应用区）
 8 个未用 → 兜底 0x000FE250 → 0x00081338 的 bra -1（原地停机）
 1 个特殊 → 0x3F → 0x000FE776（全固件唯一一条 andccr #0xEF，清 I 位并带队列）
```

`probe/exp_allisr.py` 把 48 个向量全量注入一遍，判定"是否精确 `reti` 回注入点、
`r15`/SSP 是否逐位复原"。结果 **39 个 OK**，8 个未用向量按预期进死循环，`0x3F` 走飞
（它本来就不是普通 ISR）。这一步是"中断通路真的可用"的硬证据，不是"看起来像能用"。

### 8.2 中断控制器

ICR 组在 `0x440–0x46F`，48 个寄存器对应 48 个向量，级别 `0x12–0x1F`。
但**哪条线接哪个外设，只有两条有实证**：

```
IRQ 0x1B → ISR 0x0012FDB4   串口（读直接页 0x60，非零则 set_flg(3, 0x20)）
IRQ 0x20 → ISR 0x0012FE54   EXT9（索引 0x1BC480 的 25 项函数指针表，末尾写 0x38 = 0xFB）
```

`icu.py` 因此做成可配置绑定表：没实证的设备 `bind=None`，需要时在机器配置里显式接上，
并在这份文档和报告里标明来源。

## 9. μITRON 半主机

`INT #0x40` 是陷阱入口（A 段 `0x000FE3C0`，B 段 `0x00040668`）。分发器是 6 条指令：

```
lsl    #1, r12            ; 服务号 ×2 → 字节偏移
ldi:32 #<表尾>, r13
lduh   @(r12, r13), r12   ; 取 16 位相对偏移
extsh  r12                ; 符号扩展（服务号是负数）
add    r13, r12           ; 目标 = 表尾 + 偏移
call   @r12
```

所以服务表是"相对表尾的有符号 16 位偏移"，服务号从 −1 递减。`fr_itron.py` 把每个服务
分成两档记：**真实现**（真的执行了那段内核代码）和**桩**（只回一个错误码），绝不混在
一个通过率里。

实测（D300 1.11）：

```
A 段 176 槽：真实现 18 条，桩 158 条
B 段 176 槽：真实现 56 条，桩 120 条
```

## 10. 快照

`savevm` / `loadvm` 对应 QEMU 的同名命令。格式：

```
"FRBOXSNP" + 4 字节长度 + JSON 元数据 + 各块原始字节
块：cpu（r0–r15、dr0–dr3、PC、PS 各标志、延迟槽、停机原因）
    ram（每个 RAM 区域的字节；ROM 不存，重新加载固件即可）
    devices（各设备的可序列化字段）
    misc（步数、poke 列表、时钟锁定 tick 数）
```

不存未映射访问审计和 trace 日志 —— 那是统计，不是状态。

它的真正用途不是省时间，是**判据**：B 段跑到 191,517 步存档，`loadvm` 回来再跑 5,000 步，
逐条 PC 与第一条完全一致 —— 这是"解释器没有不确定性"的唯一硬证据。

```

x/16x 0x40000        x/8i 0x000FC000
step [N]   cont [MAX]   reset   load [PATH]
bp ADDR    bps    bpc ADDR
```

## 14. 已知缺口

不是"再跑跑就好"的清单，是**当前能力的边界**：

1. **卡点 3 `0x0CE136` 是动态寻址**（`r8` 由算出来），自动消除器抓不到等待寄存器。
2. **三处外设窗口语义未解**：`0x50000000` / `0x68000000` / `0x4000D000`，都有上万次
   访问记录，但不知道是哪个控制器。
3. **854 个未定义编码**归属未定：可能是 FR80/FR81 专有指令（已知 `srch0/srch1/srchc`
   三条就是 binutils 表里没有、靠 NikonEmulator 标注补的）。
4. **没有 gdbstub**。想看汇编级单步只能靠 monitor 或 `-d in_asm`。
5. **B 段没有帧缓冲，也没有字库**。就算把中断链路全接通，也不会"出画面" —— 真正的
   显示对象由外部芯片处理，固件只发事件标志。
