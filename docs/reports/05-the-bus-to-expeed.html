D300 固件：B 段与 EXPEED 之间的那条线

第七轮 · 2026-10-16 · 固件 B3000111.bin（7,340,032 字节，末 2 字节 CRC16 = 0x4F36）
这一轮干了什么。上一轮证明了"模拟器画不出 UI"，但没说清 B 段到底怎么跟 EXPEED 说话。 这一轮把 0x7000xxxx 窗口挂上探针，反汇编了发送/接收两个函数， 把那根线完整地解了出来——它是一条位串行总线，三条线：片选、时钟、双向数据。 顺手还修掉了两个让 EXPEED 外设一直"没通电"的 bug。

一、先修掉两个坑

坑 1：我自己上一轮埋的守卫写错了

上一轮为了让"片上 RAM 被当成未建模外设"的误报消失，我在 ExpeedProxyIoListener 里加了一个地址上界： 

private IoActivityListener get(int address) {
    if (address >= IO_ADDR_LIMIT) return null;   // IO_ADDR_LIMIT = 0x1000
    return listeners.get(address>>>16);
}

问题在于它判断的是完整地址，不是页内偏移。于是任何高于 0x1000 的地址——包括 0x4002xxxx、0x4003xxxx、 0x4006xxxx、0x4018xxxx、 0x5000xxxx、0x5C00xxxx、 0x6300/6400/6B00xxxx 和 0x7000xxxx—— 统统返回 null。也就是说：EXPEED 的十来个外设模型一次都没被触发过，等于全部断电。

正确写法是按"页号 + 页内偏移"判断，只挡住页 0x0000 里 0x1000 以上的片上 RAM：

if (page == 0x0000 && (address & 0xFFFF) >= IO_ADDR_LIMIT) return null;
return listeners.get(page);

本轮用一个 routeAll 开关把它做成可切换，以便做前后对照。

坑 2：改好路由之后必崩——上游真 bug

改好守卫第一次跑，在第 4,208,204 步（PC = 0x43748）抛空指针。抓到的堆栈：

java.lang.NullPointerException
  at ...FrSerialInterface.getFbyte2(FrSerialInterface.java:869)
  at ...ExpeedIoListener.onLoadData16(ExpeedIoListener.java:212)

原因是串口的 fifo1/fifo2 在"禁用"状态下恒为 null，而 getFbyte1()/getFbyte2() 直接对它们调 .size()。这是 NikonEmulator 上游代码本身的缺陷， 只是以前因为坑 1 根本走不到。已加空值保护返回 0。修好后 6000 万步跑满不崩。

二、一个必须纠正的指令语义

上一轮记错了一条，这里正式更正。FR 的位操作立即数是掩码没错，但 BANDL 的方向我写反了。它在 FrInstructionSet 里的实现是 byte &= (0xF0 | u4)， 也就是清掉 u4 里「没置位」的那几个低位，而不是"清掉 u4 指定的位"。
指令实际含义例
BANDL #u4,@Ri清 u4 未置位的低位#0xD → 只清 bit1（不是 bit0/2/3）
BORL #u4,@Ri置 u4 已置位的低位#0x2 置 bit1，#0x4 置 bit2
BTSTL #u4,@Ri测 u4 掩码#0x4 测 bit2（不是 bit4）

这条更正是后面所有结论的基础——按旧理解，那三条线根本对不上。

三、总线：三条线各是什么

探针挂上后做的第一件事，是看 0x7000xxxx 到底有几个地址被碰。结果意外地小： 6000 万步里，整个 0x7000 页只有 9 个地址被访问（读 7058 次 / 写 5160 次）， 而且全挤在 0x70000000–0x7000000F 这 16 个字节里。

按访问次数排序，0x7000000A 独占 4947 写 / 6754 读，其余都是个位数。 顺着 PC 热点找到 0x19EEF8 和 0x19EF3C 两个函数， 反汇编一读，结构立刻清楚了。

三条线的定义

地址位作用置 1清 0
0x70000002bit2片选 CS（外围 ASIC 的使能）BORL #0x4BANDL #0xB
0x7000000Abit1时钟 CLKBORL #0x2BANDL #0xD
0x7000000Abit2双向数据 DATABORL #0x4BANDL #0xB
0x7000000Abit0另一条控制线（每次交易前后翻转）BORL #0x1BANDL #0xE

顺带一提，0x70000000–0x0F 这 16 个字节在复位后极早期 （第 386–428 步）被写进 8 个 16 位初值： 0x7C0F、0xFF1F、0x3FFF、 0xFFBF、0x57FF、0x3E0A、 0x31FA、0xFF3F——看起来是一组 GPIO 方向/初始电平寄存器。

四、实测：这条线上到底跑了什么

把发送/接收函数挂上钩子，录下每一次调用（注意 onClockTick() 是多周期指令， 同一条指令会连续几拍 PC 不变，必须"PC 刚跳进来"才记一次；不去抖的话接收次数会正好翻倍，452 → 226）。 6000 万步的完整清单：

开机初始化（第 2,870,872 步起）

0x86  → 读 1 字节      0x06  0x01
0x06  0x0A             0x46  0x00
0x26  0x07             0x01  0x01
0x00  0x00             0x00  0x00
0x36  0x00
0xF6  → 读 1 字节      0x76  0x00

一共 20 个字节。格式是"命令字节 + 参数字节"成对，其中 0x86 和 0xF6 后面跟的是读。

然后就只剩心跳了

0xA6  → 读 7 字节

这一条每约 1,782,000 步发一次，一共发了 32 次，最后一次在第 58,352,019 步， 之后到 6000 万步再无动静。7 次读分别来自 7 个不同的调用点 （0x19ECD0 / D8 / E4 / F0 / F2 / FE / 08）。

关键观察：这条线上没有画面。6000 万步里 B 段通过这条总线一共只发了 52 个字节。 一个 640×480 的屏幕哪怕 1 位色也要 38 KB。这条线不可能是显示数据通道—— 它是 B 段用来查询/配置某个外围 ASIC 的控制口（状态、电源、按键矩阵之类的候选），不是画面管道。

五、0x86 读回来的那个字节是个开关

既然仿真里没有 EXPEED，读回来的一律是 0xFF。 我加了一个桩：只在接收函数体内把数据线拉低，让每次读回 0x00 （选函数体内是因为发送函数共用同一条数据线，不能干扰它）。结果序列明显变了：

应答初始化序列发送字节调用点
0xFF（默认，无 EXPEED） 0x86→FF · 0x06 01 · 0x06 0A · 0x46 00 · 0x26 07 · 0x01 01 · 0x00 00 · 0x00 00 · 0x36 00 · 0xF6→FF · 0x76 00 5221
0x00（打桩） 0x86→00 · 0x46 00 · 0x36 00 · 0xF6→00 · 0x76 01 409

原因在代码里写得很直白：

0019E90C  D317           CALL    0x0019EF3C     ; 读回状态字节 → R10
0019E918  C800           LDI:8   #0x80,R0
0019E91A  82A0           AND     R10,R0         ; 测 bit7
0019E91C  F24A           BEQ:D   0x0019E9B2     ; bit7 == 0 就跳过整段配置

状态字节的 bit7 决定要不要跑中间那 6 组配置写。读回 0x00（bit7 = 0）时固件认为一切正常， 直接跳到 0x19E9B2；读回 0xFF（bit7 = 1）时才逐项写 0x06/0x26/0x01/0x00 那一串。 心跳 0xA6 两种情况下都是 32 次，不受影响。

六、EXPEED 外设接上电之后

把坑 1 修好、让 EXPEED 的各个外设模型真正生效，同样的 6000 万步：

固件明显活跃了——系统调用翻到 2.5 倍，改写块翻了一倍多，新增的热点有 0x9F80E000（17 次）、0x9F810000（18 → 22 次）。 这些都是内核数据结构所在的区域，不是画面。

但边界要守死：仍然没有出现任何 300 KB 级（8 位色）或 38 KB 级（1 位色）的整屏连续写入， 最终 PC 依旧落在空闲任务 0x407DC。 换句话说，给 EXPEED 通上电让固件更忙了，但画面还是没出来。 上一轮的结论没有被推翻，反而被加固了一层。

七、这一轮的结论

  1. 总线解出来了：B 段通过 0x7000000A 的 bit1（时钟）和 bit2（双向数据）、 外加 0x70000002 的 bit2（片选），用软件翻转 IO 的方式跑一条 8 位串行总线，LSB 先、上升沿采样。
  2. 这条线不传画面：6000 万步只发了 52 个字节，全是"命令 + 参数"和状态查询。 它管的是配置与状态，不是像素。
  3. 修好路由是有收益的：系统调用 810 → 2019，改写块 27 → 58， 并且定位并修掉了上游 FrSerialInterface 的一个空指针缺陷。
  4. 但画面依旧没有：B 段手里确实没有帧缓冲，也没有点阵字库—— 上一轮的判断成立。

接下来三条路（按信息量排序）

  1. 顺着 0x19E9B2 往下读：那是"EXPEED 正常"分支的落点， 把状态机各分支对应的命令序列摸全，就能写出一个应答表，让固件真正跑完初始化。
  2. 找出谁在管画面：既然不是这条串行总线，就去查 0x4018（图像传输）、 0x4002/0x400F（分辨率转换）这几个 EXPEED 内部模块， 看 B 段有没有走 DMA 或共享内存把位图交出去。
  3. 注入按键事件：先统计"哪个 IO 地址被反复读"定位扫描点，再喂一个 MENU 键， 看固件会不会走到菜单逻辑——那时候即使画不出来，至少能看到界面状态机在动。
