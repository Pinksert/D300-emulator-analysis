仿真台 V13：不是等消息，是在等时间

先纠正 V12 的两处误判 · 把「等待原因位」逐项钉死 · 再补上真正缺的那件硬件：完成位与中断是一对

一句话：V12 以为任务 4/5 卡在「邮箱」上，其实任务 5 只是 slp_tsk 睡着了； 真正缺的不是消息，而是一次「完成位 + 中断」的硬件事件。补上它之后， 不做任何 flag 注入，任务 1 自己推完了三个等待点，并用 sta_tsk 把任务 9 和任务 4 拉了起来。
边界：事件源是模型 —— 状态位（0x80/bit3）、向量（0x23）是从固件代码里读出来的 「必要条件」，但「多久完成一次」是我们选的（1,024–16,384 周期结论一致，说明不敏感）。 能报「补上这个事件源后固件自己把任务 9/4 拉起」；不能报「相机功能跑通了」。

一、先纠错：V12 说「任务 5 在等消息」，是错的

V12 把 TCB 的 +0x00 当成「等待对象」，于是把 0x45990 读成邮箱， 又把状态位 0x00010000 读成「等消息」。V13 用「状态字 ↔ 该任务最后一句系统调用」 逐项对照，两个都推翻了：

现场状态字最后一句调用在 flag 队列里？判定
任务 1 等 flg3/0x20000x00100004wai_flg是（flag3）等事件标志
任务 5 调完 slp_tsk0x00010004slp_tsk否休眠，不是等消息
任务 5 等 0x45990 那次0x00400004rcv_msg否等消息（另一个位）
没启动的任务0x00000010—否休眠/未启动

那 0x45990 到底是什么？看它就明白了 —— 这是 0x45980 一带的原始内存：

0x45980: 00045C0C 00800000   ← 当前 TCB / 就绪位图（bit(31−8) → 优先级 8）
0x45988: 00045988 00045988   ← 优先级 0 的就绪队列（空）
0x45990: 00045990 00045990   ← 优先级 1 的就绪队列（空）
...
0x459C8: 00045C0C 00045C0C   ← 优先级 8 的就绪队列：挂着空闲任务的 TCB

所以 0x45990 = 0x45988 + 1×8 是优先级 1 的就绪队列槽。 TCB 的 +0x00/+0x04 是链表的前后指针（prev/next），不是「等待对象」—— 任务在 flag 队列里时它恰好等于 flag 控制块，看起来像对象；但休眠的任务会留着上一次所在就绪队列的地址， 于是被误读成邮箱。

修法：realos.wait_of() 改成「状态位判种类 + 扫 10 个 flag 队列反查是哪一个」， 不再信 TCB+0x00。blockers() 现在只对 kind=flag 报 flag 号， sleep/msg 只报种类，不编对象地址。自检里三条断言跟着改了。

二、等待原因位表（可以直接引用）

TCB +0x08 状态字
  低字节   0x00 = 运行/就绪
           0x04 = 等待
           0x10 = 休眠/未启动
  高位     0x00100000 = 等事件标志（wai_flg）
           0x00400000 = 等消息（rcv_msg）
           0x00010000 = 休眠（slp_tsk）

三条判据都满足才写进表：① 该状态字能唯一对应一种等待；② 它的最后一句系统调用与这一位一一对应； ③ 同一任务换一种等待方式时，这一位跟着换（任务 5 先 rcv_msg（0x00400004）后 slp_tsk（0x00010004）， 两个位都出现过）。出处 results/frbox/wait-kind.txt。

三、真正缺的东西：中断和状态位是一对

任务 5 的循环（0x0A67C2 一带）：

0x0A67DC  把回调 0x0A6938 写进槽 0x3F074
0x0A67E6  dmovb #2  → 0x8C        ; 配置
0x0A67EE  borl #1 / #2 → @0x8F
0x0A67F6  borh #1 → @0x82         ; 启动
0x0A6810  int #0x40 (slp_tsk)     ; 睡，等中断

vec 0x23 的 ISR（0x080D8A）只有一句有用的：取槽 0x3F074，非零就 call @r0。 而槽里那两个回调，第一件事完全不同：

回调开头行为
0x0A6938直接 wup_tsk(5)「有事，起来」——不看状态
0x0A687Aldi 0x80 / btstl #8,@r0
beq 跳去取数据那一支		先测 0x80 的 bit3，置位了才 wup_tsk(5)

这就是 V12 只能叫醒一次的原因：中断来了，但状态位没置 —— 回调走「没数据」那一支， 任务被叫醒又立刻睡回去。中断和状态位必须同时到，这是硬件的活，仿真台原来两样都没有。

四、新设备：完成位 + 中断

frbox/dev_evt.py，两种模式：

  • period=N（默认 4096）：每 N 个周期置一次状态位并打中断 —— 对应「转换器/传感器在连续工作」；
  • period=0：看启动位（0x8E/bit3）的上升沿，等 delay 个周期后置位 + 打中断 —— 对应「一次操作一次完成」。

默认关闭（--events / enable_events() 才挂），所以 V2–V12 的基线一个字节都没动。

八、这一轮改掉的旧说法

  • 作废V12「任务 5 等消息对象 0x45990」：0x45990 是优先级 1 的就绪队列槽， 任务 5 是 slp_tsk 休眠。真正的等消息状态是 0x00400004（rcv_msg）。
  • 作废「TCB+0x00 是等待对象」：它是链表 prev 指针。判等待对象只能靠状态位 + 队列反查。
  • 新增等待原因位表：0x00100000 标志 / 0x00400000 消息 / 0x00010000 休眠。
  • 新增「中断 + 状态位」是一对：只有中断，回调会走「没数据」分支， 任务被叫醒又睡回去 —— 这是 V12 里 wup_tsk(5) 只能生效一次的原因。

九、下一步

  • 第二个事件源：任务 1 等 flag9/0x400、任务 9 等 flag10/0x4000，得先找到哪条向量/哪个器件能置这两位 （静态里一处都没有 → 更可能来自一个还没注册回调的外设）。
  • 邮箱对象：任务 5 现在真的在等消息（0x00400004）。邮箱结构还没读（对象基址 +0x08 是队列头）， 读出来之后才能判断那条消息该由谁发。
  • 周期与时基：现在事件周期是「随便选的、结论不敏感」。真正的时基中断（系统 tick）还没找到 —— 找到之后 dly_tsk 这类延时才能自己到期。
  • 多事件源驱动：dev_evt 已经支持多个实例（状态位/向量可配），下一步做一个「按已注册回调槽自动配事件源」的驱动。
