D300 固件 · 显示管线终于跑起来了

把"画不出界面"这个结论拆开，找到确切的卡点，并且真的让固件自己走完了整条绘制流程 · 2026-10-24
一句话结论：D300 的界面不是"没画"，是卡在等一个永远不会来的信号。 显示更新任务（任务 4）一直在等事件标志 flag 3 的 bit4（0x10）， 而整个 B 段固件里没有任何一处代码会置这个位—— 它由显示控制器的硬件中断来置。我们手动把这个位置上去之后， 固件一口气处理并绘制了 7 个显示对象，调用了 4 个真实的绘制函数。

一、这轮解出来的三张表

之前几轮一直在"猜"哪些内存地址是干什么的，这轮把支撑显示的三张核心表全部解了出来， 都是可以直接反推的静态结构，不是推测。

1. 事件标志对象表 — 0x000551B0

在内核的 set_flg 实现（0x41A48）里，第一行就把表基址写死了： LDI:32 #0x000551B0,R14。表头是「条目数 = 17，元素大小 = 16 字节」， 第 N 号标志的控制块指针在 0x551B0 + 4 + (N-1)×16。

控制块 + 8　→ flag 3 就是 0x680008E0
控制块 +0

控制块 +0x0E
等待模式（wfmode，半字）
控制块 +0x14
等待位模式（waiptn）
顺带把 wai_flg 的参数约定也钉死了（内核 0x41B0A 里逐条对照出来的）： R5 = flag 号，R6 = 等待位模式，R7 = 等待模式，R4 = 结果输出指针。 这和 set_flg / clr_flg 的「R4 = flag 号，R5 = 位模式」不是同一套顺序， 之前几轮按 set_flg 的顺序去读 wai_flg，读出来的"flag 号"是一串内存地址，就是这个原因。 等待模式的判定位是 R7 & 0x02：置位走 OR 等待（任一位命中即可），清零走 AND 等待（要全部命中）。

二、显示管线的五个阶段

任务 4 的循环体在 0x12DFAE，是一段很规整的流水线。每一段的失败都会跳到 0x12E48E（等待 / 错误处理）重新开始。

0x12DFAE  循环开始
  ├─ CALL 0x12E006   阶段 0：重置，清空 70 个节点的脏位
  ├─ CALL 0x12E0F8   阶段 1：从待绘制链表头取一个 id
  ├─ CALL 0x12E162   阶段 2：等待 flag 3 就绪      ← ★ 卡在这里
  ├─ CALL 0x12E1EC   阶段 3：选定对象，算出描述符指针 0x9F58D858
  ├─ CALL 0x12E326   阶段 4：取数据
  ├─ CALL 0x12E412   阶段 5：把数据拷进目标缓冲
  └─ CALL 0x12E674   阶段 6：★ 真正的"绘制"——调用 描述符[+0x0C]

待绘制队列本身也解出来了：链表头在 0x9F58D500， 节点数组从 0x9F58D508 起，每个 12 字节（前 4B = next，中 4B = prev，第 9 字节 = id，最高位 0x80 = 待更新）。

基线实测（2000 万步，不做任何干预）
阶段命中次数

也就是说：请求进队列了（9 次），但消费端一次都没跑。

三、确切的卡点

阶段 2 的函数 0x12E162 里，是一条带超时的等待：

twai_flg(flag=3, waiptn=0x74, wfmode=OR, tmout=100)
返回后：
    R0 = 实际取到的 flag 值
    R0 &= 0x74
    if (R0 == 0x10)  → 返回值 R4 = 1（继续）
    else             → 返回值 R4 = 0（退回 0x12E48E 等待）

判据是 (flag3 & 0x74) == 0x10，也就是 bit4 必须为 1，且 bit2 / bit5 / bit6 必须为 0。 把整个 B 段扫了一遍，往 flag 3 上写过的位模式只有这几种：

位谁写的调用点
0x01set_flg0x12E0EC / 0x12E51A
0x02（无人置位，但 0x12E48E 在等它）—
0x08set_flg（往链表插入请求时）0x12E738
0x10没有任何一处—
0x80set_flg0x12E630
0x200set_flg0x15C87A
0x800set_flg（id 9 的绘制函数里）0x12ECDA
bit4 是唯一的缺口。它不在任何一条 set_flg 的立即数里， 也不在任何 clr_flg 会保留的位里（0x12E34A 的 clr_flg(3, 0xFFFFFF8F) 保留的是 bit4/5/6，说明固件预期 bit4 已经被别人置好了）。 这符合"硬件中断里置位"的特征：信号来自 B 段之外的显示控制器 / 帧同步中断， 在我们的单芯片仿真里永远不会发生。

四、把 bit4 补上之后：管线真的跑通了

做法：每执行一步就强制把 flag 3 的位模式修正为 (cur & ~0x64) | 0x10， 即保证 bit4 = 1、bit2/5/6 = 0，其余位不动。这是最小干预—— 不去改任何代码、不去伪造数据，只补上那个缺失的信号。

结果：任务 4 连续处理并绘制了 7 个显示对象，调用了 4 个真实的绘制函数。

五、"绘制函数"到底是什么——这轮的意外收获

原来以为 描述符[+0x0C] 是一段画像素的代码。翻开 0x12F452（id 0x29 的绘制函数）， 它全部内容只有三行：

0012F452  LDI:8   #0x0A,R4          ; flag 号 = 10
0012F454  LDI:20  #0x08000,R5       ; 位模式 = bit15
0012F458  LDI:8   #0xD0,R12         ; set_flg
0012F45C  INT     #0x40
0012F45E  RET
所谓"绘制"，就是给下游任务发一个事件标志。 它不是在写帧缓冲，也不是在往串口吐数据——它只是说"0x29 号状态变了，你看着办"。 另外两个也印证了这一点：0x12E8E2（id 7）和 0x12E806（id 5）都是 拿数据缓冲里的字节去和当前状态字节逐位比对，变了就更新状态、置标志位，没变就直接返回。

再往下追一层：全固件等待 flag 10 的 wai_flg 有三处， 其中 0x242BF4 落在任务 21（入口 0x242DA0）的代码范围内， 而 flag 10 也是全固件 set_flg 次数第二多的标志（194 处）。

重新拼出来的架构

  按键 / 状态变化
        │
        ▼
  0x12E6F8  把对象 id 挂进待更新链表 (0x9F58D500)，set_flg(3, 0x08)
        │

    取 id → 拷数据 → 调 描述符[+0x0C]

        │

这解释了之前几轮一个一直没想通的现象： 0x9F5A0F60 那个"显示对象数组"为什么永远是全 0—— 它根本不在这条链上。B 段只维护状态，像素是下游的事。

六、顺手修掉的一个模拟器缺陷

跑通之后，固件在 step 3,119,524 崩了，报的是：

Serial Interface 0: cannot be configured in mode MD=0b001.
Only CSIO mode (0b010) and minimal UART (0b000) are supported for now

之前已经为异步模式 0（MD=0b000）加了旁路，这次把多机异步模式（MD=0b001） 也放行，同样走"记录字节但不真发"的旁路。D300 显然把串口 0 用在了非 CSIO 的用途上。

七、下一步

  • 找 bit4 的真实来源。它不在 B 段代码里，那就去查中断向量表里跟显示相关的那几路 ISR， 看有没有哪条在 set_flg 到 flag 3（用运行时算出来的位模式，静态扫不出来）。
  • 把任务 21 接上。它等 flag 10，是绘制的下游。如果能把它也推起来， 它才是真正把命令发给显示控制器的那一环——那里才有"画面"的影子。
  • 跑双芯片。目前只仿真了主控（B 段）。协处理器（A 段）没跑， 很多"硬件就绪"信号可能本来就来自那里。
