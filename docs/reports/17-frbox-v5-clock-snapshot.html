仿真台 V5：0x482 不是双机握手，是时钟就绪位

D300 固件全系统模拟器 frbox 0.5 · 2026-10-29
一句话：上一版把 A 段停在 0x8007C 的那条 btsth #8,@r0 判成「等 B 段举手」， 这一版把复位入口一路反汇编下来，证明它等的是自己的时钟发生器——0x482 位 3 写 1 启动、 位 7 由硬件置「就绪」。补上这个设备模型之后，A 段不用再靠 --latch 硬灌值就能自己走过去， 那个寄存器从「未建模读 66,660 次」变成「0 次」。

顺带做了一件 QEMU 有、我们没有的事：savevm / loadvm 整机快照，恢复后 5,000 步逐条指令同步， 这是「解释器确定性」第一次被硬验证。
0次 int（A 段全启动）
43,446A 段步数（原 41,565 靠作弊）
92/92frbox 自检断言
5,000快照恢复后逐条同步步数

一、上一版错在哪

V4 报告的结论是：A 段在 0x0008007C 自旋，等 0x482 的位 7， 推测「是 B 段通过双机链路写进来的」，于是给了个 --latch 0x482=0x88:2 的临时手段， 建议下一步做「双机互联，把 A、B 放进同一地址空间共享邮箱」。

这个推断方向错了。错的原因也很典型：只看了一条指令的地址，没有把调用链往上追。 其实复位入口就在 A 段 ROM 的 0x000FC000，往上追三跳就能看见写这个寄存器的人是谁。

二、证据链：从复位入口走到 0x80044

复位向量槽读到入口 0x000FC000，头六条指令就把后面的顺序交代清楚了：

0x000FC000  ldi:32 #0x4616C, r15      ; 设栈
0x000FC006  stilm  #0x10              ; ILM = 0x10，先屏蔽高优先级中断
0x000FC008  ldi:32 #0xFFC00, r0
0x000FC00E  mov    r0, TBR            ; 向量表基址 = 0x000FFC00
0x000FC010  ldi:32 #0xF8010, r13
0x000FC016  call   @r13               ; ① 第一跳
0x000FC018  ldi:32 #0x80044, r13
0x000FC01E  call   @r13               ; ② 第二跳 ← 就是这里
0x000FC020  ldi:32 #0x804FA, r13
0x000FC026  call   @r13               ; ③ 第三跳
0x000FC028  ldi:32 #0xFE426, r0
0x000FC02E  jmp    @r0                ; ④ 交给 REALOS 启动

第二跳的 0x00080044 全长不到 60 字节，写完就等：

0x00080044  ldi:8  #0x33, r0
0x00080046  ldi:20 #0x7004, r12
0x0008004A  stb    r0, @r12            ; [0x7004] = 0x33   （RAM，与本次无关）
0x0008004C  ldi:8  #0x01, r0
0x0008004E  ldi:20 #0x486, r12
0x00080052  stb    r0, @r12            ; [0x486] = 0x01
0x00080054  ldi:8  #0xF0, r0
0x00080056  ldi:20 #0x487, r12
0x0008005A  stb    r0, @r12            ; [0x487] = 0xF0
0x0008005C  ldi:8  #0x34, r0
0x0008005E  ldi:20 #0x484, r12
0x00080062  stb    r0, @r12            ; [0x484] = 0x34   （配置）
0x00080064  ldi:8  #0x08, r0
0x00080066  ldi:20 #0x482, r12
0x0008006A  stb    r0, @r12            ; [0x482] = 0x08   （位3 = 启动）
0x0008006C  ldi:8  #0xA5, r0
0x0008006E  ldi:20 #0x483, r12
0x00080072  stb    r0, @r12            ; [0x483] = 0xA5  ┐ 两键写保护
0x00080074  ldi:8  #0x5A, r0
0x00080076  stb    r0, @r12            ; [0x483] = 0x5A  ┘
0x00080078  ldi:20 #0x482, r0
0x0008007C  btsth  #8, @r0             ; 测 [0x482] 位7
0x0008007E  beq    -4                  ; 不置位就原地等
0x80080     ldi:8  #0x36, r0
0x00080082  ldi:20 #0x484, r12
0x00080086  stb    r0, @r12            ; [0x484] = 0x36   （0x34→0x36，位1 = 锁定确认）
读法：先写配置 → 置启动位 → A5/5A 两键解锁 → 空转等位 7 → 等到后把配置位 1 置上。 这一串在嵌入式里没有第二种解释：PLL / 时钟发生器的启动等待流程。位 7 是硬件状态位， 位 1 是「切换完成」确认位，0xA5→0x5A 是富士通惯用的寄存器写保护两键序列。

三、证据链：没有任何代码写位 7

上面是「它想干什么」，还缺一条「别人写不了」。「别人」包括 B 段，也包括 A 段自己的其它函数。 于是做两件事。

1. 全 A 段 ROM 静态扫描

把 524,290 字节全反汇编一遍，找立即数或位移落在 0x478–0x48C 的指令，命中 59 条。 其中写这组寄存器的只有上面那 6 条 stb，其余是：

  • 0x00080F6A：一处 ISR 里的 ldi #0x482 + bandh #7,@r0，随后读 0x3F09C 的计数——像是把某个状态位清掉再记数。
  • 0x00081310 / 0x0008132C：临界区里改 0x486（外面套着 andccr #0xEF / orccr #0x10 的开关中断包裹）。
  • 0x000D0872–0x000D089A：一段寄存器组初始化表，按 0x470/0x474/…/0x48A 顺序灌默认值。

没有任何一条指令往 0x482 写带位 7 的值。

2. 动态写入监视

把 0x480–0x48F 全部挂上 watch，跑到自旋为止，一共 200,142 步，命中 66,666 次：

方向地址值次数来源 PC

读 66,660 次、写 6 次、没有任何一次写入置位位 7 —— 位 7 只能来自硬件。

顺便把 B 段也扫了一遍：全 ROM 引用 0x482 只有 6 处，其中 2 处在启动区 （0x400E8、0x404C8），但跑起来 一次都没写过这组寄存器。 两台机器之间不存在围绕 0x482 的握手。

四、寄存器组语义（按实测填，不按手册猜）

地址实测行为判定
0x482写 0x08 后开始计时，到点读回位 7 = 1；软件写入不改变位 7位 3 = 启动，位 7 = 就绪（只读，硬件置位）
0x483连续写 0xA5、0x5A写保护两键序列
0x484先写 0x34，锁定后改 0x36配置（0x34）+ 位 1 = 切换完成
0x486写 0x01；另有一处 ISR/临界区会改使能类寄存器
0x487写 0xF0分频/预置类配置

括号里的「时钟/复位控制」是按行为给的功能名，手册原文我们手上没有；但「位 3 启动、位 7 就绪、位 1 完成」 这三条是由上面两路证据直接推出来的，不依赖手册。

五、新设备：frbox/dev_clk.py

140 行，挂到直接页 0x480–0x48F。建模口径刻意保守：

  • 寄存器按字节存影子，读回影子（没写过的位为 0）。
  • 写 0x482 时位 7 被强制抹掉——软件写不进状态位，和实测一致。
  • 写 0x482 且位 3 = 1 → 武装倒计时；倒计时到点把位 7 置 1。
  • 写 0x483：先 0xA5 再 0x5A 才算解锁（只记录，不改变锁定时机——因为实测固件是在启动之后才解锁的）。
  • 倒计时按 tick 计，默认 8 个 tick ≈ 2,048 步，命令行 --clk-lock N 可调，0 就是立刻就绪。

挂上之后 0x482 从「未建模寄存器」名单里消失。口径要说准，不然两个数字不是一回事：

  • 建模前：跑到自旋为止的 200,142 步里，0x482 被读 66,660 次，全部计入「直接页未建模读」。
  • 建模后：走完整个启动 43,446 步，直接页未建模读只剩 3 次（都在 0x0DF）。

步数不同，不能直接相减说是「降了多少倍」；能说的是：这组寄存器不再是黑盒，它的行为由模型给出，而不是由 --latch 灌值。

三种手段最后都停在同一条 reti、同一个 PC 数（824）， 说明时钟模型不是「为了能跑而凑的」，它只是把固件本来要做的事做对了： 41,655 与 43,446 的差正好是 1,792 步 = 7 个 tick × 256，不多不少。

七、新卡点：A 段整个启动一次 int 都没执行

过了时钟这一关，A 段停在 0x000FE50C 的 reti， 弹出 PC=0、PS=0。上一版记的是「栈顶 8 字全 0」， 这一版把原因量化了：把 Fr.eit() 包一层计数器，跑完 60,000 步，A 段的 EIT 次数是 0。 B 段是 1 次（向量 0x40，即唯一那次 μITRON 服务调用）。

没有 EIT 就没有栈帧，reti 必然弹到 0。而之所以走到 reti， 是因为这条链：

0x000FE426  ldi:32 #0x3FBB0, r0
0x000FE42C  ldi:32 #0, r1
0x000FE432  st     r1, @r0           ; *0x3FBB0 = 0
0x000FE434  call   …                ; 0xFE434–0xFE44A 连打 12 条初始化调用
0x000FE44C  ldi:32 #0x3FBB0, r0
0x000FE452  ldi:32 #1, r1
0x000FE458  st     r1, @r0           ; *0x3FBB0 = 1
0x000FE45A  ldi:32 #0x804FC, r12
0x000FE460  call   @r12              ; 调固件 main（0x804FC）
0x000FE462  ldi:32 #0x3FBB0, r0
0x000FE468  ldi:32 #2, r1
0x000FE46E  st     r1, @r0           ; *0x3FBB0 = 2
0x000FE470  bra    0xFE4DE           ; 去「恢复上下文」收尾

而 0x804FC 这个「main」只有一个 st r1、两个 call、 一个 ld、一个 ret——它跑完就正常返回了。收尾的地方是：

0x000FE4DE  ldi:32 #0xFE160, r0     ; 从 ROM 取一个字
0x000FE4E4  ld     @r0, r14
0x000FE4E6  ldi:32 #0x45980, r0
0x000FE4EC  st     r14, @r0          ; 记到 RAM
0x000FE4EE  …
0x000FE4F2  orccr  #0x20            ; 开中断
0x000FE4FE  orccr  #0x20
0x000FE500  ld     @r15+, r1        ; 弹 r1 / r5 / r4
0x000FE506  ldm0   r0–r7            ; 弹 8 个
0x000FE508  ldm1   r8–r14           ; 弹 7 个
0x000FE50A  andccr #0xDF            ; 清 S
0x000FE50C  reti                    ; ← 这里弹到 0
结论要改口径：「任务没建起来」这个说法不够准。更准确的是： A 段的启动主流程只做硬件初始化，从头到尾没有发起任何 μITRON 服务调用（0 次 int）， 初始化做完就返回；REALOS 于是走去「恢复下一个任务上下文」，而那个上下文根本不存在，弹出来全是 0。

所以下一步不该去找「谁写 0x482」，而该找：哪个初始化调用本该创建任务、却提前返回了。 判据很清晰——那 12 条 call 里只要有一条走进 int #0x40，EIT 计数就不会是 0。

八、意外收获：两段固件都内嵌 REALOS/FR 版权串

追 0xFE4DE 时撞见一段 ASCII，顺手把两台机器都查了：

A 段 0x000FE472  "Softune REALOS/FR is Realtime OS for FR Family, based on micro-ITRON
                   COPYRIGHT(C) FUJITSU LIMITED 1994-1999\0"
B 段 0x0004073E  （同一串，一字不差）

这条比之前的「0x0004073E 有 Softune REALOS/FR 版权串」更进一步：后半句直接写明 based on micro-ITRON， 版权年份 1994-1999。A、B 用的是同一套内核、同一段版权声明，只是链接进各自的镜像里。

九、savevm / loadvm：第一次硬验证「确定性」

新增 frbox/snapshot.py（157 行），monitor 里是 savevm PATH / loadvm PATH。 快照含 CPU 全部寄存器与标志、每块 RAM 字节、每个设备的可序列化状态、步数、poke 列表；ROM 不存（重新 load 固件即可）。

机器快照大小落点恢复后状态再跑 5,000 步
d300-a526,831 字节43,446 步 / PC=0逐字段一致逐条指令同步
d300-b1,312,620 字节191,518 步 / PC=0逐字段一致逐条指令同步

做这个的过程中被自己的实现坑了两次，都值得记下来：

  • JSON 把字节串变成了字符串：bytearray 不能直接 JSON 化，用 default=str 会静默变成 "bytearray(b'\\x00…')"，恢复后设备读寄存器返回的是字符，拼运算直接报 TypeError。改成 base64 + 类型标记。
  • JSON 把字典的整数键变成了字符串：直接页影子存储是 {0x482: 0x88}，恢复后成了 {"1186": 136}，shadow.get(0x482) 永远取不到 → 一读未建模寄存器就归零。这是快照看起来成功、跑起来两万步就分叉的元凶。
这两个坑的形状是一样的：序列化会把类型信息吃掉，而吃掉的恰好是「读一个寄存器返回什么」。 所以快照这种东西不能只看「恢复后 PC 对不对」，必须看「恢复后再跑几千步还同不同步」。 第 5,000 步还同步，才算过。

十一、下一步（按证据强度排）

  1. 追那 12 条初始化 call：0xFE434–0xFE44A，逐条看谁本该创建任务。 判据是「哪一条内部出现 int #0x40」。这是唯一能让 A 段不靠弹 0 结束的路径， 也是把「824 个 PC」往上抬的最短路径。
  2. 把 0x3FBB0 这个相位变量做成断点：0 / 1 / 2 三个值分别对应 「未初始化 / main 运行中 / main 已返回」，watch 0x3FBB0 就能一眼看出有没有回到过 1。
  3. 用快照做假设检验：现在可以「跑到 43,446 步 → 存盘 → 反复试不同 poke / 不同 --clk-lock 值」， 不用每次重跑 4 万步。这是本轮最直接的效率收益。
  4. 三处未建模外设窗口（0x50000000 / 0x68000000 / 0x4000D000）的语义， 以及 B 段 854 个未定义编码的归属。
一句话收尾：这一版没有让固件「跑出画面」，但它把上一版一个方向性错误纠了正， 把「等谁」从一个猜测变成了两路证据支持的事实，并且顺手证明了这个模拟器是确定性的。 对「做成像 QEMU 一样的模拟器」这个目标来说，能存盘、能恢复、还能保证恢复后一步不差， 比多跑十万步更有价值。
