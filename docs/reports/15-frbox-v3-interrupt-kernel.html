仿真台 V3：把中断、向量表和 μITRON 内核接上

D300 固件函数级仿真台 · 第三次加固报告 · 2026-10-29
一句话：前两版能跑「一个函数」，但跑不了「一个中断」——因为中断入口、向量表、内核派发这三段都没实现。 这次补上之后，两段固件各自的 256 条向量槽全部读通，94 条真接线的中断能一条条拉起来跑，其中 83 条能自己跑完 reti 回来； μITRON 那层也不再靠猜，而是直接读固件自己的分发表。

一、先补的是「进中断」这条路

之前仿真台能从一个函数入口跑到底，但固件里真正干活的很多东西不是被「调用」的，是被「打断」进来的。 中断处理这条路要四件事配合：把 PS 和 PC 压进系统栈、切到系统栈、按 TBR 算向量槽、跳进去。少了任何一环， 要么跳错地方，要么 reti 弹出一堆垃圾。

动手前先确认了 FR 的入栈顺序。fr30.cpu 里 int 指令的注释写得很清楚： 先压 PS、再压返回地址，都压到 系统栈（h-dr 2），然后置 I=0、S=0。 所以栈顶是返回地址，reti 先弹 PC、再弹 PS —— 顺序反了不会报错，只会静默跑飞。

顺手抓到一个真 bug：原来的 SSP/USP 是两套各管一半 —— 一个 stack_bank 字典负责 S 位切换， 专用寄存器 dr2/dr3 又单独存了一份，两者从不同步。结果是「读 SSP」和「切换栈」拿到的是不同的值。 现在统一成：dr2/dr3 是权威值，R15 永远等于当前 S 位选中的那一支。 这个 bug 只在 reti 恢复 S 位时才暴露，不写这条自检就永远发现不了。

补了 16 项自检，专门盯不会报错的错

中断这块最麻烦的地方是「错了也照跑」：栈指针错 8 字节、PS 恢复成脏值、ILM 屏蔽判断反了，程序都不会崩， 只是行为不对。所以每一项都单独验：

  • 向量槽地址 = TBR + (255 - 向量号) × 4（倒序）
  • 入栈后 SSP 恰好下移 8；栈顶是返回地址；栈顶 +4 是旧 PS，且旧 PS 的 S 位原样保留
  • 进中断后 I 被清 0、S 变 0（走系统栈）、USP 被存进 dr3
  • reti 之后 PC 回到断点、S 位恢复、R15 回到 USP、SSP 复原
  • 中断级别 ≤ ILM 时不受理且请求留在队列；I=0 时不受理

自检总数从 38 条涨到 54 条，全过。

二、向量表：两段各 256 条槽，摸清了

把两段固件的 TBR 定下来，再把 256 条槽全部读出来。判据很干脆：没接的中断统一填一个兜底地址， 所以「地址 != 兜底」就等于「这台机器真接了这条中断」。

段TBR兜底地址占位真接线去重处理程序
A（IO 协处理）0x000FFC000x000FE2502104644
B（主控）0x000EFC000x000404F82084846

两个兜底地址的形态也不一样，值得记一笔：

  • A 段的兜底 0x000FE250 是一段真实代码的起点，接着往下是「压栈 → 取默认处理 → 返回」的流程；
  • B 段的兜底 0x000404F8 是两条指令：ldi:32 #0x404DE, r13 加 jmp @r13， 而 0x404DE 是 borh #8, r13 接 bra *-2 —— 一个原地自旋的死循环。 也就是说 B 段的设计意图是「没接的中断一旦误触发，就停在那儿」，不是静默返回。

A 段那 46 条接线中断里，0x10 到 0x33 这一段处理程序地址几乎是等间距的（相邻相差 0x32 字节）， 是典型的中断桩表：每个桩只做「压栈、记下自己是几号中断、跳到公共处理」。B 段则是各中断各写各的， 处理程序散落在 0x42xxx（内核区）、0x12Dxxx/0x12Fxxx（驱动区）、0x172xxx/0x1A5xxx（应用区）。

三、μITRON：不猜服务号，直接读固件自己的表

上一版的 μITRON 层是「服务号 → 查社区那份名称表 → 直接返回成功」。这其实有个隐患：万一服务号偏了一位， 或者那份表和这份固件的版本对不上，整个分析就建立在一个错的前提上，而它不会报错。

这次找到了固件自己的派发方式。A 段的 μITRON 陷阱入口在 0x000FE3C0，B 段在 0x00040668， 两处代码结构一模一样：

    lsl   #1, r12            ; 服务号 × 2 → 字节偏移
    ldi:32 #0x000FE3B8, r13  ; 表尾地址（B 段是 0x00040660）
    lduh  @(r12, r13), r12   ; 取 16 位「相对表尾的偏移」
    extsh r12                ; 符号扩展（偏移可以为负）
    add   r13, r12           ; 目标 = 表尾 + 偏移
    call  @r12

于是服务号是负数、从 -1 往下数，表尾就是基址 —— 和之前从调用点反推出来的口径完全一致。 把表整张倒出来：

段表尾槽数真实现指向桩
A0x000FE3B817618158
B0x0004066017656120

两个桩就贴在表尾前面，各两条指令，ret:d 加一条往 R12 塞错误码的延时槽指令：

000FE3B8  9F20      ret:d
000FE3BA  CEFC      ldi:8 #0xEF, r12     ; 有符号 = -17
000FE3BC  9F20      ret:d
000FE3BE  CECC      ldi:8 #0xEC, r12     ; 有符号 = -20

按 μITRON 标准错误码表，-17 是 E_PAR、-20 是 E_NOMEM。但固件里没有直接证据说明它为什么挑这两个码， 所以这里只当「未实现的服务返回负数」看，不当成「这里报了参数错误」。

一个能自证的数字

A 段只实现 18 个服务，B 段实现 56 个。把两个集合对一下：

  • A 的 18 个，全部落在 B 的 56 个里面，一个不漏（A − B = 空集）；
  • B 多出来的 38 个，恰好是定时器（cyc/alm）、内存池与块、信号量、邮箱、任务挂起/恢复、 调度器开关、版本与系统信息这一整批；
  • 之前从光圈函数里实测到的 4 次服务调用（clr_flg×2、wai_flg、sta_tsk）， 4 条全在 A 的 18 个实现里。

如果服务号偏了一位，这三条同时成立的几率极低 —— 尤其「子集关系」这一条，错位之后必然被打断。 所以这次可以说：服务号编号已交叉验证

四、真跑一条中断：串口 ISR 到底通知谁

有了中断机制，就能把某条中断单独拉起来跑，还能往直接页寄存器里喂值看它走哪条分支。 IRQ 0x1B（Serial IF0）的入口是 0x0012FDB4，它做判断的方式很简单： 读直接页 0x60，和 0xE0 做与，为 0 就直接返回。

喂给 0x60 的值步数峰值栈读的外设μITRON 调用
0x003160 B0x60, 0x61无
0x20 / 0x40 / 0x80 / 0xE0 / 0xFF3160 B0x60, 0x62sys_set_flg(flag=3, pattern=0x20)

读清楚了：这条串口中断只要看到状态位非零，就置「事件标志 3 的第 5 位（0x20）」，唤醒在等这个标志的任务； 状态位是 0 就一声不响地返回。等它的是谁，还没往下跟。

另一条 IRQ 0x20（EXT9）的入口 0x0012FE54 走的是另一套：从 0x9F58DA85 读一个字节当索引、 左移 2 位、加到 0x1BC480 的函数指针表上再 call，最后往直接页 0x38 写 0xFB 清中断。 和之前从静态分析得到的口径对得上。

五、意外收获：一条 binutils 表里没有的指令

把 48 条中断逐条拉起来跑，IRQ 0x3F 卡住了：0x00040E20 处的字节解不出来。 那个字节是 97DD。查 NikonEmulator 的实现，这个族被明确标了注释：

/* SRCH0 Ri */  // FR80/FR81 only
/* SRCH1 Ri */  // FR80/FR81 only
/* SRCHC Ri */  // FR80/FR81 only

也就是说 binutils 的 fr30 指令表只覆盖 FR30，而 D300 用的是 FR80 —— 差的那几条就是位检索指令。 补进去之后：

  • 编码空间的可解码数从 64634 涨到 64682（多了 48 个编码），助记符从 119 种涨到 122 种；
  • 未定义编码从 902 降到 854；
  • IRQ 0x3F 从「跑到 0x40E20 卡死」变成「41 步跑完 reti」。
一个没定下来的地方：参考实现里 bitSearch 的循环只走 31 次，漏掉了最低位。 遇到「只有 bit0 匹配」的输入，它返回 32（等于"没找到"），而按「从最高位起第一个匹配位的序号」这个定义应该返回 31。 本实现按后者写，并在代码里标注了这个分歧。哪个对得上真机，目前没有证据 —— 不猜。 这条只影响 SRCH 的极端输入，对上面所有结论没有影响。

说明：跑的条件是「RAM 全 0、外设读一律返回 0、遇到服务调用立即返回」。这套条件下能跑完，说明处理程序本身的控制流是通的； 不代表接了真实外设之后还一样。复位入口和异常处理不返回是设计如此，不算失败。

上一次的结论也回归过一遍，没有被推翻：1.10 / 1.11 各跑 2 组，步数仍是 552 / 608 / 596 / 664， 256 种标志位取值扫描仍是「1.10 两种走向、1.11 四种走向」，三个行程常量 7812 / 17578 / 17969 一个没变。

七、还差什么

  • 外设还是假的。直接页 0x0–0xFFF 读一律返回 0，写只记日志。0x60、0x62、0x38 这些地址已经知道「有语义」，但不知道「什么条件下是什么值」——那需要示波器级别的时间模型，或者厂商文档。
  • 调度器没跑起来。IRQ 0x40（内核陷阱本身）单独拉起来会一直往下跑、栈越堆越高，这是正常的： 它期待的是「切到另一个任务」，而仿真台里只有一个任务。要跑通得把任务表和就绪队列一起建模。
  • 0xBE00–0xBEFF 这一整块 256 个编码，两份参考实现里都没有定义。B 段里有 1353 个字以 0xBE 开头， 但多数看着像数据。目前跑过的代码路径一次都没碰到它。
  • A 段向量 0x01 指向 0x07000000，落在镜像之外。仿真台没有那段内存，判断不了它是外设区还是没初始化的槽。
