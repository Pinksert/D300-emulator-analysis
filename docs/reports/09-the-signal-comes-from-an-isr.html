D300 固件 · 那个信号是从中断里来的

先量出仿真里固件到底跑了多少代码，再顺调用图找到断点，最后不用任何补丁、只补中断，把显示管线往前推了三级 · 2026-10-24
一句话结论：上一轮说"没有任何代码会置 flag 3 的 bit4"——这句话是错的。 静态代码里有 4 处 set_flg(3, 0x10)，它们全部住在中断服务程序分发的一张 25 项函数指针表里（基址 0x001BC480）。驱动这张表的是两个中断： IRQ 0x1B（串行口 0）和 IRQ 0x20（外部中断 9）。 不打任何 flag 补丁、只把这两个中断打进去，显示管线自己往前走了三级， 第一道握手 1195 次全部通过，显示文本缓冲里第一次出现了固件自己写进去的字节。

把这 199 个跑过的函数和静态调用图叠在一起，就能列出"某个函数明明跑了， 它调用的某个子函数却一次都没进"的位置——这就是执行流断掉的地方。

三条值得记的：

  • 0x1200AC（开机总装配）调用了 0x175186 但没进去——按键处理任务（任务 6）压根没被拉起来。
  • 0x13822A 会调用 0x242B96，那个地址正落在任务 21（0x242DA0）的范围内——也就是我们一直想接上的那个下游。
  • 0x12DFAE（显示管线）后面的三段全是 0，和上一轮看到的一致。

三、bit4 到底是谁置的：两张中断分发表

静态扫一遍所有 set_flg 的调用点，flag 3 上一共 44 处， 里面有 4 处写的正是 0x10：

0x0012F794   0x0012F964   0x0012FB10   0x0012FDB0
  └ 0x12F77A   └ 0x12F952   └ 0x12FAEA   └ 0x12FD9E   （所在函数入口）

顺着这 4 个函数往回找调用者，结果是一个静态调用者都没有—— 不是没人调用，是它们通过函数指针表被间接调用。把它们的地址拿到固件里反查， 全部命中同一片区域：

0x1BC490: 0012F778 0012F77A 0012F798 0012F7DC     ┐

0x1BC4B0: 0012F968 0012F9C0 0012FA1C 0012FA3E     │ IRQ 0x1B 用（21 项）
0x1BC4C0: 0012FA90 0012FAEA 0012FB22 0012FB76     │
0x1BC4D0: 0012FBC6 0012FC52 0012FCA6 0012FCF6     │
0x1BC4E0: 0012FD9E                                ┘
0x1BC4E4: 00020103  25 33 64 20 20 25 33 64 …     ← "%3d  %3d" 格式串，表到此为止
位置关系很整齐：上一轮解出的显示对象描述符表是 0x1BC020 起 70 条 × 16 字节， 正好到 0x1BC480 结束；这张 25 项的处理函数表紧接着就排在它后面。 表尾紧跟 printf 的格式串 "%3d "、"%2d "、"%10d"。

再往前追一步，找到索引这张表的代码——两段以 RETI 结尾的函数， 确认是中断服务程序：

把两个 ISR 的地址拿去反查中断向量表，得到确切的中断号：

0x1B（Serial IF 0 共享）0x000EFF900x0012FDB40x001BC4900x9F58DA8621

这就是答案：显示管线死等的 bit4，由串行口 0 的中断服务程序按状态字节 0x9F58DA86 分发到某个处理函数、再由那个处理函数 set_flg(3, 0x10) 置起来。 它是一个硬件事件，不是"固件里少了一段代码"。 上一轮我从运行时日志里看到"没人置过 bit4"，就推断成"没有代码置"——那是把"没执行"当成了"不存在"。

四、只补中断、一个补丁都不打

既然卡点是中断没来，那就不碰 flag，只往中断控制器里打请求， 并且在 CPU 接受后立刻撤销（模拟边沿触发，否则会像上一轮的按键实验那样无限重入）。

给两处判定点各加了一个取值直方图，读的是 flag3 & 0x74：

0x12E404 取数据后    读到 0x04   x1195   （卡住）

第一道握手 100% 通过，一次没失败。而且显示文本缓冲里第一次出现了固件自己写进去的字节：

idx=4  0x12F778  x1        idx=5  0x12F77A  x1195     idx=24 0x12FD9E  x1195

五、剩下那道坎：OR 等待 + 中断时序

第二道握手过不去。原因是 twai_flg(3, 0x74, wfmode=2) 是OR 等待—— bit2 / bit4 / bit5 / bit6 里任意一个先置位，等待就结束。返回后代码判的是 (flag3 & 0x74) == 0x10，也就是"必须恰好只有 bit4"。

真机上，一次串行事务里的几个中断会连着来，任务没机会插进来， 等它恢复时状态机已经走完，看到的正好是 0x10。仿真里中断是一步步"喂"的， 任务被调度回来时状态机才走到一半，于是读到中间态：

mode 3  周期 5000  -> 读到 0x04  x1195      （bit2 先到：IRQ20 的处理函数 0x12FE20 置的 0x06）
mode 9  周期 2000  -> 读到 0x24  x5         （bit2 + bit5）
mode 10 周期 10000 -> 读到 0x20  x1         （bit5：处理函数 0x12F82C 在 0x12F882 置的）

试了几种更接近硬件的喂法：

  • 状态驱动（状态字节非 0 才发中断）：IRQ20 发疯——0x9F58DA85 一旦被置成 2 就再也没人清它，9 万次中断把显示任务饿死了。
  • IRQ1B 单独状态驱动：只发得出 9 次，管线连第一道都没到。
  • 电平触发（状态非 0 就一直挂着中断，让 CPU 反复进 ISR 直到状态机跑完）： 状态机确实连着跑，但第 9 号处理函数 0x12F9C0 在 0x12FA06 处 自旋死循环，第 304 万步就停在那了。它等的是串口的状态位， 我们的 UART 旁路给不出它要的时序。
所以剩下的差距不是"缺代码"，是"缺波形"：要把串行口按真实波特率一位一位地把字节 收发出去，让 0x9F58DA86 这条状态机在正确的时间点被正确的中断推着走完。 这条路要做的是给模拟器补一个带时钟的串行模型，不是再去找什么隐藏分支。

0x61 是发送出去的字节（DMOVB R13,@0x61）， 0x62/0x63 在重置时被写成 0x00 和 0xB8， 0x38 被写成 0xFB（清中断）。 0x64 读不出来（模拟器没映射），ISR 的错误分支会去动 0x62 的低位。

七、修正上一轮的一处结论

勘误上一轮写的是"整个 B 段没有任何一处 set_flg 会置 bit4"。 按运行时日志看确实如此，但静态代码里有 4 处： 0x12F794、0x12F964、0x12FB10、0x12FDB0。 它们没在日志里出现，是因为它们所在的中断服务程序一次都没被执行， 不是因为它们不存在。

顺带一条：这 4 处的存在，反过来印证了上一轮的另一个判断是对的—— 这个信号确实是从硬件来的，只是"硬件"具体是串行口中断，现在可以说死了。

  2. 接任务 21：0x13822A 会调用 0x242B96，落在任务 21（0x242DA0）范围内， 那是"绘制"通知的下游。
