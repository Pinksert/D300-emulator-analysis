D300 固件 · μITRON 系统调用表

把两台 CPU 各自的系统调用入口、编号、名字和调用次数全解出来 · 2026-10-15
一句话结论：D300 的 A、B 两个处理器各自跑一份 μITRON， 用同一套系统调用编号，但内核被裁成了两种尺寸—— 主控（B 段）实现 58 个服务、实际用到 21 个； 协处理器（A 段）只有 20 个实现、用到 17 个， 而且没有信号量、没有延时服务。 两端加起来，调用最多的都是事件标志：set_flg 与 clr_flg。

一、怎么找到的

线索是一句官方说明没有、但固件里到处都是的指令：INT #0x40。 它是 μITRON 的系统调用陷阱（software trap）。顺着它往上追三级，就能把整张服务表解出来。

第 1 级：中断向量表

实跑时我们已经测出 TBR = 0x000EFC00（复位代码里 LDI:32 #0x000EFC00,R0 / MOV R0,TBR）。表是 4 字节一项，共 256 项：

  • 208 项指向同一个兜底 0x000404F8（跳到一句 RET）
  • 48 项指向各自的真实中断处理函数
  • #255 = 0x00040000 —— 复位地址

表是倒着排的：中断号 n 的表项在 TBR + (255-n)×4。 所以 INT #0x40（n = 64）对应 #191， 表里写着 0x00040668。

第 2 级：系统调用分发器

反汇编 0x00040668，是一段标准的 RTOS 分发器：

00040668  ST      R14,@-R15
0004066A  ST      RP,@-R15
...         压栈、保存现场（STM0/STM1 存 R0-R14、MDH/MDL、RP）
000406A4  LSL     #1,R12            ; R12 = 服务号 × 2
000406A6  LDI:32  #0x00040660,R13   ; ★ 分派表基址
000406AC  LDUH    @(R13,R12),R12    ; 取 16 位偏移
000406AE  EXTSH   R12               ; 按有符号扩展
000406B0  ADD     R13,R12           ; 目标 = 基址 + 偏移
000406B2  CALL    @R12              ; ★ 跳进服务实现
000406B6  ...     返回后处理
000406BE  EXTSB   R12               ; ★ 返回值放在 R12（错误码）
000406E2  RETI

要点：服务号放在 R12，是一个负数（8 位有符号）； 表基址 0x00040660 其实是这张表的末尾， 所以索引是往回走的；返回值也从 R12 出来。

第 3 级：176 个服务号

按 target = 0x40660 + int16(0x40660 + 2n) 把 n 从 −176 到 −1 全算一遍：

  • 176 个服务号算出来的目标全部落在固件地址范围内，零个越界——模型成立
  • 去重后是 58 个不同的实现地址（大量服务号指向同一个"未支持"桩）
  • 对照 NikonEmulator 自带的 D300S 配置文件里的 102 条符号， 176 个服务号 100% 都对上了名字，一个没落空

两个独立佐证

① 仿真器源码里的常量
ITron3.java 写着 SYSCALL_NUMBER_SET_FLG = 0xD0、 CLR_FLG = 0xD1、 REF_TSK = 0xEC。 而我们实测调用次数最多的三个号， 正是 0xD0、0xD1， 0xEC 也确实解出 sys_ref_tsk。
② A 段向量表的默认值
A 段向量表默认填充 0x000FE250 ×210， 与我们之前靠"未用中断填什么"判代际时记下的 D300 填 0x000FE250 共 210 条完全吻合—— 两条独立路径对上了同一个数。

三、协处理器（A 段）的那一份

A 段也有自己的向量表（0x000FFC00）和自己的分发器 （0x000FE3C0），结构与 B 段逐条同构：

000FE3C0  ST      R14,@-R15
000FE3C2  ST      RP,@-R15
000FE3EE  LDI:32  #0x000FE3B8,R13   ; ★ A 段的分派表基址
000FE3F4  LDUH    @(R13,R12),R12
000FE3F6  EXTSH   R12
000FE3F8  ADD     R13,R12
000FE3FA  CALL    @R12

同样 176 个编号，同样零越界，但去重后只有 20 个实现地址—— 比 B 段的 58 个少了一大半。实际调用 841 次（可解析的），分布在 17 个服务：

★ 最值得注意的一点：A 段的内核被裁掉了整类功能

把两段的清单并排看，差别不是"用得多用得少"，而是根本没有：

  • A 段没有信号量 sig_sem / wai_sem / preq_sem 在 A 段的分派表里 全部指向同一个"未支持"桩 0x0FE3B8，代码里也一次都没调用
  • A 段没有延时服务 dly_tsk、tslp_tsk 同样未实现； A 段要睡觉只用 slp_tsk（无超时），B 段则用带超时的 tslp_tsk 136 次
  • A 段才有中断级管理 chg_ilm / ref_ilm 只在 A 段被调用（20 + 9 次）， B 段一次没用
  • A 段用了消息队列 snd_msg 7 次；B 段清单里没有

换句话说：协处理器那颗核的任务同步只靠事件标志， 不需要互斥、也不需要超时等待——这与它负责 IO 驱动的定位是一致的。

四、顺带确认：D300 与 D300S 的内核是同一份

这次能给 176 个服务全部命名，靠的是 NikonEmulator 仓库里那份 D300S 的配置文件 （b810101b.dfr.txt，102 条符号）。 对照结果是逐一吻合，例如：

服务号我们独立算出的 D300 实现地址D300S 配置里的符号
0xAB0x040F1Asys_dly_tsk
0xDB0x04137Esys_tslp_tsk
0xE90x0414C8sys_sta_tsk
0xEC0x0417ECsys_ref_tsk
0xF50x040660sys_unsupported_function
两边地址完全相同，说明这两台机器共用同一份 μITRON 内核、放在同一个位置。 但应用层不同：同一个配置文件里还标了 39 个任务入口（task_0x01–task_0x27） 和任务表 tblTaskData @0x63EF0。 内核同址、业务各异——正合"同一平台、不同机型"的预期。
2026-10-15 修订（两处，都是这次才查清的）
  • ①「39 个一个都没命中」说错了，实际是 38 个没命中、1 个命中。 逐条实测：D300S 的 task_0x02（/* Autorun */，入口 0x1200AC）在 D300 里一字不差地存在，位于 0x054C2C； 其余 38 个在 D300 里找不到同值。也就是说这两台的任务编号顺序一一对应，代码位置各自不同， 只有 Autorun 这一颗是原样搬过来的。上一版的"一个都没命中"属漏检，已作废。
  • ② D300 自己的任务表不在 0x63EF0。 直接读内核代码里的常量：sta_tsk / ext_tsk / ter_tsk / rot_rdq / get_tid / ref_tsk 六个服务的第一条实指令都是 ldi:32 #0x00054BFC, R14； 而 set_flg / clr_flg / wai_flg / pol_flg 四个都是 ldi:32 #0x000551B0, R14。 → D300 的任务表基址 = 0x00054BFC，事件标志表基址 = 0x000551B0； D300S 的 tblTaskData 写的是 0x63EF0，而 D300 里那一片全是 FF。 内核代码同址，数据表不同址。

五、边界：哪些别写死

  • 调用次数是"静态"的：数的是反汇编里出现了多少次调用指令， 不代表运行时真的每次都走到。真实执行频率要靠跑起来才知道。
  • 数据区会有误判：全段线性反汇编会把数据里的同形字节也当成指令。 B 段 2297 处里有 427 处读不出服务号，A 段 1002 处里有 161 处，这些已排除； 但剩下的里面仍可能混有少量假命中。
  • A 段的服务名是"借用"的：A 段自己的分派表我们解出来了（176 项零越界）， 但它没有配套符号表，名字是沿用 B 段已确证的编号体系。 依据是两端编号结构完全一致（连"未支持"桩的位置都同构），属于强推断，不是直接标注。
  • 服务号是负数这件事由分发器代码推出（EXTSH 之后 ADD），并由"176 项零越界"反证；没有第二份文档可比对。
  • 没验证的：每个服务内部做了什么、各任务的优先级与栈大小、 D300 与 D300S 内核是否逐字节相同（只验证了入口地址相同）。

六、复现方法

  • 全段反汇编：Dfr（NikonEmulator 自带） -x conf/d300_b_full.dfr.txt -o out.asm B3000111.bin， B 段 7MB 只要 5 秒
  • 脚本：.workbuddy/tmp/scan_svc.py（找 INT #0x40 与 R12 装载）、 svc_table.py（解分派表 + 套符号 + 统计）
  • 产物：svc_table.json（176 个服务号→地址→名字）、 svc_calls.json（两端调用统计）
