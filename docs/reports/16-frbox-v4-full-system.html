仿真台 V4：把「能跑一个函数」做成「一台机器」

D300 固件全系统模拟器 frbox 0.4 · 2026-10-29
一句话：前三版解决的是「CPU 算得对不对」，这一版解决的是「机器装不装得起来」。 新增 13 个文件、约 2,072 行，把单个 CPU 核心包成地址空间 + 设备 + 中断控制器 + 机器 + monitor + 启动参数六层， 命令行对齐 QEMU 的肌肉记忆（-M / -kernel / -S / -d / -D / -c）。

三、两台机器：内存映射从哪来

D300 不是一个 CPU 加一份固件，而是至少 A（IO 协处理）+ B（主控）两套独立子系统，各有自己的固件、 自己的向量表、自己的 RAM。所以建的是两台机器，而不是一台机器两个核。

（A3000111.bin 全长，含末 2 字节 CRC）		 0x00001000–0x0007FFFF
520,192 字节		0x000FFC000x000FC000
d300-b0x00040000 + 7,340,032 字节

每条数字的来源都不是猜的，是固件自己的行为：ROM 基址与长度 = 镜像文件大小；TBR = 向量表所在 （A 段槽 0x000FFFFC 读到 0x000FC000、B 段槽 0x000EFFFC 读到 0x00040000）；RAM 上界 = 固件真正写过的高地址。

B 段那块 1MB「新 RAM」是怎么发现的

第一轮跑 B 段时，总线上出现 59,183 次写入无处可去。按 4KB 页汇总一看，写集中在两处： 0x9F58C000 起 1307 次、0x9F5AA000–0x9F5AF000 五页共 5120 次（步长 4）。

这不像「未映射」，更像把 0x9F58xxxx 当 RAM 在用 —— 而且早先静态分析里，串口 ISR 读 0x9F58DA86、EXT9 ISR 读 0x9F58DA85，正好落在同一片。于是把 0x9F580000 起 1MB 映射成第二块 RAM，未映射写从 59,183 次降到 3,868 次：

指标补之前补之后
未映射写次数59,1833,868
未映射写地址数58,4833,868
剩余写落在0x9F58C000 一带、0x68000000 一带0x68000000 一带 3,743 次（96.7%）
其余 125 次散在 27 个页

那 125 次散落的写值得单独说一句：主要在 0x4000D000（12 次）、0x50000000（26 次）、 0x40060000–0x401F0000 之间（约 70 次，横跨 2MB）、0x9F800000（4 次）。 0x40000000 起那 2MB 窗口像是某种「别名窗口」（写进去不报错、读回来也不影响流程）， 没有文档就只能记成痕迹，不能当 RAM 用。

顺带确认了一件事：0x9F58xxxx 是主控的数据 RAM，不是外设。这也解释了为什么早先的 ISR 实验里 ldub @0x9F58DA86 一直读到 0 —— 那块 RAM 当时根本不存在，读的是「未映射」。

四、启动诊断：四组实测

判定「跑不下去」分三种形态，必须分开记：停机（CPU 自己 halt）、起飞（PC 离开 ROM 区）、 自旋（连续 20 万步都在同一 4KB 窗口里）。

其中 200,000 是空转		61

4.1 A 段：它在等一个握手位

卡点只有三条指令，全在 ROM 最前面：

0x00080078: ldi:20 #0x482, r0        ; r0 = 直接页 0x482
0x0008007C: btsth  #8, @r0           ; 测 (0x482 & 0x80)
0x0008007E: beq    0x00080078        ; 零 → 跳回去再测
位掩码这里容易搞错：btsth #8 不是「测 bit0」，也不是「测 bit3」， 而是把 4 位立即数当高半字节 —— 掩码 = 8 << 4 = 0x80。 所以它等的是 0x482 的 bit7。这一位我是从 fr30.cpu 里 (sll QI u4 (const 4)) 核对的，不是靠猜；改之前我先试过打 0x08，纹丝不动，正是这个原因。

而固件自己在进入这个循环之前，已经把 0x482 写成了 0x08（就在 0x80044 那一段里）。 所以它是在「我先报个到，等你把 bit7 举起来」—— 典型的跨芯片握手。0x482 是直接页寄存器， 谁来回这一位在我们的模型里是空的，所以只能空转。

用 --latch 0x482=0x88:2（第 2 次读之后返回 0x88）假装对方举手，A 段立刻往下走了 41,565 步、碰到 824 个不同 PC，然后在 0x000FE50C 的 reti 处把 PC 恢复成 0。

4.2 B 段：跑到 191,518 步，卡在一次上下文恢复

B 段的路更长：先做了大段结构体初始化（能看到 12 字节步长的填充循环），执行了一次 int #0x40（服务号 R12 = 0xAD，即 −83，社区表里是 sys_set_tim）， 进入内核窗口 0x406xx，最后停在 0x407D8 的 reti。收尾这几条长这样：

0x000407CC: ld    RP,@r15+          ; 弹返回地址进 RP
0x000407D2: ldm0  {r8..r15}         ; 批量弹寄存器
0x000407D4: ldm1  {r0..r7,r12..r15}
0x000407D6: andccr #0xDF            ; 清 S 位 → 切回系统栈
0x000407D8: reti                    ; 弹 PC 与 PS
先排除「是不是解释器算错了」：我在 reti 之前直接把栈读出来看 —— B 段 r15 = 0x00008448，栈顶 8 个字全是 0；A 段 r15 = 0x000461B4， 栈顶 8 个字也全是 0。也就是说 reti 读到的「返回地址」就是 0， CPU 老老实实跳到 0，没有算错。是栈上那个上下文帧本来就是空的。

两台机器的形态完全一样：都是「清 S 位 → 批量弹寄存器 → reti」，都发生在各自的内核窗口里 （A 0xFE3xx–0xFE5xx，B 0x406xx–0x407xx），都是把 0 弹进了 PC。这不是两个 bug，是同一个：第一次任务上下文恢复时， 被恢复的那份上下文是空的。半主机模式（--itron）下结果一模一样，也说明不是内核代码本身跑歪， 而是它要去恢复的东西不存在。

五、这一版新增的两个调试手段

命令作用为什么需要
--poke ADDR=VAL[:SIZE]复位后往任意地址写值，未建模寄存器也有影子存储接着模拟「上电时某个外设已经是某个状态」
--latch ADDR=VAL[:N]该地址第 N 次读之后返回 VAL静态打值会被固件自己覆盖（0x482 就被写成 0x08），握手必须能「过几拍再响应」
audit未映射访问按 4KB 页汇总，带页码与样例地址就是它把 0x9F58xxxx 那片 RAM 找出来的
自旋检测连续 20 万步不出某个 4KB 窗口就停下并报告否则「等外设」和「真在算」看起来一样，都是满速跑

六、设备模型的可信度分级

这部分必须说清楚，免得把推断当实测：

设备可信度依据 / 缺口
串口有实证 ISR 在 0x0012FDB4：读 0x60，(值 & 0xE0)==0 直接返回，否则读 0x62 并 set_flg(3,0x20)。掩码 0xE0 是实测，三个位各自叫什么（ORE/RDRF/TDRE）是推断
中断控制器有实证 只绑两条：线 0x1B → 串口 ISR、线 0x20 → EXT9 ISR，都是从向量表读出来的。其余不猜
重载定时器推断 D300 固件里没能把某条向量反查到「这是定时器」，所以默认不绑向量； 寄存器布局按 FR 系列常见重载定时器摆，只当时间源用
直接页其余地址影子 读回上次写入的值、默认 0；B 段一共摸过 52 个这样的寄存器，最热是 0x042/0x043/0x03A/0x03B（各 7–8 次）
0x50000000 / 0x68000000 / 0x4000D000空白 读返回 0、写丢弃，但逐地址记账；没有语义就去猜等于造假数据

八、跑不起来的三件事（按重要性）

1. 任务上下文是空的

两台机器都停在「第一次任务上下文恢复」。μITRON 服务只观察到 1 次调用（sys_set_tim）， 没有 cre_tsk / sta_tsk。要么任务创建走的是不经过 int #0x40 的内部路径（那就是我们还没跟到的代码）， 要么任务控制块建在我们没建模的地方。下一步应该绕着「谁写 TCB」而不是「谁恢复 TCB」去查。

2. A 段等的那一位没人举

0x482 的 bit7。这一位要么由 B 段写（跨芯片握手），要么由某个外部芯片写。要判是哪种， 得把两台机器放进同一个地址空间跑，让 B 真的去写 A 的 0x482 —— 也就是把「双机」做成一台真正的异构机器。

3. 三处外设窗口语义空白

0x50000000 / 0x68000000 / 0x4000D000。它们都不在固件的 RAM 或 ROM 里，只能是外设。 没有厂商文档或示波器就推不出来，我不打算猜。
