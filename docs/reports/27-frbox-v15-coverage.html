一句话：V15 干了两件事。一是给模拟器加了一把尺子 —— 每条指令执行时在 1.8 MB 的位图里点一下，于是「哪段代码从来没跑过」第一次可以被问出来； 二是顺着这把尺子把 V14 的一条结论推翻重写：任务 8 能被拉起来， 跟我们喂不喂事件位图没关系，真正起作用的是那两个中断向量。

一、先更正：位操作的立即数是「掩码」，不是位号

V14 记过一条怪事，还把它列成了未解之谜：0x0AD652 明明写的是 btstl #2, r0，可是逐位去喂 0x90，只有 bit1 能放行。 当时的解释是「立即数与位号不是一一对应，只能逐位实测」。

其实没有怪癖。FR30 的 BANDL / BORL / BEORL / BTSTL 是对 @Ri 指向的那一个字节做操作，#u4 是低半字节的掩码； 带 H 的版本是高半字节掩码（真掩码 = u4 << 4）。 拿 NikonEmulator 的 Java 指令表对照，BANDH 的注释写得很直白：

// AND'ing only the highest 4 bits with xxxx is like AND'ing the byte with xxxx1111
context.memory.store8(reg, load8(reg) & ((imm << 4) + 0x0F));

所以 btstl #2 测的是 bit1（掩码 0x02）， btsth #4 测的是 bit6（掩码 0x40）， btsth #8 测的是 bit7（掩码 0x80）。 模拟器 CPU 一直是按掩码实现的（fr_emu.py 里 mask = g("u4")）， 错的是我们读反汇编的方式。新加的 frbox/bits.py 把这件事固化成函数： B.bits("btsth", 4) → [6]。

更正 1：V14 表里的「vec13 → 位图 bit4」「vec19 → 位图 bit8」是按位号读的，实际是 「vec13 → 字节 0x41A56 的 bit6」「vec19 → 字节 0x41A56 的 bit7」。 位号没变过，是我们把掩码当成位号，自己把编号搅乱了。

二、再更正：「bit4 + bit8 必须同时置」不成立

V14 的头条结论是「位图 bit4 与 bit8 必须同时置，固件才会 ref_tsk → sta_tsk(8)」。V15 用 16 次单喂 + 1 次不喂重做了这件事 （results/frbox/bit-matrix.txt，每次 20 万步）：

不喂     服务32   位图 0x0020  自置0x80:否   T4×1@0x8C7F4, T8×1@0xACB2C, T9×1@0x81542
bit0   服务32   位图 0x0021  自置0x80:否   T4×1@0x8C7F4, T8×1@0xACB2C, T9×1@0x81542
...
bit14  服务31   位图 0x4020  自置0x80:否   T4×1@0x8C7F4, T8×1@0xACC16, T9×1@0x81542
bit15  服务69   位图 0x8020  自置0x80:否   T4×1@0x8C7F4, T8×1@0xACB2C, T9×1@0x81542

不喂位图，任务 8 一样被 sta_tsk。 真正的前提是把 vec 0x13 与 0x19 两个中断打出去 —— V14 的「基线」只打了 0x23，两个回调根本没跑，于是把「回调跑了」误认成了「位图位对了」。 16 位里任意一位都能拉起任务 8，可见那一位不是条件。

位图真正的作用是选路：

位图 bit现象
bit14（0x4000）sta_tsk(8) 改从 0x0ACC16 发出（V14 记成「位图全置时换入口」，其实只要这一位）
bit15（0x8000）服务调用 32 → 69，明显是另一条更长的通路
其余 14 位与不喂完全一致
更正 2：V14 表里的「任务 8 入口 0x0ACB2C / 0x0ACC16」也不是入口。 Flow 记的 c[1] 是 int #0x40 的调用点 PC， 这两个地址正是两处 sta_tsk 指令本身。任务 8 在任务表里的真入口是 0x0ACC32（覆盖率确认它被执行过）。

三、新能力：覆盖率

做法土但够用：CPU 每执行一条指令，把 (pc - 0x80000) >> 1 在一个 bytearray 里置 1（512 KB 的 A 段 → 262,145 个槽）。 代价是一条指令「两次比较 + 一次字节写」，1.8 MB 内存。

用途不是刷百分比（ROM 里混着字符串和表格，分母没意义），而是反向找洞： 哪些 ≥64 字节的连续区间一条指令都没执行过 —— 那就是「还缺哪块硬件」的清单。

反直觉的一条：事件给得越多，踩到的代码不一定越多。 B 只有一路 vec 0x23，却踩了 6,119 个地址；C 多打了两路中断，只剩 2,764。 原因是任务 9 在 B 里跑的是「一路往下走」的初始化路径，到 C 里被别的事件打断， 改成在几个等待点之间转圈。「服务调用更多」「覆盖更广」「任务更多」是三件事，不能互相代替。

四、顺着尺子找到的一件事：任务 4 被同优先级的任务 8 饿死

任务 4 的状态字是 0x00000000（就绪）、PC 停在入口 0x08C486， 可是入口那条指令一次都没执行过，ext_tsk 也是 0 次。 把就绪队列倒出来就明白了（probe/exp_ready_queue.py）：

就绪位图 0x45984 = 0x10800000 → 优先级 [8, 3]
槽 3  head=0x045B30(任务8) tail=0x045A80(任务4)
其余 12 个槽 head=tail=槽自己（空环，和 V11 的结论一致）

任务 4 和任务 8 在同一个优先级槽里排队，任务 8 是队头而且在 0x0AD652 死等 0x90 —— 一个纯忙等环，从不让出 CPU。同优先级的轮转让不到后面那个。

V14 逐位实测过：0x90 只有 bit1 能放行。于是做三组对照 （probe/exp_task4_unblock.py，各 20 万步）：

喂 0x90服务调用任务 4 入口跑过任务 8任务 4执行地址
不喂32没忙碌 0x0AD654ready 0x08C4862,764
bit140是sleep 0x0ACE86退出（state 0x10）6,382
bit232没忙碌 0x0AD654ready 0x08C4862,764

放行之后任务 4 干了五件事，然后干净退出：

wai_flg  @0x08E63E    等一个标志
set_flg  @0x08E6B8    置一个标志
chg_pri  @0x08C5F4    改自己的优先级
set_flg  @0x08C600    再置一个标志
ext_tsk  @0x08C60A    退出
这是第一次让任务 4 真正跑起来。之前几版报的「任务 4 起来了」只是 sta_tsk 成功、状态字变成了 ready —— 它在队列里站着，一步没走。 覆盖率把这个区别变得可判定：状态字说「在队列里」，覆盖率说「跑没跑」。
