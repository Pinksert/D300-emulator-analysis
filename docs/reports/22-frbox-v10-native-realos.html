一、上一版的结论被推翻了，而且是被一条 orccr 推翻的

V2 到 V9 一共攒下八个版本，结论一直是「A 段的 REALOS 内核进不去，只能自己做两件事：手工造任务上下文、 用 μITRON 半主机假装内核」。这句话是错的。内核一直都在固件里，完整无缺，只是 CPU 少做了一步—— orccr / andccr 改 CCR 的时候没有带着栈指针一起搬家。

FR80 的 CCR 里有个 S 位（bit5），它决定 r15 此刻指向的是 SSP 还是 USP。 S 位一翻，r15 必须立刻换到另一根上，并把旧值存回原来那根。中断返回走的 reti 一直做对了这件事（所以跑 ISR 从来没出过问题），ldm/stm 碰 /T 也做对了 —— 唯独 orccr 和 andccr 这两条是例外，老代码是这么写的：

# 修复前（fr_emu.py）
ccr = (ccr & v8) if mn == "andccr" else (ccr | v8)
self.s = (ccr >> 5) & 1          # ← 直接给 s 赋值，绕过了 ps 的 setter，r15 不换支
# 修复后
self.ps = (self.ps & ~0xFF) | ccr  # ← 走 setter，setter 里那一段会把 r15 在 SSP/USP 之间换支

为什么这一条足以让整个内核瘫痪？因为 REALOS 恢复任务上下文的那二十几条指令，就是靠翻 S 位在两个栈槽之间搬指针过日子的：

地址指令干了什么
0x0FE4DEldi:32 r0,#0xFE160取任务表第 13 条记录（空闲任务）
0x0FE4E4ld @r0,r14r14 ← 空闲任务的 TCB
0x0FE4ECst r14,@r0把当前 TCB 写回 *(0x45980)
0x0FE4EEld @(r14,0x18),r0TCB+0x18 = 这个任务保存的 SP
0x0FE4F2orccr #0x20S 0→1，r15 换到 SSP 槽
0x0FE4F4–0x0FE4FCld/st ×4在两个栈槽之间搬运 SP
0x0FE4F8andccr #0xDFS 1→0，换回来
0x0FE4FEorccr #0x20再换一次
0x0FE506–0x0FE508ldm0 / ldm1弹 r0–r7 / r8–r14
0x0FE50Aandccr #0xDFS 1→0
0x0FE50Creti弹 PS / PC，正式落到任务里
0x0FE510bra -1空闲任务的本体（原地自旋）

S 位不换支时，0x0FE4F4–0x0FE4FC 那四条访存全部打在同一个地址上搬来搬去， 最后 reti 弹出来的 PC 是错的 —— 表现出来就是「任务一起步就飞掉」。 把这一行改对，复位链一路跑到 0x0FE4DE，剩下的事固件自己全包了。

实测的 S 位切换现场（results/frbox/realos-run.txt 第 2 节）： 43,433 步 @0x0FE4F2 S 0→1（r15 0x04617C / SSP 0x04616C）→ 43,436 步 @0x0FE4F8 S 1→0 → 43,439 步 @0x0FE4FE S 0→1 → 43,445 步 @0x0FE50A S 1→0 → 43,446 步 @0x0FE50C S 0→1。 整个 boot 过程中 S 位只在这五处翻过，五处全在这二十几条指令里。

二、任务表不是 8 条，是 13 条

V9 留下一个悬案：sys_sta_tsk 里出现过 tsk_id 9 和 10， 可任务表按表头那个「8」去解，只解出 id 1–8。现在知道原因了 —— *(0xFE000) 那个 8 是「用户任务数」，不是记录总数。记录从 0xFE010 起每 0x1C 字节一条，一路排到 0xFE160，一共 13 条：id 1–12 加一条 id 0 的空闲任务。

这 13 条不是猜出来的：任务表和 TCB 是互指的两套账，TCB+0x24 恰好回指自己的那条表记录， 13 条全部核对得上；TCB+0x0C 的高 16 位恰好等于表里的属性值。任一侧读错，另一侧立刻对不上。

三、TCB 布局，以及「任务 1 入口 0x8133A」现在是固件写的事实

每个 TCB 0x2C 字节，13 个连号排开：

偏移内容V10 新看出来的东西
+0x00 / +0x04双向链表前驱 / 后继两个都自指 = 不在任何队列里；指别人 = 挂在这个对象上等着
+0x0C属性 << 16 | 状态字任务 1 跑起来后低半字是 0x0002
+0x18保存的 SP正在跑的时候就是它的活现场
+0x24回指自己的任务表记录13 条全对得上，这是两侧互校的关键

内核在启动阶段亲手摆好了三份初始上下文，压在任务自己的栈顶上：

0x0462EC  任务 1   [0x08133A, 0x001F0030, 0x000FE250]
0x0466B4  任务 5   [0x0A62FE, 0x001F0030, 0x000FE250]
0x04617C  任务 0   [0x0FE510, 0x001F0030, 0x000FE250]

首字等于表里的 entry，TCB+0x18 等于表里的 sp，逐字一致。 第三字统一是 0x0FE250，拆开看是：

0x000FE250: ldi:32 r13,#0x81338
0x000FE256: jmp   @r13

也就是内核给任务准备的「返回落地处」——任务如果 ret 出去， 会精准落到 0x081338 这条 bra -1 停机占位上。 以前「任务 1 入口 0x8133A、栈顶 0x462EC」是我们从表里读出来的推测，现在是固件自己写在内存里的事实。

四、不借助任何外部内核：任务 1 由固件自己跑了 30 万步

做法只有一步：在派发点 0x0FE4E6（r14 刚从任务表取到 TCB、还没写回当前 TCB 变量） 把 r14 换成任务 1 的 TCB，然后把 CPU 撒出去。其余全是固件自己做的。

1,888 次陷阱一次都没走 μITRON 半主机：这一次 svc_hook 是空的， int #0x40 老老实实进 ROM 的向量表 0x0FFEFC → 0x0FE3C0，由固件那套陷阱分发器处理。我们之前花了八个版本写的半主机， 现在只剩下对照用途。

五、还没做到的：任务切换

把「当前 TCB 到底被写过几次」这件事盯死，答案很干脆：

*(0x45980) 全程只被写了 1 次： 0x0459FC，来自 0x0FE4EC（首次派发）。

之后 30 万步一次都没改过。也就是说至今没发生过一次真正的任务切换。 原因不是内核不行，是现实不允许：

  • 任务 1 是唯一能跑的任务。别的要么还没被起、要么挂在 0x45990 那一带的对象上等着。
  • 任务 1 自己也不闲着，它反复「clr_flg → 干活 → wai_flg」， 每次等待都立刻满足，所以从不进入等待态 —— 内核没有任何理由把 CPU 让给别人。
  • 空闲任务的本体是 bra -1，就算切过去，从 PC 上也看不出痕迹，只能靠 TCB 变量判。

所以下一轮的墙非常具体：要有一个真实硬件事件把别的任务唤醒。在此之前， 任何「调度器跑起来了」的说法都是假的。

顺带更正两处旧信息（已同步进 KNOWN_ISSUES.md）： ① 任务表是 13 条不是 8 条，「tsk_id 9/10 找不到」这个悬案就此结案； ② 0x0AF/0x174/0x524 三处「置启动位→轮询完成位」是模型化的假设，不是从硬件手册读来的。 它们默认关闭（保住 V2–V9 那些基线），跑原生 REALOS 时才打开。

六、怎么复现

# 自检（V10 新增第 16 组，专门验原生 REALOS）
cd emu && python frbox_selftest.py      # 258/258
cd emu && python fr_selftest.py         # 63 条 CPU 断言，第 7 组就是那个换栈漏门

# 三份取证输出
python probe/exp_realos_chain.py        # 启动链 + 13 条记录 + 初始上下文
python probe/exp_realos_tcb.py          # TCB 布局 + 队列归属
python probe/exp_realos_run.py          # 任务 1 跑 30 万步 + 服务分布

# 交互式：realos 是这一版新加的命令
python -m frbox -M d300-a -c "realos; realos 1; cont 20000; realos"

realos 不带参数是列表（13 条记录的 TCB / 入口 / 栈顶 / 上下文 PC，当前那条打 ◀）， 带任务号是把内核改派给那个任务。固件路径现在按顺序找 FRBOX_FW_DIR → 仓库 data/ → 仓库里的 D300Update/， clone 下来有 data/ 就能直接跑。
