仿真台 V7：把 A 段的应用区真正跑起来

D300 固件 A 段（0x00080000 起 524,290 字节）· 四处空桩的证据链 · 任务入口定位 · 手工启动任务后的应用区实测
4版本一致的空桩
0x8133A任务 1 的函数入口
500应用区被执行到的 PC
120/120自检通过

一、先把结论摆出来

V6 说「内核对象建好了，缺的是启动调度器那一行」。这一版把那一行找到了，而且验证了它不是被改小、不是版本回退，而是从 1.02 起就一直是空的。同时做了一件此前没做过的事：跳过 REALOS，手工把任务的初始上下文造出来，让应用区跑起来——结果它真的活了。

  • 空桩确认：复位链第三跳 0x804FA 与 main 的第二条 call 0x80520，都是纯 ret，1.02 / 1.03 / 1.10 / 1.11 四个版本一字不差
  • 任务入口定位：任务定义表在 0xFE00C，任务 1 的函数入口 = 0x0008133A，第一句就是 stm1 r12,r13 的标准序言
  • 应用区是活的：手工跳进去之后 1,981 步就走到第一个硬件等待，期间走出 500 个应用区 PC、发起 10 次 μITRON 服务、自己写入了 6 个中断回调槽
  • 死锁的另一半通了：应用区确实会填回调表——只要它跑起来。之前「应用不跑→回调全空→中断无效→应用不跑」的闭环，断点在「任务从未被 sta_tsk」

二、空桩：不是版本差异，是设计如此

做法是从每个版本自己的复位入口解析 call 链，再反汇编目标处，这样地址不同也能对上。

版本复位段 call 链0x804FA 处字节main 第二 call 目标
1.020xF8010 → 0x80044 → 0x804FA → jmp 0xFE42697 20（ret）0x80520 = ret
1.03同上97 20（ret）0x80520 = ret
1.10同上97 20（ret）0x80520 = ret
1.11同上97 20（ret）0x80520 = ret

纠正之前的推测是「1.11 把这行改小了」。四个版本完全一致，这个推测可以撤掉。

main 的完整代码只有 5 条

0x804EC  ; 前一个函数 0x804F0 的尾部
0x804F0  ldi:8 #0x80, r0
0x804F2  ldi:20 0x240, r12
0x804F6  ret:d            ; 延迟返回
0x804F8  stb r0,@r12      ; 延迟槽：写 0x240 = 0x80
0x804FA  ret              ★ 一条孤立的 ret —— 复位链第三跳的目标
0x804FC  st r1,@-r15      ; main 入口
0x804FE  call 0x80506     ; BSS 清零（33,666 条指令）
0x80500  call 0x80520     ★ 也是一条孤立的 ret
0x80502  ld @r15+,r1
0x80504  ret
0x80506  ldi:20 0x4592C,r5 / ldi:20 0x3F000,r4 / ldi:20 0x3F000,r0 / cmp ...
0x80520  ret              ★ 空函数
0x80522  ldi:8 #0, r0      ; 真实代码从这里开始：清 0x420–0x425
         stb r0,@(0x420) … stb r0,@(0x425)

注意 0x80520 和 0x80522 的关系：0x80520 是 2 字节的 ret，0x80522 紧接着是一段独立的合法函数（把 6 个中断屏蔽字节写 0）。也就是说 main 的第二条 call 调用了一个空函数，而真正的初始化代码就在它后面两个字节，却没有任何调用者。

还有一处同样形状：复位段之后 0xFC030–0xFC03C 是 7 条连续的空 ret，直到 0xFC03E 才开始数据（一张 48 项的中断源序号表）。

口径「空桩」只是描述形态：这些位置在二进制里确实只有一条 ret，没有内容。至于它们在生产固件里是否被填充过、填充了什么，本报告不做推断，也没有证据支持任何一种说法。

三、任务表与任务入口

任务定义表在 0xFE00C。已确认的字段形态是：条目里出现 0x00010000 这种「高 16 位为任务号」的字（0x0001、0x0002 …），条目里还有指向 TCB 的指针。

0xFE000: 00000008 0004616C FFFFFFFF 000C001C   ; 0xFE000 是首字（步长信息）
0xFE010: 000459FC 00010004 00000000 80000000   ; 任务 1：属性 4
0xFE020: 0008133A 000462EC 00000000 00045A28   ; ★ 0x8133A 就是任务 1 的入口
0xFE030: 00020004 00000000 00000000 00089632   ; 任务 2：入口 0x89632
0xFE040: 00046404 00000000 00045A54 00030004   ; 任务 3
0xFE050: 00000000 00000000 0008B264 000464D8   ; 任务 4：入口 0x8B264

TCB 区在 0x45C38 起每 16 字节一个，+0xC 回指 0xFE184 / 0xFE194 / 0xFE1A4 / 0xFE1B4 四个表项——V6 已实测确认这 4 个 TCB 都建好了、状态是 0（休眠）。

0x8133A 是一个完整的函数，不是数据

0x81336  ret              ; ISR 的默认处理（空回调）
0x81338  bra -1           ; 停机占位 while(1);
0x8133A  stm1 r12,r13     ★ 任务 1 入口：标准函数序言
0x8133C  st r1,@-r15
0x8133E  enter #2
0x81340  mov r4,r8        ; 参数从 r4 进来
0x81342  ldi:20 0x3F0EA,r9 / mov r9,r0 / add 1,r0 / borl #8,@r0
0x8134C  ldi:8 #0x10,r0 / cmp r0,r8 / bge +0x48
0x81354  ldi:20 0x81302,r12 / call:d @r12

0x8133A 正好压在「从未执行的应用区」边界上，而它前面两个字节就是 bra -1 停机点——这个位置关系本身就说明：这个地址是任务入口，停机点只是它前面的占位。

四、手工启动任务：应用区活了

做法：启动链先跑到 0x80506（BSS 清零入口，此时内核对象已建好），然后把 PC 直接设成 0x8133A、r15 设成复位入口给的用户栈 0x4616C、r4=0。

指标原始启动链手工启动任务 1
执行步数43,446（跑到 reti 弹出）1,981 就到第一个硬件等待
不同 PC（总）824802（仅统计跳进去之后）
0x81300 以上应用区 PC0500
int #0x40（μITRON 服务）0 次10 次
0x3F000 中断回调槽被写0 个6 个
PC 覆盖的 4KB 页0x80000 / 0xFE0000x81000 / 0x82000 / 0x88000 / 0xAD000 / 0xDC000 / 0xDD000 / 0xDE000 / 0xE2000 / 0xFE000

对照组也做了：不铺垫（干净 ROM 直接跳任务入口）只有 207 个 PC、4 次服务、写 1 个槽，跑到 0x0FECA0 就散架。所以 0x80506 那次 BSS 清零是必要的——全局变量不清零，应用区走两步就踩垃圾。

规模参照300 万步与 1,000 万步的结果完全相同（802 PC / 10 次服务 / 6 个槽）。说明任务 1 在 1,981 步之后就一直卡在同一个硬件等待里空转，不是「跑得慢」。

五、回调槽公式与五个真回调

48 个 ISR 各自读的回调槽，是严格线性排布的：

槽地址 = 0x3F01C + (vec - 0x10) × 4

逐个验证：vec 0x10→0x3F01C、0x11→0x3F020、0x12→0x3F024 … 0x24→0x3F078、0x2B 例外读 0x3F018、0x2F→0x3F09C。

任务 1 跑起来后被写入的 6 个：

槽对应向量ISR 入口状态
0x3F028vec 0x130x080A54已注册回调
0x3F040vec 0x190x080B78已注册回调
0x3F048vec 0x1B0x080BD4已注册回调
0x3F078vec 0x240x080DB2已注册回调
0x3F0D4vec 0x3C0x0811D0已注册回调
0x3F0EB——不是槽 非 4 字节对齐，是状态位

这 5 个就是「A 段真正在乎的中断」。其余 34 个槽在任务 1 这条路径上仍为空。

六、0x3F01C 的真实回调：0xABFD8

写了个极简数据流扫描器（只维护「每个寄存器当前的立即数」），把整张回调表的写入值全部挖出来：19 个槽、81 条代码指针写入。0x3F01C 只有一处：

0xABCB0  int #0x40                     ; μITRON 服务
0xABCB2  ldi:20 0x43,r0 / borl #3,@r0
0xABCB8  ld @(r15,r4), ...
0xABCBC  ldi:8 #0xBD → extsb → int #0x40   ; 服务号 -67 = sys_chg_ilm（改中断级别掩码）
0xABCC0  ldi:20 0x40,r0 / bandl #0xE,@r0   ; 清中断标志
0xABCC6  ldi:20 0xABFD8,r0                 ; ★ 回调函数地址
0xABCCA  ldi:20 0x3F01C,r12 / st r0,@r12   ; 注册
0xABCD0  ldi:20 0x41,r0 / borl #1,@r0      ; 置使能位

这就是一段带中断屏蔽的中断注册函数：关中断（sys_chg_ilm）→ 清标志 → 装回调 → 置使能 → 恢复。而 0xABFD8 本身第一件事就是把自己的槽清 0：

0xABFD8  st r1,@-r15
0xABFDA  ldi:20 0x41,r0 / bandl #0xE,@r0   ; 清标志
0xABFE0  ldi:20 0x40,r0 / bandl #0xE,@r0   ; 清标志
0xABFE6  ldi:8 #0,r0
0xABFE8  ldi:20 0x3F01C,r12 / st r0,@r12   ; ★ 自己把槽清 0 = 一次性回调

顺带确认服务号 -67 = sys_chg_ilm（社区那份 REALOS 服务名表，A 段 20 处调用、B 段也有）。这也反过来说明 0xAB000 一带的代码是「应用层自己管中断」的逻辑。

A 段有 1,000 处 μITRON 服务调用，其中 108 处 sys_sta_tsk

静态扫 int #0x40 且 R12 可静态确定的调用点：

108 处 sys_sta_tsk，启动链一处都没执行到——首处在 0x81542，就在应用区里。这和前面的结论完全吻合：任务启动动作写在应用层，而应用层从来没被拉起来。

七、卡点链：一个接一个的「置启动位 → 轮询就绪位」

任务 1 在 1,981 步后停下，停点是一段和 0x80044 等时钟就绪完全同构的代码：

卡点一  0x0DCD2C
0x0DCD26  ldi:20 0x0AF,r0
0x0DCD2A  borl #2,@r0        ; 置 [0x0AF] bit2 = 启动
0x0DCD2C  ldi:20 0x0AF,r0
0x0DCD30  btsth #8,@r0        ; 测 bit7（掩码 8<<4 = 0x80）
0x0DCD32  beq -4              ; 不满足就回去
0x0DCD34  ldi:20 0x0AF,r0 / bandl #0xD / bandh #0x7   ; 软件自己清启动位
0x0DCD3C  ldi:20 0x14,r0 / btstl #1 …               ; 读结果状态
0x0DCD4C  ldi:20 0x06,r0 / btsth #2 / btsth #4       ; 更细的错误位
0x0DCD62  ldi:8 #5,r4
0x0DCD64  ldi:20 0x15,r0 / borl #8,@r0               ; 置完成标志

bit2 = 启动、bit7 = 就绪——和 0x80044 那组（0x482 bit3 启动 / bit7 就绪）属于同一类模式，只是启动位换了一位。实测佐证：卡住时 0x0AF 的影子值是 0x02，正好是 borl #2 置的那一位。

给它补上 bit7 之后，任务 1 冲过去了，撞上第二个：

卡点二  0x09C97C
0x09C974  borl #2,@0x174      ; 置启动
0x09C97A  btsth #4,@0x174     ; 测 bit6（掩码 4<<4 = 0x40）
0x09C97C  beq -4

从补上 bit7 到撞上它只用了 79 步。再补 bit6 之后又冲出 12,981 步，停在第三个 0x0CE136——形态一样（borl #2,@r8 / btsth #4,@r8），但寄存器是运行时算出来的（r8），不是立即数。

自动卡点消除器

既然三处同构，就不该手工一个个填。写了个迭代器：

  1. 连续 1,200 步里 PC 跨度 < 64 且不同 PC ≤ 12 → 判定自旋
  2. 在自旋窗口（lo..hi，不是固定 span）里反汇编，取 btsth 的 u4 得掩码 u4<<4，取窗口里第一个 ldi 的直接页地址得当寄存器
  3. 把该寄存器影子值的对应位打开，记录一条，继续

实测输出：

  #  循环起点    寄存器  等待位   首遇步数   第几次注入
  1  0x0DCD2C  0x0AF   0x80    3,328      1
  2  0x09C976  0x174   0x40    4,608      1
  → 最终停 0x0CE136（第三处，寄存器在 r8 里，超出本方法识别范围）
两个实现坑（都踩了）
① 自旋窗口起点不能向下多取整：lo & ~0x7 从 0x0DCD2C 取到 0x0DCD28，那里是 ldi 立即数的第二个字节，解码全错位 → 只能 lo & ~1。
② 解码范围必须用实际自旋的 lo..hi，不能用固定 span=0x30：那样会越过循环边界，把后面 ldi 0x6 当成轮询寄存器（表现是「它去轮询 0x006」）。
方法边界这个方法只处理「btsth 轮询直接页立即数」这一种形态。第三个卡点用 r8 动态寻址就抓不到；如果循环是 ld + cmp + beq 形态也抓不到。它的价值是把「已知同构模式」批量扫掉，不是万能。

八、这套东西现在怎么用

「手工启动任务」已固化进仿真台，两条命令都能复现本报告的全部数据：

# 命令行
python -m frbox -M d300-a --task 0x8133A:0x4616C:0:0x80506 -c "cont 5000; info registers"

# monitor 里
boottask 0x8133A:0x4616C:0:0x80506
cont 2000
x/8i 0x0DCD2C

--task 的参数是 ENTRY[:SP[:ARG[:STOPPC]]]：先跑到 STOPPC（做 BSS 清零），再把 PC/SP/r4 设好跳进去。m.boot_task() 返回三元组并留在 machine.task_boot 里。

十、下一步

  1. 把三个卡点做成真设备：0x0AF（bit2 启动 / bit7 就绪）与 0x174（bit2 / bit6）的语义已经有实测支撑，可以照 dev_clk.py 的样子建模；第三个 0x0CE136 要先追清 r8 的来源。
  2. 让 ISR 真正响一次：现在 vec 0x13 / 0x19 / 0x1B / 0x24 / 0x3C 已经有真实回调，注入这五个向量应该能看到 ISR call @r0 跳进应用区并执行实质逻辑——这是「中断驱动」第一次真正闭环的机会。
  3. 找 sys_sta_tsk 的调用者：108 处里首处 0x81542，看它是任务 1 自己调的（创建子任务）还是被别的路径调用。
  4. B 段同样的方法：B 段有 27 处 sys_sta_tsk、2,282 处服务调用，规模更大；如果也能定位任务表入口，同样可以手工拉起。
