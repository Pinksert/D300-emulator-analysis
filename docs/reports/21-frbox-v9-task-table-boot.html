一、这一版最重要的三件事

V8 的结尾留了一句话：「缺的不是硬件，是调度器给任务铺的那层栈帧」。这一版把这句话否掉了 —— 真正的原因只有一个，而且比想象的简单得多。

  • 栈顶其实不影响结局。此前用的 0x0004616C 确实错了（它是表头那一项， 任务 1 真正的栈顶是 0x000462EC），但把栈顶从 0x45000 一路换到系统栈 0x7F000， 跑出来的步数和结束地址一个字节都不差。原因是任务的压栈/弹栈是平衡的。
  • RP 从来没设过 —— 这才是唯一成因。任务的收尾是 ld @r15+,rp; ret， 返回地址就是进函数时压进去的那个 RP。不设的话，它沿用引导阶段最后一次 call 留下的 0x00080500，于是任务「返回」到一段不相干的代码里，看起来像「掉到地址 0」。
  • 「跑得越久」不代表「跑得越对」。把 wai_flg 当成立即返回的空实现， 任务会一路往下冲、从来不等，56 次调用里没有一次是真的；挂上会阻塞的内核后， 它在 9,841 步就停在了第一个握手上 —— 比「跑完」早得多，但那次才是真的。

二、任务表：8 个任务，一条 0x1C 字节

入口在 0x000FE000。头 16 字节之后，每 0x1C 字节一条记录， 共 8 条。

2.1 表头

偏移值读法
+0x000x00000008任务数 = 8
+0x040x0004616C不是任务栈顶，是个基准值（此前一直被误当任务 1 的 SP）
+0x080xFFFFFFFF结束/无效标记

三、真正的原因是 RP —— 栈顶其实不影响

3.1 任务函数长什么样

0x08133A  stm1 r12,r13       ; 存 r12/r13
0x08133C  st   rp, @-r15     ; 存 RP —— 注意 0x1781 / 反过来的 0x0781 就是 ld @r15+,rp
0x08133E  enter #2           ; 开 2 个字局部变量
   ...
0x0813F8  leave
0x0813FA  ld   @r15+,rp      ; 取回 RP
0x0813FC  ldm1 r12,r13
0x0813FE  ret                ; 跳到 RP

关键在于这个压栈/弹栈是平衡的：进函数时压进去的那个 RP，就是出函数时弹出来的那个。 所以任务「返回」到哪里，只由进函数时的 RP 决定，与栈顶初值无关 —— 栈顶只决定那 4 个字节压在哪个地址。 boot_task 只设了 PC / SP / r4，RP 没管。

3.2 五种栈顶 × 两种 RP 的实测

栈顶RP结果
0x462EC（任务表真值）0x81338入口后 32,726 步 → 固件自带的 bra -1 停机占位
0x4616C（表头字段）0x81338一模一样：32,726 步 → 停机占位
0x46000 / 0x45000（往下挪）0x81338还是一模一样：32,726 步 → 停机占位
0x7F000（系统栈，明显错）0x81338仍然一模一样：32,726 步 → 停机占位
0x462EC（对）不设（沿用残值 0x80500）跑满 200 万步（实测 2,000,480）停在 0x0FE404，看着最「成功」
0x4616C（错）不设（沿用残值 0x80500）累计 39,391 步 → PC=0，报「取指落在不可执行区」（V8 看到的那个现象）

两半的结论很干净：

  • RP 给对，栈顶怎么给都能跑完，连给到系统栈 0x7F000 都是同一个 32,726 步。 因为压栈/弹栈平衡，栈顶只影响那 4 个字节的落点，不影响返回值。
  • RP 不给，栈顶给对也跑不完 —— 返回地址是引导阶段最后一次 call 留下的 0x80500，一路弹栈弹到别处。栈顶不同只决定「弹到哪儿」： 给表头字段弹到地址 0，给真值则绕回 0x080500 那条残余链。
这一版的纠正：V8 说「掉到地址 0 是因为缺一层调度器铺的栈帧」。 不对。唯一的成因是 boot_task 从没设过 RP，于是沿用了引导阶段最后一次 call 留下的 0x080500。改一个参数就能让它正常返回， 不需要造任何假调度器。
顺带纠正本文档自己的初稿：曾把「栈顶取错」也列成成因之一，实测证明它不影响结局。

四、μITRON 半主机：让 wai_flg 真的会停

4.1 为什么非做不可

frbox 原来把 int #0x40 全部当成立即返回的空实现。这对 sys_get_ver 这类查询没问题，对 sys_wai_flg 就致命： 等待立刻「成功」，任务于是不停地 wai_flg → clr_flg → sta_tsk。

结果就是：任务不会停，但也从来没「跑对」过 —— 它一路往下冲， 把本该等外部事件的地方全部当成「已经就绪」。 「没停机」不等于「跑对了」。这条判据是这一版最重要的收获。

4.2 做法

  • 建 17 个事件标志对象（数量取自固件自己的标志表 0x551B0 的 17 项）；
  • set_flg / clr_flg 按 μITRON 语义真改位模式；
  • wai_flg 按 wfmode 判：位 0x02 = 或等待（任一位命中）， 否则与等待（全部命中）；满足才返回，不满足就把机器置成「阻塞」， 记下标志号、等待位、等待模式、PC；
  • sys_slp_tsk / sys_dly_tsk / sys_ext_tsk 同样按「停下来」处理；
  • 外部事件用 flag set <id>=<bits> 注入，resume 把 CPU 恢复到那条 int 指令重新执行一遍 —— 这次条件满足，服务正常返回。
「重新执行那条 int」而不是「直接往下走」，是为了让 r12（错误码）和 r13（返回的标志位模式）由同一条代码路径产生，避免出现「状态对了但寄存器没填」的半吊子结果。

4.3 参数顺序的坑

服务标志号位模式模式输出
sys_wai_flgR5R6 waiptnR7 wfmodeR13 flagptn / R12 err
sys_set_flgR4R5-R12 err
sys_clr_flgR4R5-R12 err

两套顺序不一样。混用会读到一个假标志号，表现为「等的东西和实际固件等的不是同一个」， 而且不会有任何报错 —— 这一版第一次跑就踩到了。

读法：

六、服务调用：换了 μITRON 那一层，路径就变了

四种挂法，同一快照、同一 200 万步上限，只换 int #0x40 那一层。 「次数」按执行到的 int #0x40 指令条数数，不用钩子计数 —— 因为不挂钩子时它真的会走 EIT 进向量表，挂上钩子就被截住当服务返回，两者不是同一条路。

挂法int #0x40累计步数停在哪这个数说明了什么
不挂钩子（走真向量表）5642,4420x081338调用全被当普通中断吞掉，等于没有 REALOS
--itron 一律立即返回5638,6390x081338任务一路往下跑，从来没等过任何事件
--itron-block 真阻塞99,8410x081492停在第一个 wai_flg，步数少一个数量级但那次是真的
--itron-block --autoevent5635,5730x0813F8补上 13 个事件走完整条链，sys_ext_tsk 退出

关键读法：前两种也各有 56 次调用，和第四种一样多。所以「调用次数」根本不是判据 —— 判据是有没有真的在某一步停下来等。第三行只执行了 9 条 int 就停住， 那 9 条里有 8 条是立即满足的查询，第 9 条是真的等。

八、结束：sys_ext_tsk

0x0813EE  add    #1, r9
0x0813F0  bandl  #0x80, r9        ; 取状态位
0x0813F2  ldi:8  r12, 0xEB         ; 0xEB = -21 = sys_ext_tsk
0x0813F4  extsb  r12
0x0813F6  int    #0x40             ; ← 任务自己退出
0x0813F8  leave

所以任务 1 是一次性初始化任务：把该起的东西起起来、该置的标志置上，然后退出。 它不是常驻循环，也不是「卡住了」。

这就是 V6 起一直在问的那个问题的答案。从 V6 起我们一直在说「内核对象建好了，缺的是启动调度器那一行」。 现在可以说得更准确：

  • 启动链是完整的、可执行的 —— 只要给它一个能落地的 RP，再让 wai_flg 真的会等；
  • 缺的那一行仍然缺（0x804FA 的孤立 ret 还在）， 所以真机上这段跑不起来的原因不在这一段代码，而在没人调用它；
  • 一旦调用，它需要的事件来自别处（其他任务或中断）—— 仿真台现在可以代替那个「别处」。

十二、一句话总结

V8 说「缺的是调度器铺的那层栈帧」。V9 证否：栈顶错了不影响（五种取值跑出同一结果）， 唯一的成因是 RP 从来没设 —— 补上一个参数，任务 1 就能正常返回到固件自带的停机占位。
再把 wai_flg 从「立刻成功」改成「真的会等」，任务 1 在 9,841 步停在了 第一个握手上 —— 早了一个数量级，但那才是真的。
喂进 13 个事件之后它走完了：56 次服务调用、10 次 sta_tsk、 35,573 步，然后 sys_ext_tsk 退出。 任务 1 是一次性初始化任务，不返回、不循环。
