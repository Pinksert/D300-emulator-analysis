一、V10 那句「至今没有发生过一次真正的任务切换」，作废

V10 结尾把这句话写进了结论，还专门列了三条「都不成立」的路：硬件中断被 ILM 挡在门外、 把 wai_flg 换成别的阻塞服务一律立刻返回、把 clr_flg 改成 set_flg 只改变任务 1 自己的走向。三条路都试对了方向，唯独漏了一点： 不是内核不想切，是内核请求调度的那个动作，被仿真台吞掉了。

内核每次需要换任务时，会往直接页 0x44 写一个字节 1：

0x000FECEC  ldi:8  #1, r13
0x000FECF0  dmovb  @0x44      ; R13 → @0x44（普通内存写，不是 int 指令）
0x000FECF2  ld     @r15+, rp
0x000FECF4  ret

跑 30 万步，它被写了 1,016 次；而固件里从头到尾没有任何一处读它。 只写不读 —— 那它不是内存，是硬件寄存器。以前仿真台把它当普通内存， 于是内核的每一声「该换任务了」都喊进了一个没人听的格子。

这一版补的三样东西（前两样是新设备，第三样是改错）： ① 直接页 0x44「请求调度」：写 1 → 向中断控制器挂 vec 0x3F； ② 0x3F4/0x3FC 硬件优先级编码器：写就绪位图进 0x3F4，从 0x3FC 读回最高优先级号； ③ ILM 的优先级约定一直搞反了：正确是「级别号越小优先级越高，受理条件 lvl < ILM」。 三样缺任何一样，任务切换都不会发生。

补完之后，同一份固件、同一条启动链、一个字节都没改：

  step    43,429  → 任务 1     TCB=0x0459FC  入口 0x08133A   由 0x0FE4EC 写入
  step    43,516  → 任务 5     TCB=0x045AAC  入口 0x0A62FE   由 0x0FE8BE 写入
  step    43,806  → 任务 1     TCB=0x0459FC  入口 0x08133A   由 0x0FE8BE 写入
  step    44,614  → 任务 5     TCB=0x045AAC  入口 0x0A62FE   由 0x0FE8BE 写入
  step    45,125  → 任务 1     TCB=0x0459FC  入口 0x08133A   由 0x0FE8BE 写入
  step    45,341  → 空闲任务     TCB=0x045C0C  入口 0x0FE510   由 0x0FE8BE 写入

1,043,428 步跑完，最终停在 0x0FE510（空闲任务的 bra -1）， 中途一次都没停机。第一次是 0x0FE4EC（首次派发的上下文恢复段）， 后面五次全是 0x0FE8BE —— 那是调度器里真正做「换一个任务」的那条写。

二、第一处错：ILM 的优先级约定反了

这一条最要命，也最难看出错。FR80 的 CCR 里有个 4 位 ILM（中断级别屏蔽）， 旧代码是这么写的：

# 修复前：号越大越优先，受理条件 lvl > ILM
if lvl <= self.ilm:  return False      # 被挡掉
# 修复后：号越小越优先，受理条件 lvl < ILM
if lvl >= self.ilm:  return False      # 被挡掉

反证硬得不能再硬：任务上下文 PS 里的 ILM 是 0x1F，而固件写进 48 个 ICR 的中断级别 全部落在 0x12–0x1F。按旧约定，任务运行时一条中断都进不来 —— 固件等于全聋，那它写这 48 个 ICR 干什么？

反过来看则处处自洽，而且能解释一个以前解释不了的细节：

量值在新约定下怎么读
vec 0x3F 的 ICR0x1E所有启用向量里级别号最大 = 优先级最低。调度器本就该最低，好让所有外设 ISR 都能抢占它
串口 vec 0x1B 的 ICR0x1A比调度器高两级 —— 串口中断能打断调度过程
内核临界区 stilm #0x1E0x1E恰好只把 0x1E 这一级（调度器自己）挡在门外，其余全放行
任务的 PS.ILM0x1F放行 0x00–0x1E 全部 31 级

于是派发的时机被固件安排得很自然：内核在临界区里请求调度 → 调度器被自己的 ILM 挡住 → reti 回到任务上下文（ILM 变回 0x1F）→ 派发立刻落地。 这不是我们设计的时序，是固件自己的 ILM 取值逼出来的。

还没定的一处：新约定下 ICR 级别为 0x1F 的那 20 条向量（其中 13 条有真 ISR） 永远不会被受理。要么 0x1F 在真机上是「禁用」值，要么比较其实是 <=。 当前取 <，因为它是唯一让调度器工作的方向。记在 KNOWN_ISSUES 第 41 条。

三、第二处缺：直接页 0x44 = 「请求调度」

它是只写寄存器（读恒为 0），写非零字节就挂一条中断。请求哪条向量？三条证据互相咬合：

  • 内核区里唯一一个还没被解释的向量入口是 vec 0x3F → 0x000FE776， 而它的头几条指令正是调度器该有的样子（见下）；
  • 它的 ICR 级别 0x1E 是所有启用向量里最低的 —— 调度器本就该最低；
  • 打开它之后，任务切换第一次真的发生了。
0x000FE776  andccr #0xEF        ; 先关中断：调度过程不许被外设 ISR 打断
0x000FE778  orccr  #0x20        ; 切到系统栈
0x000FE77A  stm1   r8-r14
0x000FE77C  ldi:32 #0x459F0, r12
0x000FE782  ldi:8  #0, r13
0x000FE784  xchb   @r12, r13    ; 原子读走并清零「待派发」字节
0x000FE786  cmp    #0, r13
0x000FE788  beq    → 返回       ; 为空 → 不用调度
            ...
0x000FE798  ldi:32 #0x45980, r7 ; 当前 TCB
0x000FE79E  ld     @r7, r14

xchb（原子交换）是关键：调度请求是个字节标志， 读走和清零必须一步完成，否则并发请求会丢。固件在这里用了原子指令， 说明它确实把自己当成「会被异步打断的那一段」来写。

这是推断出来的绑定，不是手册确认的。寄存器名、以及「是不是还有别的触发源」都还没定 （KNOWN_ISSUES 第 42 条）。但三条证据咬合，而且它是唯一让调度器动起来的建模方式。

四、第三处缺：0x3F4/0x3FC 是硬件优先级编码器

调度器挑下一个任务时，要先把「就绪位图」变成「最高优先级的那个号」。固件是这么做的：

0x0FE830  ldi:32 #0x45984, r12
0x0FE836  ld     @r12, r13        ; r13 = 就绪位图
0x0FE838  ldi:20 #0x3F4,  r14
0x0FE83C  st     r13, @(r14,0)    ; W 0x003F4 ← 位图（4 字节）
0x0FE83E  ld     @(r14,8), r13    ; R 0x003FC → 结果（4 字节）
0x0FE840  add    #4, r12          ; r12 = 0x45988 就绪队列数组
0x0FE842  lsl    #3, r13          ; 结果 × 8 = 队列节点大小
0x0FE844  ld     @(r12,r13), r13  ; 取该优先级的队首 TCB

写入口和读出口差 8 个字节、写完立刻读、读完乘 8 当数组下标 —— 这是一个纯组合逻辑的硬件查表器。结果必须等于「最高优先级号」， 否则下标必然越界：就绪队列数组只有 13 条（优先级 0–12）， 而位图的置位规律是 bit(31 − 优先级)。于是

结果 = 前导零个数 = 32 − bit_length(位图)

实测（把位图直接写进去读回）：

写进 0x3F4 的位图从 0x3FC 读回含义
0x508000001置位 bit30/28/23 = 优先级 1/3/8 → 最高是 1（任务 5）
0x800000000只有优先级 0 就绪
0x0000000131只有优先级 31 —— 队列数组里没有，越界
0x0000800016同上，越界（固件不会让它发生）
0x0000000032空位图。100 万步里一次都没出现过
语义是从「写什么、读什么、读完怎么用」三点唯一确定的，寄存器真名未知 （KNOWN_ISSUES 第 43 条）。它和 0x44 是同一条推断链上的两环： 少任何一环，调度器都会读到 0 号（空）优先级。

七、⚠️ A / B 两个模式必须分开报，数字不能混着比

这一版最容易踩的坑：开不开 0x44，跑出来是两套完全不同的数字。 以前所有基线都是 A 模式跑出来的，V11 起新增 B 模式。两个都得留着，但必须标明是哪个。

模式怎么开现象
A（V10 基线）enable_xfer() + realos.prepare() 任务 1 一路跑到底，30 万步里 1,888 次服务调用（clr_flg 754 / wai_flg 751 / sta_tsk 376 / set_flg 6 / snd_msg 1）， *(0x45980) 只写 1 次
B（V11 新增）boot_realos()（= A + enable_dispatch()） 任务 1 阻塞后被切走，30 万步里只有 14 次服务调用， *(0x45980) 写 6 次

B 模式下服务调用反而少了 99%，原因很直白：任务 1 早就阻塞了， 剩下的 99 万步都在空闲任务的 bra -1 里打转。 如果拿 B 的 14 去否定 A 的 1,888，或者拿 A 的「只写 1 次」去否定 B 的切换，都会读反。

CLI 上 --realos 走的是 B（boot_realos() 里自动打开）； 裸跑 -M d300-a 默认是 A，以保住 V2–V10 那些基线。 自检第 16 组刻意只开 xfer，就是为了把 A 的「xfer 三处握手都走完 (3,3)」钉死。

八、还差什么：别把「任务切换跑通了」读成「相机跑起来了」

  • 13 个任务里只有 3 个上场（任务 1 / 任务 5 / 空闲任务）。其余 10 个的上下文要靠 sta_tsk 去建，而触发 sta_tsk 的硬件事件 （按键 / 拨盘 / 存储卡 / 时钟）一个都没有。
  • 7 次调度全部来自内核自身的服务调用，没有一次是外设中断引发的。 所以现在证明的是「调度器能换任务」，不是「相机有任务在互相唤醒」。
  • B 段（主控 UI）还是没跑。这一整条线都在 A 段。
  • xfer 三处握手（0x0AF / 0x174 / 0x524）仍是模型化假设，不是从硬件手册读来的。
  • 854 个未定义编码仍然未实现；gdbstub 还没做。
现在可以报的：固件自带的 REALOS 在 frbox 上换起了任务 —— 调度器是固件自己的代码，就绪位图、就绪队列、优先级编码器、派发请求字节全部是固件自己的数据结构， 我们只补了三样「固件以为存在、仿真台没有」的东西。
还不能报的：相机功能跑起来了。差的是硬件事件源，不是内核。

九、怎么复现

# 自检：frbox 282 条（第 17 组是本版新增的调度专项），CPU 63 条
cd emu && python frbox_selftest.py      # 282/282
cd emu && python fr_selftest.py         # 63 条，第 6 组验 ILM 的新约定

# 本版新增的取证脚本
cd emu && python probe/exp_realos_sched.py    # 三张表 + 编码器 + ILM 约定 + 切换时间线

# 交互式
python -m frbox -M d300-a --realos 1 -c "cont 1000000; realos"
实现上踩到的两个坑（都会让计数器翻倍或越界，写新设备时照抄即可）： ① 直接页是按字节路由的，dp.attach(lo, hi, dev, base) 的 base 要传 0（它是加在访问偏移上的常数）， 多字节寄存器还要自己拼装、等最后一个字节落地才结算，否则 4 字节写会被算成 4 次； ② 别把 int 指令和内存写搞混 —— 0x44 那条是 dmovb 普通写（int #0x40 的编码是 0x1F40）， 所以钩子要挂在总线上，不能挂在陷阱分发上。
