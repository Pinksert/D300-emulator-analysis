二、意外收获：D300S 的现成配置

Java/Emulator/conf/ 下躺着 24 份机型配置。我原以为只有 TX 机型有，实际一读发现 FR 机型一大堆：

配置文件机型芯片
b810101b.dfr.txtD300s "B" 固件 1.01bFR
bd3s101c.dfr.txtD3s "B" 固件 1.01cFR
b700_103.dfr.txtD700 "B" 固件 1.03FR
b630102a.dfr.txtD800 "B" 固件 1.02aFR
b720103c.dfr.txtD4 "B" 固件 1.03cFR
b910101a.dfr.txtD600 "B" 固件 1.01aFR

D300S 那份给出的关键参数：

-i 0x00040000-0x0073FFFF=0x00000000     # B 固件装载到 0x40000
-t 0x000EFC00                            # 中断向量表基址
-s 0x40EDE=sys_set_tim(...)              # 一整套 μITRON 系统调用符号
-s 0x40F1A=sys_dly_tsk(R4 [IN dly_tim], ...)
-s 0x414C8=sys_sta_tsk(R4 [IN tsk_id], R5 [IN tsk_param], ...)
   ... （共 60 余条系统调用）
两份硬巧合：①D300 的 B3000111.bin = 7,340,032 字节 = 0x700000，与 D300S 配置的 0x40000–0x73FFFF 长度一模一样，文件映射可以原样照搬； ②源码里 FrCPUState.RESET_ADDRESS = 0x00040000，正是这个装载地址。 另外那套 sys_* 符号表再次印证了我们此前「Softune REALOS/FR + μITRON」的判断。

三、反汇编互校：零实质分歧

用它的 Dfr（移植自 Kevin Schoedel 的原版，独立第三方实现）反汇编 A3000111.bin（基址 0x80000，与我们自己的解码器同一份输入），逐条比对：

口径数值
Dfr 反汇编指令数233,191
自建解码器指令数233,071
指令起始地址完全一致233,071（自建的每一条都能在 Dfr 里找到）
助记符不一致27 → 一致率 99.988%
其中 Dfr 标 UNK、我们能解27（MOV / STRES / LDRES / COPSV 等系统寄存器指令）
真正「两边解出来却不一样」0
两边都解不出119 个字（集中在 A 段尾部 0x0E3CA0 起，是数据区）

拿 0xC0D9E 这个函数逐行看（上一份报告的主角），两边给出的完全一样：

000C0D9E  9B34 FAE9      LDI:20  #0x3FAE9,R4      ; 唯一输出 = 0x3FAE9
000C0DA2  9B4C 56EA      LDI:20  #0x456EA,R12     ; 闸门 A：[456EA]==0 ?
000C0DB0  8825           BTSTL   #0x2,@R5         ; 闸门 F：45753 的 bit1
000C0DBE  8925           BTSTH   #0x2,@R5         ; 闸门：45753 的 bit5
000C0DDA  E302           BNE     0x000C0DE0
000C0DDC  81D4           BANDH   #0xD,@R4         ; 清 bit5（0xD<<4 = 0xD0）
...
000C0DD6  06C0           LDUB    @R12,R0
000C0DD8  A860           CMP     #0x6,R0          ; ★ 闸门 B：[456ED]==6
000C0DEE  9124           BORH    #0x2,@R4         ; 置 bit5（0x20）
已验证上一份报告里 「btstl #u4 掩码 = u4、btsth #u4 掩码 = u4<<4」「0x0781 是 ld @R15+,RP 不是普通 ld」 这两条我们踩过的坑，Dfr 的输出全部印证。

四、真跑：最小平台（纯 CPU + 内存）

先不走 GUI，写了个无头驱动 D300Run（照抄仓库自带 FrEmulatorTest 的初始化方式）。B 固件从 0x40000 启动，头几条指令是这样的：

0x00040000  LDI:32  #0x50000000,R0      ; FR 的 I/O 区基址
0x00040008  STH     R1,@R0
0x0004000A  STILM   #0x10               ; 中断级别掩码 = 0x10
0x0004000C  LDI:32  #0x00008400,R15     ; 栈指针 SP = 0x8400
0x00040012  LDI:32  #0x000EFC00,R0
0x00040018  MOV     R0,TBR              ; ★ 中断向量表基址 = 0x000EFC00
关键交叉验证固件自己写进 TBR 的 0x000EFC00，与 D300S 配置里的 -t 0x000EFC00 一字不差。 这同时说明两件事：我们把 B 固件装在 0x40000 是对的；D300 与 D300S 在这个层面是同一套布局。

接着是两个标准启动循环：

  • 清 RAM：0x40380 起，R1 初值 0x23368，每次 R1 -= 4，约 10.8 万条指令
  • 搬数据：0x403D8 起，长度 0x11C48 字节，展开成每轮搬 2 个字

40 万条指令之后，PC 停在：

0x000407CC  LD      @R15+,RP      ; ← 又一次撞上 0x0781 这个坑
0x000407D2  LDM0    (R0..R7)
0x000407D4  LDM1    (R8..R14)
0x000407D6  ANDCCR  #0xDF
0x000407D8  RETI
0x000407DC  BRA     0x000407DC    ; ★ 自转

五、真跑：完整框架（带时钟、定时器、中断控制器、外设）

第二个驱动 D300Full 走 EmulationFramework.initialize(CHIP_FR, ...)，把主时钟、可编程定时器、中断控制器、IO 端口、LCD / JPEG / SD / 镜像箱全接上，然后 masterClock.start()。

指标数值
12 秒执行周期数253,514,205
稳定后 PC 落在0x00125A0C – 0x00125A18（7 条指令的小循环）
结束时ILM=31、r14=0x9F800ADC（已是真实栈地址）、r6=0x5C003000
未建模外设寄存器1,102 个不同地址（5 秒内 1,248 条告警）

那个小循环是什么——一个忙等超时：

00125A02  LDI:32  #0x5C003000,R6     ; 硬件计数器基址
00125A08  LDI:8   #0x34,R13
00125A0A  LD      @(R13,R6),R5       ; 读一次 → 0x5C003034
00125A0E  LD      @(R13,R6),R0       ; 再读一次
00125A12  SUB     R0,R12             ; 增量 = 第二次 - 第一次
00125A16  CMP     R4,R0
00125A18  BC      0x00125A0C         ; 增量 < 超时值就一直转

因为 0x5C003034 从来没被建模、读出来恒为 0，增量永远是 0，于是永远转下去。

有意思的是同一片代码里有 INT #0x40（0x125A2E）——这正是 conf 文件里 「Table of offsets used by INT 0x40」说的 μITRON 系统调用陷阱。实跑的代码里真的在用它。

六、给计数器打个桩，看能不能往前走

加了一行最小打桩：后台线程每 1 ms 往 0x5C003034 写一次递增的值。

结果：循环确实退出了——1 秒内 PC 从 0x125A14 离开，随后一路走到 0x407DC，又是那个 BRA 自身。此时 r0–r14 全部归零，ILM=31（可屏蔽中断全关）。

两条完全不同的路径（最小平台走 RETI 之后、完整框架走完超时等待之后）都汇到 0x407DC 的自转， 而且停在那里时中断是全关的——这更像停机/异常兜底，而不是「等中断的空闲循环」。 不过这一条我不敢写死，需要再确认。

七、这次能写进文章的，和还不能写的

能写

  • NikonEmulator 能在现代 JDK 上编译并运行 D300 固件
  • 社区口径称这颗核为 FR80（CHIP_LABEL = {"FR80","TX19"}）——可引用佐证
  • D300 B 固件装载地址 0x40000、向量表 0xEFC00，与 D300S 完全一致
  • 启动流程实测：设栈 → 设 TBR → 清 RAM → 搬数据 → 进 RTOS
  • INT #0x40 = μITRON 系统调用陷阱，实跑代码里就在用
  • 解码器经独立第三方实现逐条验证，233,071 条零分歧

不能写

  • 别写「D300 已经能在模拟器里开机」——差得远
  • 别把 0x407DC 说成「崩溃」——性质待定
  • 别用这次的结果去推测菜单/界面行为（一次都没跑到）
  • 1,102 个未建模寄存器只是 5 秒内的采样，不代表总数

八、下一步

  1. （性价比最高）先用它的 Dfr 把 D300 B 段整段反出来，再配上 D300S 那套 sys_* 符号——能直接读出固件在调哪些 RTOS 服务。
  2. 把 A 段也接进去：A3000111.bin 装到 0x80000，用另一个 FR 实例跑，再把两台的串口/IO 互连（框架里 interconnectChipSerialPorts 就是干这个的）。
  3. 补外设：0x5C003034 这个自由运行计数器是第一个该补的，补完可能就跨过 0x407DC 了。
  4. 长期：把 D300 写成正式的 platform 类，参照 D5100/D3100 那套结构。
