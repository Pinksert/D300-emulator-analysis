D300 固件模拟器完善：从"跑到空闲任务就死"，到持续运行

第五篇仿真记录 · 对象 B3000111.bin（D300 主控固件 1.11）· 工具 NikonEmulator（FR80）
一句话：之前固件跑完开机初始化就钻进一条自转指令、再无动静。这一轮找到并修掉了四个仿真器自身的毛病， 现在固件能被自己的定时器中断周期性唤醒、持续产生系统调用 —— 在 6000 万步里新增了 755 次， 而且节奏稳定。顺带坐实了那堵"墙"的真实身份：它不是崩溃点，是操作系统的空闲任务。

二、修掉的四个问题

① "1,105 个未建模外设"里，97.5% 是把内存当成了外设

仿真器把地址的高 16 位当作"外设页号"来分派监听，其中一页就是 0x0000 打头的整个 64K。 可 D300 的片上内存恰好也在这一页里 —— 复位后栈指针是 0x8400，任务表 0x54BF4 处存着的也是 0x8400，说明内存从 0x8000 起步。于是操作系统读写任务控制块 （0x83B0–0x83FD）的每一次动作，都被当成"访问了一个不认识的外设"记了一笔。

10,177 次"未建模"告警的分布（修复前）
  落在 0x8000–0xFFFF（片上内存，内核任务控制块）  10,126 次   ← 误报
  落在 0x0000–0x0FFF（真正的 FR 外设区）              51 次   ← 真实缺口

而且告警只是"嚷嚷"，实际返回值仍是内存里的真值，并不影响执行 —— 坏的是统计口径。 给监听器加了一条地址上界后，地址数从 1,105 降到 28。

这一条直接影响上一份报告的措辞：原来写的"1,102 个外设寄存器没建模"是虚高的， 真实缺口是几十个量级，不是上千。

② 同样跑一次，结果却不一样

固件会读一个自由运行的硬件计数器（0x5C003034）来做精确延时，代码是"读两次、算差值、够不够、不够再读"。 之前我用一个独立线程按真实时间给它加值 —— 结果机器忙不忙，决定了固件走哪条分支， 同一份固件两次跑出 55 次和 161 次调用。

改成按仿真步推进之后，跑了两次完全相同的参数：

第 1 次：3,041,494 步进空闲任务 / 55 次调用 / 申请中断 13,479 次 / 未建模 28 个
第 2 次：3,041,494 步进空闲任务 / 55 次调用 / 申请中断 13,479 次 / 未建模 28 个

又把计数器的增速扫了 5 档（每步 +1/64 到 +64），结果全部相同。所以那个 161 是时序随机的产物， 不是固件的固有行为 —— 把它当成"D300 开机做了 161 次系统调用"是不成立的。

③ 定时器配好了，却从来没走过一步（关键突破）

固件在启动阶段就把 0 号定时器配置完毕了：

FR80 Reload timer #0 @50000000Hz: TMCSR=0b0000000000011011, TMRLRA=33000, interrupt enabled, value=33000

参数齐全、中断也开了。但我在驱动里替它走了一千多万拍，它一次都没溢出。根因在仿真器的结构： 定时器启动时只是把自己登记到主时钟上，而"是否在运行"这个开关由主线程设置。 我们不启主时钟，它就永远停在 active=false，计数一次都不递减。

补上主时钟本该做的那一步之后，固件立刻有了反应。反汇编的那段中断服务程序也印证了这条路走通了：

0004046E  stm1  {r9..r15}        保存现场
00040470  stm0  {r0..r7}
00040472  st    dr4 / dr5 / dr1  保存专用寄存器
00040478  ldi:8 #0x1A, r13       中断号
0004047C  ldi:32 #0x40A44, r12
00040482  call  r12              通知操作系统内核
00040484  ld    dr1 / dr5 / dr4  恢复
0004048A  ldm0 / ldm1
0004048E  reti                   中断返回

④ 串口只支持同步模式，固件用的是异步

修好定时器后跑长一点，第 637 万步直接崩了：

Serial Interface 0: cannot be configured in mode MD=0b000.
Only CSIO mode (0b010) is supported for now

D300 把串口配成异步 UART（MD=000），而仿真器只实现了同步 CSIO。 补了一个最小旁路：允许该模式，写入发送寄存器就当作发完、并把字节留下来（可打印字符原样记， 不可打印的记成 <XX>），好让固件不被卡住。补完之后 6000 万步全程跑完、不再中断。

顺带一个观察：固件一个字节都没往串口打印。这台机器启动时不像留了调试输出口。

三、那堵"墙"到底是什么

之前卡住的地址是 0x407DC，一条 BRA 自身（e0ff）死循环， 性质一直没敢下结论。这轮的证据可以定论了 —— 它是操作系统的空闲任务：

  • 地址写死在数据区：ROM 0x54F20 处存着 0x000407DC， 而整个 B 段里这个常量只出现这一次；同一条记录里还有栈指针 0x6800060C、 状态字 0x21，是一条完整的任务控制块。
  • 前面是标准的恢复现场序列：0x407CC–0x407D8 是 弹 RP/MDL/MDH、ldm0/ldm1、andccr、reti， 不是普通函数的收尾。
  • 行为完全吻合：最后一条系统调用是 wai_flg（等待事件标志）， 任务随即阻塞；再没有可运行任务，调度器自然落到空闲任务里自转。

所以此前"跑到它就停了"并不是固件崩溃或跑飞，而是启动已完成、所有任务都在等事件、 又没有任何中断源来唤醒它们 —— 是我们这台假机器太安静了。

四、唤醒之后，固件在做什么

6000 万步里新增 755 次系统调用，构成如下：

服务次数含义
sig_sem196释放信号量
wai_sem196获取信号量
twai_flg99带超时地等待事件标志
ref_tsk96查询任务状态
clr_flg67清除事件标志位
set_flg35置起事件标志位
pol_flg33轮询事件标志
dly_tsk32延时
wai_flg1等待事件标志

三点值得说：

  • sig_sem 与 wai_sem 恰好各 196 次，是成对的 —— 像两个任务在一来一回地交接，而不是各自乱撞。
  • ref_tsk（查询任务状态）在启动阶段一次都没出现，是唤醒之后才有的新行为。
  • 调用量随时间稳定增长（每 500 万步约 65 次，多数区间恰好 69 次）， 说明是有固定节拍的周期行为，而不是偶发抖动。

五、下一个缺口：0x70000000 这一段

反汇编唤醒后跑得最多的那段代码，看到固件在反复做一件事：

0019EF4C  mov   0x70000000, r0
0019EF4E  add   #0xA, r0          ← 目标地址 0x7000000A
0019EF50  bandl #0xD, r0          清若干位
0019EF52  call  ...
0019EF58  borl  #0x2, r0          置位
0019EF5E  btstl #0x4, r0          测试 bit4
0019EF60  beq   ...               ← 没等到就重试
0019EF66  add2  #-1, r8           重试计数递减
0019EF68  beq   ...               最多 8 次
0019EF6A  bra:d *-32              回到开头

它在轮询 0x7000000A 这个地址的 bit4，最多试 8 次。而 0x7000xxxx 这一段完全不在仿真器的外设清单里，读回来恒为 0，所以固件每次都等不到、重试 8 次后放弃。 这就是目前最值得攻的下一个点。

六、必须说清的边界

  • 计数器速率是猜的。固件的延时依赖一个我们不知道真实频率的硬件计数器。 本轮 5 档增速下启动结果一致，说明这一段对它不敏感；但不排除别的环节敏感。
  • 55 与 161 的旧账：161 那次是旧版线程打桩的产物，已不可复现。 以本轮为准，启动阶段是 55 次。若引用旧数字，必须注明是特定时序下的观测。
  • 定时器是手动激活的。真实机器上由主时钟驱动，我们补了这一步， 但节拍与真实快慢不一定对得上——所以"每 500 万步 69 次"这个节拍数字本身没有物理意义， 有意义的是"确实存在稳定周期"这件事。
  • 串口只做了旁路，不是真 UART：没有波特率、没有时序、也没有接收端。
  • 离"开机"仍然很远。屏幕、按键、存储卡、镜头卡口、反光板全都没建模， 界面一次都没跑到。现在的成果是：固件在这台假机器上能持续调度、周期性工作，仅此而已。
