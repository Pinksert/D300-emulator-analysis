仿真台 V6：A 段不是「启动没做完」，是「根本没打算启动任务」

D300 固件 A 段（0x00080000 起 524,290 字节）· 中断系统全解 · 48 个向量全量注入实测
48ISR 向量全量注入
39精确 reti 且状态复原
181启动配置的外设寄存器
105/105frbox 自检
一句话结论：A 段把中断系统配得很齐——48 个中断级别寄存器、39 个真实 ISR、每个 ISR 都按 0x3F0xx 上的函数指针分发。但它从头到尾没有启动过任何 REALOS 任务： 复位链上本该是 vsta_knl() 的那个位置，是一条空的 ret。 所以 main 结束后去恢复上下文，系统栈上什么帧都没有，reti 弹出 0。

这一轮之前，我把这件事说成「启动流程只做硬件初始化」。这个说法不够准确——内核对象其实是建好了的 （4 个及以上 TCB、全套空链表），缺的不是初始化，是启动调度器的那一行。

一、复位链四跳，一条不漏

入口是向量表中的 vec 0x00 → 0x000FC000。整条链只有四跳：

0xFC000  ldi:32 0x4616C,r15     ; 复位就设好用户栈顶
0xFC006  stilm  #0x10           ; ILM=0x10，只放行级别 ≥16（ICR 配的正是 0x12–0x1F）
0xFC008  ldi:32 0xFFC00,r0
0xFC00E  mov    r0,TBR          ; TBR=0xFFC00
0xFC010  ldi:32 0xF8010,r13
0xFC016  call   @r13            ; ① 双标记比对（升级模式检测）
0xFC018  ldi:32 0x80044,r13
0xFC01E  call   @r13            ; ② 硬件初始化，约 1.2 KB
0xFC020  ldi:32 0x804FA,r13
0xFC026  call   @r13            ; ③ ★ 空的：这条就是 ret
0xFC028  ldi:32 0xFE426,r0
0xFC02E  jmp    @r0             ; ④ 进 main，永不返回

第①跳 0xF8010 里有个分支：先调 0xF8020 比对 0xF2FF8 与 0xFFBF8 两个地址上的 8 字节标记， 不等才调 0xF8580。实测两个标记相等，所以是正常启动、不进升级分支。

二、0x80044：一次配置 181 个外设寄存器

把「运行到 0xFE426 之前」这段时间里的所有外设写全抓下来，共 187 次写、覆盖 181 个寄存器，地址全部落在 0x80000–0x804EE。结构一眼就能分开：

地址段内容判据
0x000 / 0x400 / 0x600三组镜像寄存器 值成对互反：0x600=0xFF ↔ 0x400=0x00、0x601=0xF0 ↔ 0x401=0x0F，典型的方向/功能选择
0x440–0x46F48 个中断级别寄存器 恰好 0x30 = 48 个，值全在 0x12–0x1F，与向量表 48 个 ISR 一一对应
0x040–0x045中断标志/控制 ISR 里用 bandl #0xE,@0x40 清标志
0x0B4–0x0CB定时器预置值 0xFFFF / 0x44 / 0x46 / 0x48 这类小常数成组出现
0x108–0x117串行/通信类 0x110=0xC2C2、0x116=0x98（ISR vec 0x2B 正是操作 0x116）
0x521 / 0x531两处 0x07 成对出现，疑似两路同构外设的同一字段
这条链本身就是「A 段是 IO 协处理器」最直接的证据：它不读传感器、不碰影像通路， 只做一件事——把所有对外引脚、中断优先级、定时/串行接口一次性配好，然后交出控制权。

三、0x80506 的真身：一次 BSS 清零，不是初始化逻辑

main 只有 5 条指令，两条 call。第一条 call 进 0x80506，单独占掉 33,666 条指令 / 6,732 次内存写——占整个启动的 78%。看代码就三行：

0x80506  ldi:20 0x4592C,r5      ; 上界
0x8050A  ldi:20 0x3F000,r4      ; 下界（= sp）
0x80516  st r0,@r4 / add #4,r4 / cmp r4,r5 / bnc -4    ; 循环写 0

跨度 0x3F000 → 0x4592C = 26,924 字节 ÷ 4 = 6,731 个字， 与实测 6,732 次写对得上（多出的 1 次是循环外的首字）。所以它是纯 memset， 把 0x3F000 起的 26 KB 工作区全部清零。这片区域后面会被当成 硬件状态镜像 + 回调指针表 + REALOS 对象区，三种用途混在一起。

六、每个 ISR 都是「回调指针分发器」

39 个真实 ISR 的骨架完全一致，以 vec 0x10 为例：

0x809BE  stm0 r0–r7 / stm1 r12,r13 / st r4,r5,r1   ; 压现场
0x809C8  ldi:20 0x3F01C,r4                        ; 回调指针槽
0x809CC  ldi:20 0x40,r0
0x809D0  bandl #0xE,@r0                           ; 清中断标志（直接页 0x40）
0x809D2  ld    @r4,r0                             ; r0 = [0x3F01C]
0x809D4  cmp   r0,#0
0x809D6  beq   +3                                 ; 槽为空 → 走默认
0x809D8  ld    @r4,r0
0x809DA  call  @r0                                ; ★ 把槽里的值当函数调用
0x809DC  bra   +3
0x809DE  ldi:20 0x81336,r12
0x809E2  call  @r12                               ; 默认处理
0x809E4  ld 弹 r1,r5,r4 / ldm1 / ldm0
0x809EE  reti

而默认处理 0x81336 只有一条指令：ret。 槽为空时，中断进来什么也不做就返回。

关键：0x3F000 区在启动阶段被写入 0 次。 BSS 清零把它整片抹平，之后再没有任何代码去填。所以 39 个 ISR 的回调槽全是 0， 每一个中断都只会走「清标志 → 空处理 → reti」。 静态扫下来，引用 0x3F000–0x3F0FF 的指令有 426 条， 填表的那批集中在 0xAB000 一带——那属于从未执行过的应用区。

七、48 个向量全量注入：39 复原、8 停机、1 特殊

这是本轮最有分量的一组实测。做法：机器跑到 main 的循环里（0x80506）， 存一份快照；然后对 vec 0x10–0x3F 每一个向量，各自从快照恢复、注入、单步跑到出结果。

判定数量行为
OK39 精确 reti 回到注入点，r15 与 SSP 逐位复原
停机8 vec 0x1F/0x27/0x2C/0x2D/0x2E/0x37/0x38/0x39 指向兜底 → 0x81338 的 bra -1
特殊1 vec 0x3F → 0xFE776，先清 I 位再处理 0x459F0 队列，不按普通中断返回

ISR 长度分布很规整：绝大多数是 15–23 条指令，只有 vec 0x2B （0x80588）是 299 步——它同时操作 0x3F40E / 0x3F404 / 0x3F407 三个状态区加 0x3F018，是唯一有实质业务逻辑的中断。

为什么这组数据重要：39 个向量各自完整走一遍「硬件压栈 → ISR → 弹栈 → reti」， 每一次都要求 r15 和 SSP 回到注入前的值。这比单点测一次 EIT 强得多—— 只要压栈顺序、PS/PC 顺序、延迟槽、stm0/stm1 的寄存器掩码里有任何一处错， 39 个里必然有若干个回不到原位。现在 39/39 全过。

八、0x804FA：那个空的 ret

复位链第③跳 call 0x804FA，而 0x804FA 就一条 ret。它前面紧挨着的 0x804F0 是个真函数 （写 0x240=0x80 后返回），所以 0x804FA 是独立的小函数， 等价于 C 里的 void f(void) {}。

位置很说明问题：复位链是「初始化 → 这一跳 → jmp 进 main」。在 REALOS 的标准启动里， 这个位置正是 vsta_knl()——启动调度器、然后恢复第一个任务上下文、永不返回。 这里它是一条空 ret，于是紧接着的 jmp 0xFE426 就成了「直接跳进 main，没有任何任务上下文被建立」。

main 结束时的收尾就很自然了：

0xFE470  bra 0xFE4DE            ; main 返回后跳过去
0xFE4DE  orccr #0x20            ; S=1，切系统栈
0xFE4E2  弹 r1 / r5 / r4
0xFE4EC  ldm0 r0–r7
0xFE4F2  ldm1 r8–r14
0xFE50A  andccr #0xDF           ; S=0
0xFE50C  reti                   ; ← 从 SSP 弹，弹到全 0

这段是标准的「中断/任务返回」序列。它要求 SSP 上有一帧，而 SSP 从复位到现在一次都没下压过 （实测 0x7F000 纹丝不动），栈顶 8 个字全是 0，于是 PC 变成 0。

九、内核对象建好了，但一个都没启动

运行结束后看 0x45C38 起的内存：

0x45C38: 00045C38 00045C38 00000000 000FE184
0x45C48: 00045C48 00045C48 00000000 000FE194
0x45C58: 00045C58 00045C58 00000000 000FE1A4
0x45C68: 00045C68 00045C68 00000000 000FE1B4

每个 16 字节：+0 和 +4 都指向自己（双向链表的空环）， +8 是状态 0，+C 挂到表项 0xFE184/94/A4/B4 （每条 16 字节，正好接在 0xFE17C 表头后面）。

0x45988 一带则是成排的自引用对（每 8 字节一个环）， 是 μITRON 对象（信号量、事件标志、邮箱）的等待队列头，全部初始化为空。 结论：对象内存布局是对的，就是没有一个任务被置为可运行。

十、死锁：约 400 KB 应用代码一行没跑

A 段 ROM 524,290 字节，实际执行过的 PC 只覆盖两小片：0x80000–0x81300 （启动 + ISR）和 0xFE000 附近（REALOS 库）。中间 0x81300–0xF2FFF 约 400 KB 是应用主体，一条都没执行。

于是形成一个闭环：

  • 回调表 0x3F000 由应用区（0xAB000 一带）填 → 应用没跑 → 表全 0
  • 表全 0 → 所有中断只清标志后空返回 → 不会把应用拉起来
  • 任务不启动 → 应用区没有别的入口 → 回到第一条

要打破它，只有两条路：一是找到应用区的另一个入口（某个还没被识别的调用链）， 二是外部事件先让某个 ISR 的回调槽有值。前者是静态问题，后者需要建模具体外设。

十一、对 V5 两处说法的修正

V5 的说法V6 的修正
改「启动只做硬件初始化、根本没发起 μITRON 服务调用，做完就返回，REALOS 去恢复一个不存在的任务上下文」 「没发起服务调用」成立（12 条 call 里 int 为 0），但内核对象确实建好了——4 个 TCB、全套空链表。缺的是启动调度器那一行，即 0x804FA 那个空 ret
改「0x482 位 7 只能来自硬件」（V5 结论本身对） 补一条：A 段与 B 段都没有围绕 0x482 的握手代码，B 段引用 0x482 共 6 处、跑起来锁定 0 次。V4 的「双机握手」判断可以彻底放下
留「两段都停在 reti 弹 0」 维持。B 段 191,518 步 / 1,239 PC / 1 次 int（向量 0x40）；A 段 43,446 步 / 824 PC / 0 次 int

十二、下一步

  1. 找应用区入口：在 0x81300–0xF2FFF 里找「只被数据表引用、不被代码 call」的函数， 这类通常是任务入口或回调；再对照 0xFE17C 表里那 3 项的内容，看能否落到具体地址。
  2. 确认 0x804FA 是不是弱符号：如果 REALOS 库里有同名强符号，它会出现在 0xF8000 段；找到就能证明「这一版固件故意把它留空」。
  3. 给 0x3F01C 找一个真实回调：从 0xABCCA / 0xABFE8 / 0xAC9BC 这三处写它的代码反推应该填什么函数，然后手工预置、注入中断，看应用区能跑多远。
  4. vec 0x3F 单独建模：它是唯一清 I 位、允许嵌套的入口，还带一个 0x459F0 队列， 很像系统时基或 NMI。搞清它的触发条件，可能是让 A 段「活起来」的钥匙。
