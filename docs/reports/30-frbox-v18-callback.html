一句话：V17 留下两个问号 —— 那个回调指针 0x0008225E 到底谁调用、任务 5 被叫醒后为什么卡在闸门上。 V18 把前者查到底了：A 段有两套完全对称的单槽，槽里存一个代码指针 + 一个倒计时， 每来一个 tick 计数减 1，减到 0 才 call [槽]。基线跑完，槽里早就登记好了 （0x8225E / 计数 12 / 挂起标志 0x02），可派发器和它所在的整张主循环分派表 一次都没有执行过 —— 登记是活的，派发是死的。手动替主循环转几圈， 回调链就一站站往前走，覆盖涨了 507 个地址。

1. 先更正 V17 的一处读法

V17 说「消息体 +0x10 是个代码指针，任务 5 整条抄到 0x3FE48， 所以消息 = 回调注册单」。挂上访存监视重跑一遍，两件事都不对：

说法V17 的读法V18 实测
回调代码有没有跑过没查回调段 0x8225E–0x8229C 共 32 个地址，命中 0 个
落地缓冲 0x3FE48整条消息抄过去，含代码指针只写 +0x08 起四个半字（0x3FE50/52/54/56）；+0x10 实测 0
0x417DC +0x10 是什么消息载荷的一部分它就是全局回调槽 0x417EC —— 发送侧的构造区，不是交给信箱的那份内容
0x0008225E 的引用当作消息字段全段 ldi 立即数只出现 1 次（0x8145E），装进 r6 送给登记函数 0x81744
更正：「投递消息」和「登记回调」是发送侧并列做的两件事，不是载荷关系。 0x81744 有个 r4 == 1 的「只登记不发送」分支，把 r6 写进 0x417EC 并置 0x3F404 的挂起位；消息体走的是另一条路。 V17「消息首字不是命令码」这个否定结论仍然成立（15 例矩阵否证）， 但「消息 = 回调注册单」这个机制描述要按上面收敛。

2. 找到派发器：单槽 + call [槽]

扫全段 4 字节常量与 ldi 立即数，0x417EC 只有两处引用： 0x81752 写、0x82252 读。读它的那段就是派发器：

0x0008223A  ...             ; 派发器入口（槽0）
0x00082252  ld   r0, @(0x417EC)   ; 从全局单槽取代码指针
0x00082258  call r0               ; 直接调它 ← 「谁调用回调」的答案

而 0x8223A 自己只有一处引用：0x00080606，在启动代码区那张 「事件位 → 处理函数」分派表里（btstl 逐位测，bit2 对应它）。整张表归主循环 0x80588 管，还被 0x805E4 bne +0x50 挡着 —— 只在「没事可干」时才跑。

3. 决定性事实：登记是活的，派发是死的

跑完 24 万步基线（不注入任何 tick），读三个量：

槽0  = 0x0008225E   计数 = 0x000C   标志[0x3F404] = 0x02  *挂起*
槽1  = 0x000822F2   计数 = 0x0008   标志[0x3F40D] = 0x04
主循环 0x80588      覆盖 = False
派发器 0x8223A      覆盖 = False
派发器 0x822CE      覆盖 = False

而且 0x80588 在静态上也没有任何调用者：相对 call 0 个、 jmp 0 个、ldi 引用 0 个、4 字节常量 0 处、A 段向量表里也没有它。 也就是说这块主循环既不是任务、也不是中断入口、更不是被某处直接调用的子程序 —— 在目前这套建模下，它没有进入路径。槽里躺着的回调因此永远等不到那一圈扫描。

边界：「没有进入路径」是在模拟器里的结论，不等于真机上它不跑。 真机可能由某个尚未建模的时钟/中断/协处理器把它拉起来。V18 能报的是 「当前模型里没人调」，不能报「固件设计有缺陷」。

4. 派发器是「倒计时门控」的

借 CPU 真正的 call 语义（FR 的返回地址在 RP，不在栈上）手动调一次派发器， 前 11 圈每圈 10 步、只把计数从 0x0C 减到 1、覆盖 +0；第 12 圈计数归零才真的 call：

tick 11  槽0 0x8225E → 0x82278    632 步   覆盖 +133   ← 真执行
（此前 11 圈：每圈 10 步，覆盖 +0，计数 0x0C → 0x01）
tick  8  槽1 0x822F2 → 0x00000000  165 步   覆盖 +42    ← 槽1 计数 8，跑完把槽清空（一次性）

两种性格很清楚：槽 0 是链式的（每站登记下一站），槽 1 是一次性的（跑完注销）。 「门控是否到点」的判据是调用前倒计时 ≤ 1，不能拿「有没有新覆盖」当判据 —— 派发器自己的序言第一次跑也会带来十来个新地址，那不是回调被执行。

整条回调链（静态反汇编 + 动态走通）

0x0008225E  → 登记下一站 0x82278
0x00082278  → set_flg(9, 0x400)          叫醒任务 9；这一站会把控制权交给调度器
0x00082298  → sta_tsk(6, 1)              建起任务 6
0x000822B6  → set_flg(9, 0x200)          终点，不再登记下一站

这正好补上 V16/V17 的一个缺口：任务 1 轨迹里那个「静态扫不到 set_flg(9,0x400)」 的疑惑 —— 置位的人在这条回调链上，只是链从来没被派发过。

为什么这次涨了？V15 说「事件越多≠覆盖越广」，V17 加了一句「换原语也不涨」， 两次的共性都是在已经走过的路径上重复。V18 涨，是因为它换的是路径： 把一条「静态存在、动态从未执行」的派发链接上。 C 场景再空转 12 万步仍是 +0，也说明涨的不是「多跑了步数」。

6. 口径说明（为什么 CLI 里看到的数字会不一样）

同一条链，预热方式不同，现场就不同：中断口径跑满 24 万步时任务 8 已在 sleep， 一次性 fast 60000 时它还是 dormant；chain 能走几站因此不同。 所以本报告的增量一律只跟各自起点比，不跨场景并列「谁比谁多走了多少」。 这与项目里「A / B 模式数字不能混比」是同一条规矩。

8. 边界与下一步

能报不能报
  • A 段有两套对称单槽，派发器是 call [槽]，倒计时门控
  • 基线里槽已登记、主循环与两个派发器均从未执行（静态也无调用者）
  • 手动注入 tick 后链走完四站、覆盖 +507、任务 6 被 sta_tsk 建起
  • 槽 0 链式 / 槽 1 一次性
  • 真机上是谁、在什么时钟下把主循环 0x80588 拉起来（本版最大 OPEN）
  • 回调各字段的业务含义、这套链对应哪个硬件事件
  • 「相机跑起来了」—— 任务 7 / 10 / 12 仍 dormant，任务 5 仍在等消息
  • 把「手动 tick」说成「固件自己在跑」：这是外部注入，不是自运行
V17 的另一个 OPEN（任务 5 叫醒后卡在 flag @0x0A635A）在 V18 里有了更具体的落点： 第一轮的 set_flg(flg2,0x4000) 是任务 1 在投递之前开的， 而这条回调链里的 set_flg(9,0x400) / set_flg(9,0x200) 是另一路闸门。 把「谁该提前开闸门」和「主循环谁拉起来」放在一起看，可能是同一块缺失的建模。
