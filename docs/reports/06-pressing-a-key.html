把按键按下去：D300 固件按键链路的解剖与注入实验

模拟器第 8 轮 · 2026-10-16 · 固件 B3000111.bin（Ver.1.11，2013/04/11）· 全部数字来自实跑
一句话结论：按键这条线我打通了——从引脚电平、外部中断、内核事件标志，到消抖、状态机、显示更新函数，整条链路都拿到了反汇编级的一手证据，并且能精确控制按几次（按 30 次，中断就被接受 30 次）。
但是：按下去之后，固件仍然没有画出任何东西——显示更新函数确实跑了，可它写出来的「显示对象数组」9 个槽位全是 0、命令队列全是 0。这不是模拟器缺功能，是固件自己判定"此刻没有要画的界面"。

一、先修掉两个坑（一个是我埋的，一个是上游的）

坑 1：中断请求永远撤不掉

我给外部中断通道 3 发请求后，2000 万步里的系统调用从基线 743 次暴涨到 6 万多次（按键驱动上是 63,301 次，点火驱动上是 64,160 次），最终 PC 卡在 0x42A34。一开始我以为是"固件被唤醒了"，做了剂量-反应曲线才发现不对：点火 1 次 = 759（≈ 基线 743 + 16），点火 2 次及以上全部 = 64,160，完全饱和。

根因在模拟器的中断控制器里：

public void removeEdgeTriggeredRequest(InterruptRequest interruptRequest) {
    // empty, because all FR interrupts are all level-triggered
}

而 CPU 派发中断的地方只调了这一个撤销函数：

platform.interruptController.removeEdgeTriggeredRequest(interruptRequest);   // 空实现
((FrInterruptController)platform.interruptController).processInterrupt(...);

也就是说请求一旦进队列就再也不会出队列。中断服务程序返回后，请求还在，CPU 立刻再次进入——无限重入。真实的按键是边沿触发：CPU 响应一次就该撤掉。修法是等 CPU 真正接受（PC 进入向量入口 0x42A2C）之后立刻调 removeRequest(0x13)。

坑 2：写内存根本没用，引脚值被外设模型拦截了

修好坑 1 之后，我扫了端口 8 个位（0x01 到 0x80）逐个模拟按键，结果八组数据一字不差：都是 761 次系统调用、14 个改写块、界面文字读 56 次。这不可能是对的——按不同键不该完全一样。

查下去发现，引脚端口的读走的是这条路：

所以我往 0x50000107 写字节（哪怕绕过监听器直接写页面数据）固件一个字都看不到。正确的注入点是 platform.getIoPorts()[7].getPin(3).setInputValue(1)。

这两条合起来能解释一个很容易误判的现象：如果你只看到"按键之后系统调用暴涨 80 倍"，会以为固件活了；其实是 ISR 在无限重入。判断按键是否真的生效，只能看"中断被接受的次数是否严格等于按键次数"。

二、按键链路：从引脚到显示更新

2.1 中断现场（进入空闲任务后 dump）

寄存器值含义
EIRR0（0x40）0x00无待处理请求
ENIR0（0x41）0x4D = 0100 1101只开了外部中断通道 0、2、3、6
ELVR0（0x42）0xAFAB各通道的触发边沿配置
端口 P7 方向P0–P7 全为输入8 条引脚线都是输入

四个使能的通道里，#0x10/#0x12/#0x13 的入口在内核小桩（0x42xxx），只有 #0x16 的入口在应用层。逐个点火试下来，只有通道 3（请求号 0x13）的桩里带着完整的按键语义。

2.2 中断服务程序 0x17584C

0017584C  ST      RP,@-R15
0017584E  LDI:32  #0x9F5A31E8,R0
00175854  BORL    #0x8,@R0          ; RAM 标志置 bit3 = 「有按键」
00175856  LDI:32  #0x0004049E,R12
0017585C  CALL    @R12              ; 内核调用
0017585E  LDI:20  #0x00041,R0
00175862  BANDL   #0x7,@R0          ; ENIR0 &= ~0x07 → 关掉通道 0/1/2
00175864  LDI:8   #0x0C,R4
00175866  LDI:32  #0x80000000,R5
0017586C  LDI:8   #0xD0,R12         ; 0xD0 = -48
0017586E  EXTSB   R12
00175870  INT     #0x40             ; ★ set_flg(12, 0x80000000)
00175872  LD      @R15+,RP
00175874  RET

一共做三件事：置一个 RAM 标志、关掉另外三个外部中断通道（防抖期间的互斥）、然后调 set_flg(12, 0x80000000)。事件标志 12 的 bit31 就是"有按键"。

2.3 消抖函数 0x175876（标准到可以直接抄进教科书）

00175876  LDI:32 #0x50000000,R7
0017587C  LDI:8  #0x00,R5                 ; 稳定计数清零
0017587E  LDI:20 #0x00107,R13             ; 端口偏移 0x107 → 地址 0x50000107
00175882  LDUB   @(R13,R7),R6
00175884  LSL2   #12,R6
00175886  LSR2   #15,R6                   ; 净右移 3 → R6 = bit3
00175888  LDI:8  #0x0A,R4
0017588A  LDI:8  #0xDB,R12                ; 0xDB = -37
0017588C  EXTSB  R12
0017588E  INT    #0x40                    ; ★ tslp_tsk(10) 睡 10 个 tick
00175892  LDUB   @(R13,R7),R4             ; 再读一次
00175898  LSL2   #12,R4 / LSR2 #15,R4     ; 还是 bit3
0017589C  CMP    R6,R4                    ; 和上次比
0017589E  BEQ    0x001758A6               ; 相同 → 计数 +1
001758A0  LDI:8  #0x00,R5                 ; 不同 → 计数清零重来
001758A6  ADD    #0x1,R5
001758A8  CMP    #0xA,R5                  ; 连续 10 次一致才算稳
001758AA  BLT    0x00175888
001758AC  LDI:20 #0x00040,R0
001758B0  BANDL  #0x7,@R0                 ; EIRR0 清 bit3 → 撤销本次请求
001758B8  CMP    #0x0,R4
001758BA  BNE:D  0x001758C0               ; 注意这是「延迟分支」
001758BC  LDI:8  #0x03,R5                 ; 延迟槽，必执行
001758BE  LDI:8  #0x02,R5                 ; 不跳转时才执行
001758C0  LDUH   @R0,R1                   ; ELVR0
001758C6  AND    #0xFFFFFF3F,R1           ; 清掉通道 3 的两位
001758D6  STH    R1,@R0                   ; 按 R5 重设触发边沿
001758DC  LDI:20 #0x00041,R0
001758E0  BORL   #0x8,@R0                 ; ENIR0 |= bit3 → 重新打开通道 3
001758EA  RET
这里有一个 FR 的坑，不拆开看会读反。BNE:D 是延迟分支，0x1758BC 那条指令无论跳不跳都会执行。所以真实语义是：电平为 1（键还按着）→ R5 = 3 = 下降沿，等松开；电平为 0（已松开）→ R5 = 2 = 上升沿，等下次按下。逻辑完全自洽。

2.4 按键状态机 = 任务 6，入口 0x175192

001751B4  LDI:8  #0xD1,R12 ; INT #0x40   ; clr_flg(12, ~0x80000000) 先清标志
001751C4  CALL   0x00120064              ; 按键 GPIO 初始化
001751C6  BORL   #0x8,@R11               ; 0x9F5A31E8 置「有按键」
001751D6  BTSTH  #0x4,@R0  ; 0x9F58D40C  ; 忙等某个状态位
001751E4  LDI:8  #0x14,R4 ; LDI #0xDB,R12; tslp_tsk(20)
001751F4  BTSTL  #0x2,@R0 ; 0x9F58D02D   ; 再等
001751FE  BTSTL  #0x2,@R0 ; 0x50000104   ; 读另一条引脚
0017520A  CALL   0x00120000              ; 读按键矩阵
00175212  LDI:8  #0x40,R4
00175214  BANDL  #0x7,@R11               ; 清「有按键」
00175216  CALL   0x00198004              ; ★★ 调显示更新
0017521E  LDI:8  #0x0C,R4 ; 0x80000000,R5
00175226  LDI:8  #0xD0,R12 ; INT #0x40   ; ★ set_flg(12, 0x80000000)

这就是完整的按键主循环：读矩阵 → 调显示更新 → 置事件标志 → 消抖。而 0x198004 就是我要找的显示出口。

三、实测：按下去之后发生了什么

参数：40,000,000 步确定性仿真，第 3,151,747 步进入空闲任务后激活定时器，从第 5,000,000 步开始按键，每次按下保持 200,000 步再松开。

四、决定性的一刀：显示对象数组是空的

光看计数不够。我把显示相关的 RAM 整块 dump 出来（0x9F5A0000 起 32KB）逐字节查：

地址内容
0x9F5A311001 —— 0x198004 写的「画面已更新」标志，说明显示更新函数跑了
0x9F5A0CC011 条 4 字节指针（每条重复 2 次）的图层表，指向 0x9F56206C、0x9F55D260… 已初始化
0x9F5A0F60显示对象数组（= 0x9F5A0D00 + 0x260，9 个槽 × 18 字节）—— 全部为 0
0x9F5A10F0显示命令队列（= 0x9F5A0D00 + 0x3F0，显示任务 19 从这里取命令）—— 全部为 0
0x9F5A320723 字节残留：02 00 00 04 3D 63 62 62 28 63 63 03 E7 63 62 62 28 63 63 03 E7 88 02（格式未解码）
这就是最终答案。显示更新函数被调用了、图层表初始化好了、"画面已更新"标志也置上了，可是它往显示对象数组里一个东西都没写，命令队列也是空的。固件判断"当前没有要显示的界面"，于是整条显示链路空转。

这不是模拟器的锅。真机上开机后屏幕是要亮出拍摄信息的，而模拟器里没有镜头、没有存储卡、没有电池组、没有 EXPEED 的真实应答，UI 状态机根本没走到"要画菜单"的分支。

一条必须自我证伪的旁证

我在统计里看到"界面文字区（0x1C0000–0x1E0000）被读了 56 次（20M 步）/ 133 次（40M 步）"，一度以为按键触发了文字读取。这是错的，我把读它的地址全 dump 出来验证：

  • 0x001C0244（8 次）→ 内容是 00 02 01 03 00 02 01 03，不是文字
  • 0x001CFDE7（8 次）→ 28 28 29 2A 2B 2C 2D 2E 2F 30 31 32 32 32 32 32...，一张带连续段的查表数据
  • 0x001CFEA7（40 次）→ 混合二进制，不是文字

而且读它们的 PC 是 0x19ECD4/0x19ECDC/0x19ECE8/0x19ECF8/0x19ED02/0x19ED0C——全都在 0x19ECC0 那个 EXPEED 心跳查询函数里（第七轮已确认它每约 178 万步发一次 0xA6 查询）。读取次数只随步数增长、与按键次数完全无关。
另外，菜单/帮助文字池（0x3A0000–0x3B0000）全程读取 0 次。

下一步能做的（按性价比排序）

  1. 解码 0x9F5A3207 那 23 字节命令流。它是目前唯一一段真实的、格式未知的显示数据，解出来就能知道 B 段给显示模块的命令长什么样。
  2. 伪造外设应答把 UI 状态机推过去。显示对象数组之所以全 0，是因为上游状态位（如 0x9F58D40C、0x9F58D02D）没有置起来。找出它们依赖的外设（镜头/存储卡/电池），逐个打桩。
  3. 给 5 个绘制子模块做单元测试。直接调 0x19A27A 并手工填好图层表，看它能不能往 0x9F5A0F60 写出对象——这是"让固件自己画东西"最短的一条路。
