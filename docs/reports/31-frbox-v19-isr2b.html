仿真台 V19：那条没人拉的中断线

向量表第 0xD4 项 · 14 字节待办标志 · 61 个开关 · 回调链自己走完四站

61一个中断里的位开关

一句话：V18 把 0x80588 读成「一段没有被接线的后台主循环」。 V19 翻向量表发现它是 INT 0x2B 的处理函数（向量表第 0xD4 项）， 一个把 0x3F402–0x3F40F 这 14 个待办标志字节逐位分派的大家伙， 61 个开关后面挂着 57 个处理函数。V18 说「静态上找不到调用者」是对的 —— 它不是被 call 进来的，是被中断打进來的。把这条线接上， 两个回调槽不用再手动 tick 就自己往前走，一路走到第四站、计数归零、标志位清零。

1. 先更正 V18 的三处读法

V18 的观测没错，错在「它是什么」这一步：因为查不到静态引用，就把它当成了 「没有调用者的后台调度器」。真实的接线一直在向量表里。

问题V18 的说法V19 实测
0x80588 是什么主循环（无从进入的后台调度器） INT 0x2B 的处理函数：向量表 0xFFF50 = 0x00080588
向量表里有没有它没有 有，而且就是这一项。TBR = 0x000FFC00，索引 0xD4 → n = 255-0xD4 = 0x2B
静态上有没有调用者相对 call 0 处、jmp 0 处、ldi 立即数 0 处 这条是对的 —— 中断处理函数本来就不需要 call。它的「调用者」是 ICU
ICR 里这条线配过没有没查 配过：0x45B（= 0x440 + (0x2B-0x10)）的值是 0x1A，级别 26
为什么容易漏：A 段向量表在文件里的偏移是 0x7FC00， 但它映射到的地址是 0xFFC00（A 段 ROM 从 0x80000 起）。 整条线索里最容易被当成「地址」直接用一次，就用这个偏移。 按地址查 0xFFF50，第一眼就能看到 0x00080588。

2. 证据链：从向量表到 reti

向量表 0xFFF00 起（每项 4 字节，倒序：索引 i 对应 INT n = 255-i）

  000FFEFC: 000FE3C0     ← INT 0x40，μITRON 陷阱入口（V10 起一直在用）
  000FFF00: 000FE776     ← INT 0x3F，调度请求（V10 实测的派发点）
  000FFF04: 0008129C  …  000FFF4C: 000FE250（兜底 = 没接线）
  000FFF50: 00080588     ← 就是它：索引 0xD4、INT 0x2B
  000FFF54: 00080EF6  …  000FFF6C: 00080DDA

处理函数本体 0x80588–0x80968（994 字节 / 378 条指令）：

  0x80588  8EFF  stm0  #0xFF        ; 压 r0–r7
  0x8058A  8FFC  stm1  #0xFC        ; 压 r8–r13
  0x8058C  1784  st    r4,@-sp
  0x8058E  1785  st    r5,@-sp
  0x80590  1781  st    r1,@-sp      ; 存 RP
  ……
  0x8095C  D006  call  0x8096A      ; 尾声子程序（0x3F403 那 7 位在这里分派）
  0x8095E  0781  ld    r1,@sp+
  0x80960  0785  ld    r5,@sp+
  0x80962  0784  ld    r4,@sp+
  0x80964  8D3F  ldm1  #0x3F
  0x80966  8CFF  ldm0  #0xFF
  0x80968  9730  reti

入口是 stm0/stm1 压栈、出口是 reti —— 这是 A 段 39 个 ISR stub 的同款模板（V8 就记过）。顺带把方向也定死了： 0x80588 跟另外 38 个落在 0x809BE–0x8129C 的 stub 挤在同一片代码里， 是「一批中断处理函数中的一个」，不是主程序。

3. 它长什么样：14 字节待办标志 + 61 个开关

整个函数就是一条长长的「测位 → 装函数地址 → 间接调」流水线。命中就 ldi:20 r12,#处理函数 再 call @r12；没命中就跳过。 14 个标志字节全部用上，一共 61 条位测试（主路径 54 条 + 尾声子程序 0x8096A 里专管 0x3F403 的 7 条），指向 57 个不同的处理函数。

两处高亮就是 V18 找了半天的派发器：0x3F404 bit1 → 0x8223A（槽 0）、 0x3F40D bit2 → 0x822CE（槽 1）。它们一直是这张表里的两格， 只是这张表所在的函数从来没被执行过。

读这张表有个坑（V15 那条铁律）：btstl #u4 的立即数是掩码不是位号 —— btstl #2 测的是 bit1，btstl #8 测 bit3； btsth #u4 才是 u4 << 4（btsth #4 测 bit6）。 按「立即数就是位号」读，这 61 条会整体错位一轮，还会把两个派发器错到别的字节上去。

还有个小发现：有 5 个位指向同一个 0x8095C（0x3F405 bit7、0x3F408 bit0、0x3F409 bit4、0x3F40A bit7、0x3F40B bit4）。那不是处理函数， 而是尾声的起点 —— 它先 call 0x8096A，再恢复寄存器、reti。 换句话说：这 5 个位是「有事，但不用做处理」的位，代码借尾声当空实现。

4. 接上这条线：回调链自己走

用固件自己配的级别（ICR = 0x1A）请求一次 INT 0x2B， 立刻进 0x80588，300 步跑完、干净地 reti 回来，带来 299 个新执行地址。 连请求下去，两个回调槽就有了自己的节拍：

1300+2990x8225E / 计数 12（这一趟还没走到 0x80602 那格）
2601+5430x8225E / 计数 11（第一次轮到派发器）
241196+1330x82278 / 计数 10（第一站点火）
44678+130x82298 / 计数 8
60711+360x822B6 / 计数 30
120——计数 0、0x3F404 清成 0x00，链注销

节拍是「每两次中断减一格」，不是每次：派发器会把 0x3F404 的 bit1 清掉 （0x8224C 的 bandl），再由 0x81A1E 的 borl 重新置上； 而那个重新置位本身也受别的位门控，所以平均下来两拍一格。

5. 把 7 个 dormant 任务一起放开

沿用 V16 的 taskboot，让 REALOS 自己创建那 7 个平时不起来的任务， 再接 240 次中断：

执行地址服务调用任务状态
起点323557 4 ready / 8 ready / 9 flag / 1·2·3·11 flag / 6·7·10·12 dormant
240 次中断后5209（+1974）301（+244） 6 ready / 9 ready / 4 ready / 8 ready；7·10·12 仍 dormant

V15 那条「任务 4 被任务 8 的忙等饿死」在这里不成立了：任务 6 经 0x82298 那一站的 sta_tsk(6,1) 起来之后，就绪队列的构成变了， 任务 4 拿到了 ready。这条只能说明「在注入的中断节拍下它不再饿」， 不能反推真机上的调度顺序。

6. 新的一道墙：0x174 的握手

不替外设答话，第 9 次中断就会一去不回。卡点在 0x9C94A 这个函数里 （ISR 里的 0x80782 和别处的 0x81538 都调它）：

0x9C974  9020      borl  r0,#2      ; 先把 0x174 的 bit1 置上（发出请求）
0x9C976  9B000174  ldi:20 r0,#0x174
0x9C97A  8940      btsth @r0,#4     ; 等它的 bit6（等应答）
0x9C97C  E2FC      beq   -4         ; 没应答就回去再读一遍

这是一个最朴素的外设握手：写请求位、轮询应答位。我们的模型里 0x174 只是一个普通字节，bit6 永远是 0，于是 beq -4 自转 —— 前 8 次能过，是因为走到这条分支上还需要别的把手凑齐。

所以 --no-answer 才是诚实的默认观测：它把「卡在第 9 次」这个事实摆出来。 answer=True（默认）会在 0x9C97A 那一条上往 0x174 写 0x40， 即假装外设答了一句「好了」。这一句是人替它答的，报告里必须写清楚， 不能读成「固件自己能过」。

7. 怎么用

# 接上 INT 0x2B 跑 240 次，同时在 monitor 里看槽
python -m frbox -M d300-a --realos 1 --cov --cb --irq2b 240

# 不替外设答话：看它卡在哪一条
python -m frbox -M d300-a --realos 1 --cov --cb --irq2b 20 --no-answer

# monitor 里
irq2b            # 接线情况：向量项 / ICR / 14 个待办标志
irq2b 240        # 请求 240 次
irq2b off 20     # 请求 20 次，但不答话

代码上是 Machine.enable_isr2b() → frbox.isr2b.Irq2B： raise_once() 请求一次并跑到 reti，burst(n) 连请求， state() 看接线与待办标志，table() 静态解出那 61 条位测试。

8. 口径与边界

数字口径（重要）：V19 的预热是 12 × 5000 步、不注入 vec 0x13/0x19， 基线覆盖 1,443；V18 的预热是 40 × 5000 步、每批喂一次事件位， 基线是 6,382。两套数字不能相减，本页所有 +N 都是各自基线内的增量。

结构14 字节待办标志块 + 61 个位开关 + 57 个处理函数；两个回调派发器各占一格

不能报真机上这条线多久来一次（固件里没有节拍器模型，请求频率是人定的）
