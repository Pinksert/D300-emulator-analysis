D300 固件 1.11：把那 4 处改动真的跑了一遍

函数级仿真台实验报告 · A 固件（A3000110 / A3000111）· 2026-10-12
一句话结论：1.11 新增的那一位（RAM 0x3F81C 的 bit6） 不改变任何光圈行程参数，它只改变一次子程序调用的时机—— 把 0xC0D9E 从「开头」挪到「结尾」（0x3FAF1 不是参数，见文末修订说明）。 而决定行程常量的旧开关（bit3）在两版里行为完全一致。

一、为什么不是 QEMU

  • QEMU 现有目标里没有任何富士通 FR（68k / Alpha / Arm / AVR / Hexagon / HPPA / LoongArch / Microblaze / MIPS / OpenRISC / PPC / RX / SH4 / RISC-V / s390x / SPARC / TriCore / x86 / Xtensa）。
  • QEMU 历史上确实有过 frv，但那是 FR-V —— 一条 VLIW 媒体处理器产品线（FR500/550/1000），和 D300 用的 FR 微控制器指令集不是一回事，而且早已移除。
  • 近年社区还在删冷门目标（moxie、lm32、unicore32 在 6.1 移除），新加 FR 目标几乎不可能进主线。
  • 更根本的：D300 是 A（IO 协处理器）+ B（主控）+ EXPEED 至少三个处理器，整机仿真是个无底洞。

所以走「函数级仿真台」路线：不追求开机进菜单，只把要验证的那段代码拿来单跑。

二、仿真台是怎么搭的

CPU

  • 指令表来自 binutils 的 cpu/fr30.cpu + opcodes/fr30-opc.c（CGEN 生成物）
  • 语义按 fr30.cpu 里的 (dni ...) 定义实现：目标操作数是最后一个；call 返回地址进专用寄存器 RP而不是压栈；:d 是延迟分支
  • 16 个通用寄存器 + CCR + ILM + TBR/RP/SSP/USP/MDH/MDL

环境

  • ROM：0x00080000 起，两版镜像都先过 CRC16/XMODEM 校验（0xC297 / 0x4F36 均吻合）
  • RAM：稀疏内存，初值 0；<0x1000 视为外设，读返回 0、写丢弃并记账
  • 子程序调用、μITRON 服务调用（int #0x40）全部打桩，只记录目标地址和参数寄存器

脚本：解码器/CPU .workbuddy/tmp/fr_emu.py、反汇编 fr_dis.py、 实验 exp_111.py、全扫描 sweep.py。

三、先自检：仿真器跑出来的跳转地址对不对

实验从 0x000DB8F0 起步（两版在该地址的字节完全相同）。跑起来之后，把两版各自"调用了哪些子程序"列出来对照—— 这些目标地址的相对位移，应当与此前用字节比对独立算出的位移表吻合：

1.10 里的子程序1.11 里的对应者位移与位移表是否一致
0x0DB9DE0x0DB9EC+14吻合
0x0E1F3A0x0E1F84+74吻合
0x0DCD260x0DCD70+74吻合
0x0F11000x0F1158+88吻合
0x0C0D9E / 0x0C0E02 / 0x08CA0E同上+0吻合
这不是结论，是自检：解释器如果取指或算分支目标算错了，这些地址不可能同时落在已知位移上。

四、主实验：把那一个字节的 256 种取值全跑一遍

变量只有一个：RAM 0x0003F81C 这一个字节。其余 RAM 变量给固定初值，外设读恒为 0。 每种取值跑一次，按"调用序列 + 写入结果"归类。

1.10：256 种取值 → 只有 2 种走向

决定因素只有一个：bit3

  • bit3 = 0 → 行程常量 0x44AA（17578）
  • bit3 = 1 → 行程常量 0x4631（17969），并多调两次 0xF1100（参数 0x46D）
  • bit6 完全不起作用：0x00 与 0x40 的行为逐字节相同
1.11：256 种取值 → 4 种走向

决定因素变成两个：bit3 × bit6

  • bit6 = 0 → 走向与 1.10 等价
  • bit6 = 1 → 走一条新的路（见下节）

两版在 bit6 = 1 时的差别

1.10（无视 bit6）1.11（bit6 = 1）
开头call 0xC0D9E　（r0 = 0）不调用
结尾call 0xC0E02　（r0 = 0x3FAF1）call 0xC0D9E
call 0xC0E02
行程常量0x44AA / 0x46310x44AA / 0x4631（未改）

对应的机器码（1.11 新增的那两句）

; 1.11 @0x000DB900（开头）           ; 1.11 @0x000DB9C2（结尾）
ldi:20  #0x3F81C, r9                borl    #0x2, @r0        ; 给 0x3FAF1 置位
btsth   #0x4,   @r9   ; 测 bit6  ★  btsth   #0x4, @r9       ; 再测一次 bit6 ★
bne     +6            ; bit6=1 跳过  beq     +6              ; bit6=0 跳过
ldi:20  #0xC0D9E, r12                ldi:20  #0xC0D9E, r12
call    @r12                         call    @r12            ; r0 里残留着 0x3FAF1，但随即被覆盖
btstl   #0x8,   @r9   ; 老判断 bit3  ldi:20  #0xC0E02, r12

btsth #4 的立即数 4 是掩码不是位号：4 左移 4 位 = 0x40 = bit6； 老的 btstl #0x8 不左移，直接就是 bit3。两条指令规则相反，别混着算。

五、这条结论对文章意味着什么

  • 可写1.11 新增的是一个开关（bit6）和一次调用时机的调整，不是光圈行程参数——三个常量 7812 / 17578 / 17969 在两版里都对得上，且都由旧的 bit3 决定。
  • 已解决被挪动的 0xC0D9E 干什么，见第二层报告：它是一个 50 条指令的纯判断函数，唯一输出是 0x3FAE9 的 bit5。
  • 不支持不能据此说"1.11 才支持电磁光圈"——bit3（旧开关）在 1.10 里就已经在选行程常量了，说明电磁光圈通路本来就存在。

六、这份结果的可信边界

打桩了什么：① 所有子程序调用（call）没真正进去，只记地址和 r0..r3，返回时把 r0 置 0； ② μITRON 服务调用（int #0x40）没实现，本次实验里这段路径一次都没触发； ③ 外设读恒为 0（本次实验 0 次外设访问）。

因此：结论只对"这段函数自身做了什么分支判断、按什么顺序调用谁"有效； 每个被调子程序内部干了什么，本次没有验证。另外，扫描只覆盖 0x3F81C 这一个字节， 其他 RAM 变量取的是人为初值——换初值可能暴露别的分支（已验证的是：bit3 与 bit6 之外的 6 个位都不影响走向）。

七、下一步：长期路线（NikonEmulator）

Nikon Hacker 社区有一个现成的 FR 仿真器，源码在 github.com/simeonpilgrim/nikon-firmware-tools 的 Java/Emulator 目录：FrEmulator.java（FR80）、TxEmulator.java（TX19）、 itron/（μITRON 服务调用层）、peripherials/（LCD、按键、串口、SD、JPEG、镜像箱、A/D、时钟、中断控制器、DMA）， 自带 dfr 反汇编器和 FR IDA 插件。要跑 D300 需要自建 platform（内存映射、加载地址、入口点）—— 仓库里现成的示例只有 D3100 / D5100 的 eeprom，那两台是 TX 机型。

  • 2026-10-15 改正：原文表格里「call 0xC0D9E（r0 = 0x3FAF1）」的表述有误。 0x3FAF1 是上一条 borl #0x2, @r0 用剩下的指针残留； 0xC0D9E 的头两条指令 ldi:20 #0x3FAE9, r4 与 ldub @r12, r0 立刻把 r4、r0 全部覆盖，不构成参数传递。 正确说法是「这次调用被从开头挪到了结尾」。
