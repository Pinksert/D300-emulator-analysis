一、这一版解决的两件事

V7 留下了两个“看得见但摸不着”的东西：一是中断表里明明填了回调，却从没验证过回调真的会被调用； 二是任务 1 卡在 0x0DCD2C 等一个硬件就绪位，只能靠手写 poke 绕过。 这一版把两件事都做成了仿真台的正式能力。

  • 中断闭环成立：以「任务 1 跑到第一个卡点」的同一份快照为基点，把 48 个向量逐个注入。 39 个精确 reti 回到注入点且 r15/SSP 逐位复原， 其中 4 个真的走进了应用区回调函数。
  • 忙等自动放行：--autospin 在运行期读轮询指令实际使用的那个寄存器， 把就绪位置 1 后继续。三处忙等全自动认出，包括第三处地址是算出来的那种。
  • 任务 1 跑通到出界：三处放行后走到 4,512 个不同 PC、 56 次 μITRON 服务调用、6 个回调槽。 然后掉到地址 0 —— 这次能说清楚是为什么了（缺的是调度器栈帧，不是硬件）。

二、闭环的判据是什么

「中断能进」和「中断能回来」是两件事，必须分开验。判据定成三条同时成立：

判据怎么测为什么这条不可省
回到注入时的 PC注入前记 home = cpu.pc，跑到 pc == home 为止只测“进过 ISR”会漏掉 reti 弹错地址的情况
r15 逐位复原注入前记 sp0，回来后比对EIT 压栈/弹栈对称性坏了，PC 可能对而 SP 漂移
确实进了回调函数看走过的 PC 集合里有没有槽里的那个地址ISR 有空槽保护，槽空时会静默跳过 —— 看起来“闭环成功”，其实什么都没干
第三条是关键。39 个向量全部闭环成功，但只有 4 个真调到了回调， 其余 35 个走的是默认空 ret。如果只看前两条， 会得出“A 段中断系统全部打通”的错误结论。

结论A 段的中断分发骨架是完整的：EIT 入口 → 每向量一个 stub → 查表 → 空槽保护 → call 回调 → reti。 这套东西不需要我们再补，固件自己写好了。

四、为什么只有 4 个回调被调到

不是分发坏了，是槽只在特定时刻才被填上。任务 1 跑到第一个卡点时写了 6 个槽， 但那份快照对应的时刻，0x3C 那条还走不到它的回调分支（见下节）， 其余 8 个槽要等任务继续往下跑才会填。

口径提醒：「39 个闭环」说的是中断通路通了； 「4 个回调」说的是这一时刻有 4 个业务函数被调用。 两个数不能合成一句「A 段中断系统完成度 39/48」之类的话。

五、vec 0x3C 是个特例：状态位驱动的双分支

这个 ISR 不查一个槽，而是按两个状态位分别查两个槽：

  0x0811E6  btsth #4, @0xAD     ; 测 0xAD 位6
  0x0811F8  ld   @0x3F0D0        ; 分支 A 的槽（实测为空）
  0x08120A  btsth #8, @0xAD     ; 测 0xAD 位7
  0x08121C  ld   @0x3F0D4        ; 分支 B 的槽 = 0x0E2D1C
0xAD 取值步数回原位走 A 支（0x3F0D0）走 B 支（0xE2D1C）
0x0020是否否
0x4023是否否
0x5030是是否
0x8023是否否
0xA053是否是
0xF063是是是

三条读法：

  • 只有 0xAD 的位7 和 位5 同时置位（0xA0）才走 B 支去调 0x3F0D4
  • 位6 + 位4（0x50）走 A 支，而 A 支的槽 0x3F0D0 是空的 —— ISR 里自带空槽保护（ld → cmp #0 → beq），所以不会跳到地址 0
  • 位6 和位7 都置位时两条支路都走，步数 63，是三者之和再减去共用序言/尾声
这就是“注入一律成功但回调有时没被调”的真正原因：业务分支由外设状态位决定，不是由向量编号决定。 仿真台要复现真机的行为，就必须能控制这些状态位。

六、自旋消除器：不用再手抠地址

6.1 为什么需要它

任务 1 跑到第一个硬件等待后就不动了。此前绕过它的办法是手工 poke： 先看它轮询哪个地址、哪一位，再写进去。三处卡点意味着要手工做三遍， 而且第三处的地址是寄存器算出来的，静态根本看不出来。

6.2 做法

判据：同一个 0x100 地址窗口内连续 N 步没离开，就算自旋（默认 N = 3,000）。

自旋成立后，不是猜，而是按固定顺序反解：

  1. 反汇编自旋窗口内的实际指令范围（注意范围要取 lo..hi 而不是固定 0x30 字节，否则会越过循环边界取到外面的常量）
  2. 找 btsth/btstl，取它的 u4 立即数 —— 那是掩码的半字节，要 u4 << 4 才是真掩码
  3. 找窗口内第一条 ldi，拿它的目标寄存器 —— 那是被轮询的地址寄存器
  4. 地址 < 0x1000 就走直接页影子存储，否则走内存
  5. 把该位置 1（不是清零、不是取反），然后继续

6.3 实测结果

自旋消除器：3 处轮询 / 3 个不同就绪位 / 共注入 3 次
  #  轮询指令   自旋点     方式   寄存器  等待位   旧→新      第几次  发生在
  1  0x0DCD30  0x0DCD30  直接页    0x0AF   0x80     0x02→0x82  1      14,776 步
  2  0x09C97A  0x09C97A  直接页    0x174   0x40     0x02→0x42  1      17,931 步
  3  0x0CE134  0x0CE134  直接页    0x524   0x40     0x02→0x42  1      33,771 步

第三处是关键：它的地址 0x524 是 r8 算出来的， 静态扫描扫不到，之前的自动消除器也抓不到。这一版改成“运行期读轮询指令实际用的寄存器”，才把它解出来。

八、最后为什么掉到地址 0

停点是 PC = 0x00000000，故障判定报「取指落在不可执行区」。 往回追两条指令：

  0x080502  ld  @r15+,rp     ; 从栈里弹出 RP，弹出来是 0
  0x080504  ret              ; 跳到 RP = 0

这条 ret 用的 RP 是刚从栈里弹出来的，而那个位置从来没被写过，读到 0。 所以这一帧的「保存的 RP」本来就是 0。

这不是硬件没建模。0x080522 那段初始化（往直接页 0x420–0x435 写 8 个配置字节）是真执行完的。

问题在 boot_task 造出来的上下文本身：REALOS 启动一个任务时会先给它铺一层栈帧 （保存的 RP、初始 PS、任务参数与退出例程地址），boot_task 只设了 PC/SP/r4，那层帧是空的。

边界可以说「A 段应用区跑起来了」——4,512 个 PC、56 次服务调用、6 个回调槽都是真的。 不能说「A 段任务能正常退出或循环」——还没到能验证那个的程度。

九、这一版新加的故障判定

以前跑飞之后会闷头执行一堆 0，看起来“还在跑”。现在多了一条硬判据： 取指地址必须落在可执行区（ROM 或已映射的 RAM），否则立刻停下并记下 (地址, 原因)。这个判据直接抓出了 0x080504 那个 RP=0 的问题 —— 在此之前它表现为“跑了很久但 PC 数不再增长”。

  故障：PC=0x00000000  取指落在不可执行区

十、这一版修掉的一个真 bug

monitor 的 irq fire 曾经把中断请求发了两次（先 raise_irq， 后面调 irq_return 时又发一次）。后果是：第一次注入留下的第二条请求会污染下一次注入， 表现为「连续注入两条，第二条的观测数据不对」。

修法是把采样和注入合成一个不可分的动作，由 irq_return 内部负责 home / sp0 的采样，调用方不再自己发请求。

十四、一句话总结

中断这件事，V7 只证明了表填对了；V8 证明了表被用上了—— 以同一快照为基点注入 48 个向量，39 个精确 reti 回原位、SP 逐位复原， 4 个真的进了应用区回调。
忙等这件事，V7 靠手抠地址绕过；V8 换成运行期反解轮询寄存器，三处全自动认出， 其中一处地址是算出来的。
放行之后任务 1 从 500 个 PC 涨到 4,512 个，然后停在 0x080504 的 ret 上 —— 而这次能明确说出： 缺的不是硬件，是调度器给任务铺的那层栈帧。
