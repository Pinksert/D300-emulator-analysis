一、为什么先修尺子

上一版能得出"bit6 是新增开关"的结论，靠的是解出来的调用地址和位移表对得上。但那个自检只证明 取指和分支算对了，不证明算出来的数是对的——寄存器值、标志位、负偏移寻址任何一处错了， 分支就会走到别的路上，而位移自检照样通过。真调用之后这一点变得致命：走进去的每一层都依赖上一层算出来的参数。

二、修掉的 7 处语义错误

判据不是"我觉得"，而是三份可对照的源头：富士通 FR80 手册（CM71-00104-3E）、 binutils 的 fr30.cpu 语义定义、以及 NikonEmulator 的 Java 实现（社区已在真机上验证过）。 三份对得上才改。

三、自检：不是"能跑通就算"

自检不手写机器码，而是从指令表里反查编码（穷举 65536 个字，找到"助记符 + 指定操作数"对应的那一串）， 再把编好的指令写进 ROM 让 CPU 真执行。这样测的是解释器，不是我的记忆。

除法：用编译器真的会生成的那条序列

DIV0S R2 → DIV1 R2 ×32 → DIV2 R2 → DIV3 → DIV4S      ; 商在 MDL，余数在 MDH

9 组数：1000/7、−1000/7、1000/−7、−1000/−7、0x7FFFFFFF/3、−1/1、123456/−789、0/5、−2147483648/2。 18 个断言（每组商 + 余数）全部命中，含向零截断和余数符号。

其它 20 项

  • 加法溢出：0x7FFFFFFF+1 → 结果 0x80000000、V=1、N=1
  • 减法借位：5−7 → C=1、N=1（修好第 2 条之前这里是 0）
  • SUBN 结果对但不改 Z；AND 清 V 且置 Z
  • LSL/LSR/ASR 各一组，含算术右移的符号位填充
  • ld/st @(−4,R14)：R14=0x00040000 时确实访问 0x0003FFFC（修好第 5 条之前访问的是 0x00040FFC）
  • XCHB 后 R0 = 0x112233AA（高 24 位保留）；LDI:8 #0xFF = 0x000000FF（无符号）
  • PS 写入 0x00050223 能原样读回

这个审计的价值在于"穷举"：不用猜固件里会不会用到某条指令，直接问"这个编码能不能执行"。 902 个未定义编码集中在 0x0720–0x077F、0x9Fxx 等 FR30 的保留区， 固件的正常代码路径上没碰到过。

顺手和 Java 实现逐编码对了一遍

把 NikonEmulator 的 FrInstructionSet.java 里 223 条"基址 + 掩码 → 助记符"表拉出来， 和我的解码器对 65536 个编码逐个比较：1172 个不一致，逐类查过之后没有发现真分歧——

  • Java 那边没收录：LDRES / STRES（Java 源码里注掉了）、部分 MOV 形式；
  • 我喂的数据不够长：比较时只给 2 个字节，LDI:20（4 字节）和 LDI:32（6 字节）自然解不出来；
  • 只剩一族真差异：Java 有 SRCH0 / SRCH1 / SRCHC（0x97C0/97D0/97E0），binutils 的 FR30 表里没有。 A 段里这三个编码共出现 3 次，逐一看过——全部落在 ldi:20 的立即数里，不是指令。
另外一个小差异：对"专用寄存器编号 6–15（未定义）"的 mov，我这边仍会解码，Java 会拒。 固件的编译器不会生成这种编码，不影响结果。

五、μITRON 层：不再死在 int #0x40

D300 的 A 固件用 INT #0x40 进 Softune REALOS/FR 内核，服务号放在 R12 的低 8 位（负数）。 以前一碰到它就停；现在接了社区仓库里那份 58 条的服务号 → 函数名映射，按"返回 E_OK"处理，并把每次服务调用记进调用树。

于是能看到这段代码在等什么：sys_clr_flg（清标志）、 sys_wai_flg（等标志，对象在 0x3F820）、sys_sta_tsk（起任务）。

六、真调用能走多深

先纠正一个前提：0x000DB8F0 只是窗口起点，不是函数入口。真正的入口是 0x000DB8EA——它的前两条是 ld r8,@R15+（从调用者栈上取第 5 个参数） 加标准序言 stm1 / st RP / enter。从入口跑，函数才能正确 ret 回哨兵地址。

七、回归：之前的结论没有被推翻

修了 7 处语义之后，把 0x3F81C 的 256 种取值重跑一遍：

  • 1.10 仍然是 2 种走向，只由 bit3 决定（0x44AA / 0x4631，bit3=1 时多两次 0xF1100(0x46D)）
  • 1.11 仍然是 4 种走向，由 bit3 × bit6 共同决定
  • 三个行程常量 7812 / 17578 / 17969 两版一致——"1.11 改的是调用时机不是行程参数"这个结论站得住
唯一被推翻的是措辞：不能写"带着 0x3FAF1 去调用"。 真调用证实 0x3FAF1 只是上一条 borl #0x2,@r0 残留的指针， 0xC0D9E 的头两条 ldi #0x3FAE9,r4 和 ldub 就把它盖掉了； 连 0xC0E02 都不读 r0（它自己第 4 条就 ldi:8 #0,r0）。这一点与第二层报告的修订一致。

八、还没做的（别当成"已经能跑固件"）

  • 没有外设：0x00000000–0x00000FFF 读恒 0、写丢弃。镜头通信、定时器、串口都没建模，所以任何依赖硬件的状态机只能走到"永远读到 0"这一支。
  • 没有中断控制器：只做了 int #0x40 的陷阱式服务调用，硬件中断（IRQ）不进。
  • 902 个未定义编码没有逐个判定归属（这轮只确认了"固件正常代码路径上没遇到"）。真遇到时解释器会明确报"无法解码 @地址"，不会静默算错。
  • 调用深度上限 5、单次 50 万步；超出就退化成打桩并记账。
  • 上次结论的边界仍然成立：0x3FAE9 那个 bit5 被谁消费，还没跟。
