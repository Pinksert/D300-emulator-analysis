# D300 Firmware Emulator Analysis

把尼康 D300 相机的固件放进模拟器里跑，看它到底做了什么。

这里有两套东西，目标不同：

| | **frbox 0.57.0** | NikonEmulator 驱动 |
|---|---|---|
| 是什么 | 纯 Python 写的 **D300 专用全系统模拟器**（FR CPU + 总线 + 外设 + 中断 + 快照 + 自旋消除 + monitor） | 给上游 [NikonEmulator](https://github.com/nikonhacker) 写的 18 个实验驱动 |
| 跑什么 | D300 的 **A 段**（IO 协处理，512 KB）和 **B 段**（主控，7 MB）整机 | B 段为主，函数级打桩 |
| 要不要装东西 | 不要，标准库就行 | 要 JDK 8 + 编译上游 + 打 5 处补丁 |
| 代码 | [`emu/`](emu/)　·　设计文档 [`docs/03-frbox.md`](docs/03-frbox.md) | [`drivers/`](drivers/) |
| 什么时候用 | 想看指令级执行、中断进出、内存映射、快照回放 | 想复现 2026-10 那批显示管线/总线实验 |

**这不是一个"能开机出画面"的模拟器**，原因写在 [`KNOWN_ISSUES.md`](KNOWN_ISSUES.md)：
固件起来之后停在「等外部事件」上（任务 4/5 等消息、任务 9 等标志位），
而按键、存储卡、测光这些外设模型还没有。
它是一份**逆向过程的记录**：哪些链路已经走通、卡在哪一位上、踩过哪些坑。

**仓库里没有任何 HTML 文件。** 69 份报告全部只留在本机（根目录中文名），
仓库只留文末那张「报告索引」表 ——
每份报告的主题和结论都写在表里，读表就够；要细节再回本地开原文。

## 30 秒上手

```bash
git clone https://github.com/Pinksert/D300-emulator-analysis
cd D300-emulator-analysis/emu

python -m frbox -M help                              # 两台机器
python -m frbox -M d300-a -c "bp 0xFE50C;c;info"     # A 段跑到启动链尽头（43,446 步）
python -m frbox -M d300-b -c "bp 0x407D8;c;info"     # B 段跑到复位链尽头（191,518 步）
python -m frbox -M d300-a -c "tasks"                    # REALOS 任务表（入口 / 栈顶）
python -m frbox -M d300-a --itron-block --autoevent --autospin \
       --task 0x8133A::0:0x80506 --task-from-table --rp 0x81338 \
       -c "c 200000;info;svc"                            # 任务 1 跑完整条启动链
python -m frbox -M d300-a --realos 1 -c "c 300000;realos"
                                                        # 走固件自己的内核（V10 起）
python -m frbox -M d300-a --realos 1 --events 4096 \
       --bits 0x0110:0x13,0x19:2048 --flow -monitor none \
       -c "fast 200000; tasks"                          # 喂事件位图 → 固件自己拉起任务 8（V14）
python -m frbox -M d300-a --realos 1 --events 4096 --cov \
       -monitor none -c "fast 120000; cov 96; readyq"    # 覆盖率 + 就绪队列（V15）
python -m frbox -M d300-a --boot 2 --realos 1 --events 4096 --cov \
       -monitor none -c "fast 80000; unlock 2; tasks"    # 让 REALOS 自己建任务 2，看它的轨迹（V16）
python -m frbox -M d300-a --realos 1 --msg --flow \
       -c "fast 60000; msg send; flow 12; tasks"         # 借固件内核投一条消息（V17）
python -m frbox -M d300-a --realos 1 --cb --flow \
       -c "fast 60000; cb; cb tick 13; cb"               # 替 0x80588 手动扫一圈回调槽（V18）
python -m frbox -M d300-a --realos 1 --cov --cb --irq2b 240 \
       -c "irq2b"                                        # 接上 INT 0x2B，回调链自己走（V19/V20）
python -m frbox -M d300-a --realos 1 --cov --cb --auto-irq2b 1024 \
       -monitor none -c "fast 100000; autoirq; tasks"    # 周期时钟：中断自己来（V21）
python -m frbox -M d300-a --realos 1 --cov --cb --irq2b 20 --answer  # 硬写完成位（V19 对照）

python frbox_selftest.py     # 1492/1492
python fr_selftest.py        # 63/63
```

固件从仓库 `data/` 读；要用别的目录就 `FRBOX_FW_DIR=/path/to/D300Update`。
完整命令（monitor、断点、快照、日志类别）见 [`docs/03-frbox.md`](docs/03-frbox.md) §11–12。

## 三句话说清现状（frbox 线）

1. **两台机器都跑到了固件自己停下为止，一次没崩。** A 段 43,446 步 / 824 个不同 PC /
   0 次中断，停在 `0x000FE50C` 的 `reti`；B 段 191,518 步 / 1,239 个 PC / 1 次中断，
   停在 `0x000407D8` 的 `reti`。~~之后 PC 从系统栈弹出 0 —— 是固件不再往下走。~~
   ⚠️ **V56 更正**：这句是 V11 修 S 位换支之前的旧现场。现在 A 段 `0x0FE50C reti`
   弹出的是 `0x0FE510`（固件自己的空闲任务），四种运行入口一致，详见 `results/frbox/ab56.txt` §B（KI#210）。
2. **停下来的原因找到了，是四处空桩。** A 段启动链 `0xFC000 → 0xF8010 → 0x80044 → 0x804FA`，
   第四跳是一条孤立 `ret`（正是 REALOS `vsta_knl()` 该在的位置），main 的第二条 `call 0x80520`
   同样是 `ret`。内核对象都建好了（4 个 TCB 在 `0x00045C38`，自引用空环、状态 0），
   **只是从没 `sta_tsk` 挂上就绪队列**。这四处空桩在 1.02/1.03/1.10/1.11 四版**逐字节一致**。
3. **那就跳过调度器。** `boottask` 手工构造任务上下文跳进任务 1（`0x8133A`）：1,981 步后
   到达第一个硬件等待 `0x0DCD2C`，期间踩过 500 个应用区 PC、发过 10 次 `int #0x40`、
   自己写了 6 个中断回调槽。中断通路本身是通的 —— 48 个向量全量注入，**39 个精确 `reti`
   回原位且 `r15`/SSP 逐位复原**（`results/frbox/isr-injection.txt`）。
4. **硬件等待不再需要手抠。** `--autospin` 在运行期读轮询指令用的那个寄存器，把就绪位
   置 1 后放行：三处忙等（`0x0DCD2C` 等 `0x0AF` bit7、`0x09C97A` 等 `0x174` bit6、
   `0x0CE134` 等 `0x524` bit6）**全自动认出，含第三处地址是算出来的那种**。
5. **任务表解出来了。** `0x0FE000` 头部 + 8 条 `0x1C` 字节记录，每条给 TCB / 任务号 /
   状态 / 入口 / 栈顶。任务 1 的栈顶是 **`0x0462EC`** —— 此前一直用的 `0x04616C`
   是表头那项，不是任何任务的栈顶。真正让任务正常返回的是 **RP**：`boot_task` 原来没设，
   于是沿用了引导阶段最后一次 `call` 的 `0x080500`。补上 `rp=0x81338` 之后，任务 1 跑
   **42,442 步**回到固件自带的 `bra -1` 停机占位，不再掉到地址 0。
   （栈顶反而无关：从 `0x45000` 到系统栈 `0x7F000` 五种取值，结果完全一样。）
6. **μITRON 会阻塞了。** `--itron-block` 让 `wai_flg` 真的会等：条件不满足就把机器置为
   「阻塞」并记下标志号 / 等待位 / PC。任务 1 在 **9,841 步**停在第一个握手上
   （`wai_flg(flag 3, 0x2000)`）。用 `--autoevent` 把事件补上，它走完整条启动链：
   **56** 次服务调用、**10** 次 `sta_tsk`、13 个握手事件，最后 `sys_ext_tsk` 退出。
   结论：**任务 1 是一次性初始化任务**，不返回、不循环。
7. **V10：固件自带的 REALOS 能原生跑，不用我们自己写调度器。** 真因只有一个 CPU 缺陷 ——
   `andccr`/`orccr` 改 CCR 的 S 位时不换 `r15`。修掉之后复位链一路跑到固件自己的派发点
   `0x000FE4E6`（43,428 步），上下文恢复靠翻 S 位在 SSP/USP 之间搬指针。
   任务表是 **13 条不是 8 条**（`*(0xFE000)=8` 是用户任务数）。
8. **V11：任务切换真的发生了。** 补上三样仿真台缺的东西 —— ILM 约定改回「号越小越优先、
   受理条件 `lvl < ILM`」、直接页 `0x44` 是「请求调度」寄存器（写 1 → 挂 `vec 0x3F`）、
   `0x3F4/0x3FC` 是硬件优先级编码器。100 万步里 `*(0x45980)` 换了 **6 次**：
   43,429 任务 1 → 43,516 任务 5 → 43,806 任务 1 → 44,614 任务 5 → 45,125 任务 1
   → 45,341 空闲任务，最后停在 `0x000FE510`（空闲任务的 `bra -1`），中途没停机。
   ⚠️ **A/B 两个模式的数字不能混着比**：A（只开 xfer）30 万步 1,888 次服务、`*(0x45980)`
   只写 1 次；B（再开 0x44）只有 14 次服务、写 6 次。
   ⚠️ 也**别读成「相机跑起来了」**：13 个任务只有 3 个上场，7 次调度全部来自内核自身的服务调用，
   没有一次是外设中断引发的。

> 老线（NikonEmulator）的三句话仍然成立，且是另一层结论：B 段显示管线能自动前进三级；
> 但"绘制"只是 `set_flg(0x0A, 0x8000); RET`，不是画像素；剩下的坎是串行口波形，不是隐藏分支。

| B 段行程 | 191,518 步 / 1,239 PC / 1 中断 / 停 `0x407D8`（复位链尽头，V20 及以前的止点） |

| B 段墙 1 拆除（V23） | 扫描起点来自 ROM 指针表 `0x1C2A98`（→ `0x740000`/`0x750000`，两块都在 7 MB 镜像之外）；按**擦除态 flash**（全 0xFF）建 1 MB `flash-erased` 后第一半字即命中终止符干净退出 |
| B 段墙 2 拆除（V23） | `0x5C003000` 是任务 2 专用硬件计数器窗口（固件 33 处引用全在 `0x120xxx–0x12Exxx`；+0x30 周期 0x813、+0x34 当前计数、+0x38 控制）；`0x125A0A` 连读两次等差值 → 挂 `FreeRunCounter`（每 tick +1）后拆除；⚠️0x813 对应频率未标定 |
| B 段开机装配（V23） | **任务 2 跑完开机装配**：set_tim + sem 握手（对象 1/16/20/21 成对）+ **11 次 sta_tsk**（拉起 26/5/17/4/9/27/28/1/21/7/16）+ chg_pri；一次派发 **+1349**、80 万步覆盖饱和（6,774 次调用；clr/wai_flg 各 3,373 对是主循环稳态） |
| B 段任务表（V23 修正） | 真实基址 **`0x54C00`**（V22 的 0x54C10 偏了 0x10）：+0x00 TCB 指针 / +0x04 任务号对 / +0x0C 激活标志 / +0x10 入口 / +0x14 栈顶；空闲任务 = 第 29 条 `@0x54F10`；TCB+0x24 背指表项，双向成链；V22「错位一格」由 0x10 位移完全解释 |
| B 段全开 28 任务（V23） | 任务 2 跑完装配进 `wai_flg` 阻塞让位后，**任务 2/3/4/5 四个入口都执行过**（覆盖 +1910，V22 同口径只有 +264）；终点 PC `0x40CEE`；新边界 = flag 3 位 0x200000 的置位者未证 |
| A 段位分派器逐位（V22） | 61 位顺序扫描：25 位 call 点执行 / 7 位自动应答 / 6 位带服务调用；最强位 `[0x3F40C]&0x20`（→`0x84900`）×64 **+2,822**；⚠️位间有状态耦合，顺序扫描 ≠ 干净机单点 |
| A 段 61 位干净机单点（V23） | 一位一台新机器全定性：**18 位 A 类**（目标函数真执行，+299~+369，前三 `[0x3F402]&0x40` +369 / `[0x3F403]&0x20` +341 / `[0x3F403]&0x01`+`&0x04` +333）/ 48 位 C 类（需前置状态）/ 0 位 B 类；与顺序扫描口径不可混比 |
| B 段服务分发表（V24） | **13 条**服务号→处理函数（动态抓 `call r12`）：`set_flg` 0x41A48 / `clr_flg` 0x41AE2 / `wai_flg` 0x41B0A / `wai_sem` 0x41902 / `sig_sem` 0x418C0 / `sta_tsk` 0x414C8 / `ter_tsk` 0x415A0 / `chg_pri` 0x4167C / `rcv_msg` 0x41D38 / `snd_msg` 0x41CDE / `set_tim` 0x40EDE；**`slp_tsk` 0x40660 与 `ext_tsk` 0x40664 是空桩** |
| flag 对象（V24） | `0x680008B8+(N-1)*0x10`：+0 自指 / +4 等待 TCB / +8 32 位位模式 / +0xC 背指表项；对象表 `0x551B0`（+4 对象指针、+8 `id<<16`）；flag 3 → 对象 `0x680008D8`、位模式 `0x680008E0` |
| ⭐wfmode 语义（V24） | **bit1(2)=OR 等待、bit0(1)=满足后清位**（与教科书 μITRON 相反，mode>3 走 E_PAR）；条件不满足时不是阻塞，而是「登记等待→请求一次重调度→复查」（满足 ≈102 步 / 不满足 ≈150 步）；**r12 恒 0 只表示受理，不代表等到** |
| 主循环事件（V24） | `0x120490 wai_flg(3, 0x80, 2)` 忙轮询（5 万步 188 圈，确定性）；0x80 的静态置位者 = 显示绘制路径 `0x12E630`；0x200000 的静态置位者 `0x12F1A8`；**42 条 ISR 无一能置 0x200000** |
| 计数器速率（V24） | `rate` 1 / 4 / 16 三种取值下，开机装配序列、覆盖集合、服务分布**完全一致**，只有总步数按比例缩短 —— 这道墙只要求「会走字」 |
| 门字节的写者（V25） | `0x9F58D08F` 共 **19 处**立即数引用；唯一写点是 **`0x12F180`**（`stb 1`），同一函数里紧跟 `set_flg(3,0x200000)`（`0x12F1A8`）—— V24「没人写」的真实含义是「这段代码没跑到」 |
| 开门实验（V25） | 手工置 1 后主循环走干活分支：**+102 地址**、调进显示区 `0x12E6F8`、置上 flag 6 `0x20` / flag 12 `0x800000` / flag 3 `0x8`；**只跑一次**就退回等待 —— 下一道门是状态字 `0x9F58D450` 的位 |
| 内核 RAM 上界（V25） | 任务 4（入口 `0x126454`）在 `0x1A4F9A` 把 ROM `0x25F534` 拷到 `0x68010000`，实测写到 **`0x6801DE84`**（14,242 次 4 字节写）→ `ram-kernel` 从 64KB 扩到 **128KB** |
| 任务停点（V25） | 全开 28 任务时 5 个上过场：任务 2 在 `0x12016C`（主循环清位）、任务 3 在 `0x12CEAA`（`wai_flg` flag5）、任务 4 在 `0x1A4FA4`（拷贝循环）、任务 5 在 `0x12E1D2`（服务 **-170**） |

## 两台机器

| | `d300-a` | `d300-b` |
|---|---|---|
| 角色 | IO 协处理 | 主控 / UI |
| ROM | `0x00080000` + 524,290 B | `0x00040000` + 7,340,032 B |
| RAM | `0x00001000–0x0007FFFF` | `0x00001000–0x0003EFFF` + `0x9F580000` 1 MB |
| TBR / SSP | `0x000FFC00` / `0x0007F000` | `0x000EFC00` / `0x0003F000` |
| 复位入口 | `0x000FC000` | `0x00040000` |

数字来源全部是固件自身：ROM 基址与长度 = 镜像大小；TBR = 向量槽里读出复位入口的那个基址；
RAM 上界 = 固件真正写过的高地址。`0x9F580000` 那块 1 MB 是"未映射写 6,000 多次"逼出来的。

**别忘了**：上面是 **CPU 地址**，读固件文件时 B 段要减 `0x40000`、A 段减 `0x80000`。
