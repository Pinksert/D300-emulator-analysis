A. boot 末的现场：一条待决派发
======================================================================
  步数 = 191520，当前 = 空闲
  就绪位图 = 0x80000000
  ICR 0x46F（vec 0x3F）= 0x1E
  CPU 待决派发 = 1 条，irq_pending = [(16, 63)]
  设备: {'请求（写 1）': 2, '挂中断': 1, '撤销（写 0）': 0, '被读': 2, '锁存位': 1, '向量': '0x3F', '最后级别': '0x10'}
  → boot 全程 i=0、ILM=0x10（整个 boot 只变过 6 次），
    所以 boot 里那两次写 1 挂上的中断一直躺在 CPU 待决队列里等开中断 ——
    **这就是 V39 之前必须人工补一次 vec 0x3F 的全部原因**。

C. 0x44 会被读：写后哑读（修正 V11 的「固件里从头到尾没有任何一处读它」）
======================================================================
  30 万步：写 64 次 / 读 64 次
    读 步  191595 pc=0x00040EAE → 0x0
    读 步  291609 pc=0x00041888 → 0x1
    读 步  291683 pc=0x00040EAE → 0x0
    读 步  291787 pc=0x00041888 → 0x1
    读 步  291861 pc=0x00040EAE → 0x0
    读 步  292261 pc=0x00041888 → 0x1
  读点只有两个：0x41888（写 1 之后）、0x40EAE（写 0 之后），
  两条后面紧跟 ret:d，读回值被丢弃 → **写后哑读**，不是读状态。
  但读回值本身说明了它是锁存器：写 1 之后读回 1，写 0 之后读回 0。

D. ICR 0x46F 的身份：48 条 ICR 里唯一不被 init 循环写的一条

  其中 task-2 的那个循环（pc 0x1209xx–0x120Cxx）写了 46 条：0x440..0x46E

H. kernel_call 不能和 dispatch=True 一起用
======================================================================
  kernel_call 的做法是「保存整份 CPU 现场 → eit(0x40) → 跑 → 恢复现场」。
  可派发一旦真的生效，服务里就会**换任务**：恢复现场等于把换手结果盖回去。
  sta_tsk(5) 返回 {'steps': 80000, 'err': 748}
  位图 0x80000000 → 0x80000000（位 28 = 任务 5 的那一位）
  ICR 0x46F 现在 = 0x10，当前 = 任务2
  → 8 万步上限用完也没回到 SAFE_PC，任务 5 的位没留在位图里。
    这是 V39 KI#161 的真实原因：**不是 ICR 时机，是调用方法**。

I. 边界：为什么只跑到 51.5 万步
======================================================================
  跑到步数 531520，当前 任务9
  覆盖 0x46F 的宽写 1 条：
    步 513781  pc=0x001356A0  st 0x46C n=4 ← 0x0
  ICR 0x46C..0x46F 现在是: 00 00 00 00
  最后一对事件：515018 REQ ICR=0x00 ILM=0x1F pc=0x00135B46 任务9
  → 任务 9 用一条 4 字节写把 vec 0x3C..0x3F 的 ICR 清零，
    派发器的级别变成 0 → 请求按 0x1F 挂上，永远不满足 level < ILM，
    于是整机停在最后一次请求之后不再换手。**不能报「系统跑起来了」。**
    能报的是：从 boot 到 51.5 万步，派发完全由固件自己驱动。

结论
======================================================================

1. 0x44 是**锁存器**：写 1 置位挂中断、写 0 清位并撤销待决项、读回锁存值。
   V11「固件从不读它」作废（写后哑读 2 处），V39 的「只置不清」补齐。
2. 0x46F = vec 0x3F 的 ICR，48 条里唯一不被 init 循环写的一条；内核服务入口
   抬到 0x1E、出口写回 0x10。服务期间 ILM=0x1E 正好挡住 0x1E 的派发请求，
   reti 之后 ILM=0x1F 才受理 —— V39 KI#161「受理时机」结案。
3. 打开 dispatch=True 之后整机**自己跑**：boot 后第一件事就是派发、换到任务 2，
   任务 2 把 3/4/5/6/7/9/10/11 依次挂起来，任务 5 上 CPU 后显示初始化自己跑完
   （294,388 步）。40 万步 24 次换手，两次运行逐条一致。
4. kernel_call 与 dispatch 不兼容（保存/恢复现场 vs 任务切换），V39 那条
   「sta_tsk 不返回、位图丢任务 5」是调用方法造成的，不是内核没请求派发。
5. 边界：51.5 万步时任务 9 一条 4 字节写清掉 ICR 0x46C..0x46F，派发器从此
   挂不上请求，整机停在那里。下一版要接的是「谁、在什么条件下清这批 ICR」。
6. 锁存的副作用已量化：A 段 boot 里 3 次写 1 由「挂 3 条」变成「挂 1 条」，
   首切 43,622 → 43,540、首次 set_flg 44,073 → 43,991（各 −82），其余不变。
   自检里这两条期望值按新语义换基线（见 J 段）。
